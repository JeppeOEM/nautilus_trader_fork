- (technique) started First Principles Thinking
- (idea by user) bedrock fact 1: every WS message carries some information about the order book
- (idea by user) bedrock fact 2: messages arrive ordered (in-sequence delivery)
- (insight by coach) RESEARCH: dYdX WS envelope carries message_id (monotonic per-connection int) + version string on every orderbook message. Rust handler.rs already tracks book_sequence per market, detects regression/dupes via message_id<=last_id (L381-402) but only logs a warning, never checks for GAPS (message_id==last_id+1), and never drops/resyncs. Fields are stripped before reaching Python (enums.rs DydxWsOutputMessage::Orderbook* carries no sequence field) - Python collector currently has zero access to this signal, relies purely on heuristic crossed-book + staleness checks
- (insight by coach) RESEARCH CONFIRMED: message_id is per-subscription (per market channel), not connection-global - dYdX docs say 'sequence number sent on the subscription', fixtures show each channel starts at message_id=1 independently, existing book_sequence map already keyed by market symbol. So per-market gap check (expected=last_id+1) is architecturally valid, no cross-channel collision risk
- (idea by coach) rebuild sketch: taint market's book instantly on message_id gap/regression (not on crossed-book symptom), stop emitting 1s snapshots for that market, targeted per-market resubscribe, clear taint only when a fresh full snapshot applies cleanly
- (decision by user) on detected corruption: discard that 1s bar entirely from parquet catalog (leave a genuine gap, not a flagged-but-present row) so ML/backtest naturally skip forward; separately log full orderbook context (before+after, with ts) to a housekeeping log for postmortem diagnosis of WHAT went wrong
- (insight by coach) RESEARCH CONFIRMED (user challenged the resubscribe assumption, correctly): dYdX orderbook updates are absolute-per-level (size replaces, size=0 deletes), NOT relative deltas - parse.rs L668-720 confirms no read-modify-write. A missed message only staleifies the specific levels it would have touched - bounded self-healing damage, not systemic corruption. No resubscribe/full-snapshot needed; book self-heals as soon as those levels get touched again
- (decision by user) Adopt professional-grade design: (1) real snapshot+buffer+replay resync on detected gap, not blind resubscribe or cooldown-heal; (2) sequence numbers (message_id) checked EXACTLY (expected==received), not just regression; (3) trade-print reconciliation as continuous free cross-check; (4) immutable raw capture wanted but must avoid TB-scale storage bloat - needs a bounded approach
- (insight by coach) RESEARCH: dYdX REST orderbook snapshot has NO anchor/sequence field (unlike Binance's lastUpdateId) - just bids/asks + coarse isoTimestamp. Binance-style precise buffer+replay resync isn't directly possible
- (idea by coach) But since orderbook updates are absolute-per-level (confirmed earlier), replay is idempotent - solves the missing-anchor problem: on gap, fetch REST snapshot as new base, then replay ALL buffered WS messages from slightly before the REST call onward with generous overlap; reapplying an already-included update is a harmless no-op. No precise anchor needed
- (idea by coach) Storage-bounded raw capture: don't archive raw messages 24/7 - keep a small rolling in-memory ring buffer (last ~30-60s) per market, only flush it to the housekeeping log when a gap/corruption is actually detected. Storage cost scales with number of corruption EVENTS, not connection uptime - matches user's original 'log context right before/after' idea exactly
- (decision by user) Converge via MoSCoW: user asked to move straight to stories+implementation
- (decision by user) Escalate: steady-state crossed-book firing (no known gap, not mid-reconnect, not mid-resync) is a CRITICAL/high-danger event - must be loud and distinctly visible, separate high-severity event log (not mixed with routine gap-triggered bar discards), since it means either a local bug or dYdX sent bad data undetectably. Moved from Should to Must.
- (insight) SYNTHESIS: session pattern = user repeatedly killed coach-proposed heuristics (blind resubscribe, cooldown) by asking 'why needed', forcing first-principles derivation of the real mechanism each time. Final design's three defenses (gap detection+resync, trade-consistency, crossed-book escalation) together answer the original ask: distinguish known-cause corruption from unknown-cause corruption, not just detect corruption.
