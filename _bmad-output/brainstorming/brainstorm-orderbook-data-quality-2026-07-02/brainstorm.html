01 First Principles

Strip it to bedrock.

The session opened by refusing every assumption about how order book quality gets protected, down to two facts nobody could argue with — the floor everything else had to be rebuilt on.

Axiom 01 — User

Every WebSocket message carries some information about the order book.

Axiom 02 — User

Messages arrive ordered — in-sequence delivery.

02 Research

The signal nobody reads.

If messages arrive ordered, something on the wire should prove it. Digging into the adapter found exactly that — and found it thrown away one layer before it could matter.

Every dYdX orderbook message carries message_id, a monotonic per-subscription counter, plus a version string. The Rust handler already tracks a book_sequence per market and checks for regressions and duplicates — but only logs a warning. It never checks for a gap (message_id == last_id + 1), and it never drops or resyncs on one.

A second pass confirmed the counter is safe to key per market: dYdX's own docs describe it as "the sequence number sent on the subscription," and fixtures show every channel starting its own count at 1. The existing book_sequence map is already keyed by symbol — so an exact per-market gap check (expected == last_id + 1) is architecturally sound, no cross-channel collision risk. docs + fixtures verified

03 First Draft

Taint, resubscribe, discard.

With the gap check validated, a first rebuild sketch went down on paper — reflexive, not yet interrogated.

Provisional

On a message_id gap or regression:

  • Instantly taint the market's book
  • Stop emitting 1s snapshots for that market
  • Fire a targeted per-market resubscribe
  • Clear the taint only once a fresh full snapshot applies cleanly

One piece of that sketch survived the session untouched — what happens to the data itself once corruption is caught: discard the 1s bar entirely from the parquet catalog, leaving a genuine gap rather than a flagged-but-present row, so ML and backtests skip forward naturally. Separately, log the full order book context — before and after, with timestamps — to a housekeeping log for postmortem.

04 The Challenge

Why resubscribe at all?

User, on the v1 sketch
taint → stop emitting → resubscribe → wait for a clean full snapshot Rejected
↓
Resolved by research

dYdX orderbook updates are absolute-per-level, not relative deltas — a size replaces the level, size = 0 deletes it. There is no read-modify-write to corrupt.

Which means a missed message only staleifies the specific levels it would have touched. That's bounded, self-healing damage — not systemic corruption. No resubscribe. No full snapshot. The book heals itself the instant those levels get touched again.

05 Escalation

Four pillars, not one heuristic.

The resubscribe reflex was gone, but so was the comfort of a single rule. The design that replaced it stands on four independent legs, each answering a question the last one couldn't.

01

Exact sequence check

expected == received, not just regression — a skipped message_id is caught the instant it happens.

02

Buffer + replay resync

On a real gap: a real snapshot, buffered messages, idempotent replay — not a blind resubscribe, not a cooldown timer.

03

Trade cross-check

Trade-print reconciliation running continuously as a free, independent second opinion on the book.

04

Bounded raw capture

Immutable context wanted for postmortem — without paying for it at TB scale, 24/7.

06 Second Challenge

No anchor. Replay it anyway.

Pillar 02 needs a base to resync from. Binance solves this with lastUpdateId — an anchor stamped on its REST snapshot that a WS replay can align to. dYdX's REST orderbook snapshot has no such field — just bids, asks, and a coarse ISO timestamp. A precise, Binance-style buffer-and-replay looked closed off.

Problem

REST snapshot carries no sequence or anchor field to align a WS replay to.

↺Solved by 04's finding

Resolution

Updates are already known to be absolute-per-level, so replay is idempotent. Fetch the REST snapshot as a new base, then replay every buffered WS message from slightly before that call, with generous overlap. Reapplying an already-included update is a harmless no-op — no anchor needed.

Storage

Raw capture stays bounded: a small rolling in-memory ring buffer (~30–60s) per market, only flushed to the housekeeping log when a gap or corruption actually fires. Storage cost scales with the number of corruption events, not connection uptime.

Critical
07 Escalation

The book crosses. Nothing else is wrong.

A crossed book — best bid at or above best ask — is normally a routine symptom of a known gap, caught and explained by the sequence check. But sometimes it fires in steady state, with none of the usual excuses available.

no known sequence gap not mid-reconnect not mid-resync

When a crossed book shows up under those conditions, it means exactly one of two things: a local bug, or dYdX sent bad data the gap detector can't see. Either way it must be loud — a separate high-severity event log, never mixed in with routine gap-triggered bar discards.

Should → Must — explicitly re-prioritized this session
08 Synthesis

Three defenses, one answer.

The shape of the whole session: every time a heuristic got proposed — resubscribe, a cooldown timer — it got killed by the same question, why is this needed, and answered by going one layer deeper into the actual protocol. What's left is not one detector but three, each covering what the others structurally cannot.

Known cause

Gap detection + idempotent resync — catches a missed message the instant the counter proves it, and repairs without guessing.

Silent cause

Trade-consistency cross-check — an independent signal that doesn't depend on the WS stream being honest about itself.

Unknown cause

Crossed-book escalation — the tripwire for damage that leaves no sequence footprint at all.

Together they answer the original ask precisely: not just detect corruption, but tell known-cause corruption — recoverable, self-healing, logged routinely — apart from unknown-cause corruption, which has to be loud.
