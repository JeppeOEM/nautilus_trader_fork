# Story 2.3: HFT-granularity and configurable-timeframe backtesting on the same underlying data

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a strategy developer,
I want to backtest at raw Snapshot (0.5s/1s) granularity as well as at slower, configurable candlestick timeframes derived from the same capture,
so that I can validate both HFT-style and structural signals without re-collecting data or writing a second backtest path.

## Acceptance Criteria

1. **Raw `DydxSecondSnapshot`-granularity backtesting (FR12).** Given a strategy that consumes raw `DydxSecondSnapshot`-granularity data, when it is backtested, then `BacktestNode` + `BacktestDataConfig` streams the Snapshot data directly, with no full-catalog in-memory load.
2. **Configurable candlestick timeframe (FR12).** Given a strategy that consumes candlestick bars, when it is backtested, then the candlestick aggregation window is a config value (e.g. 1s, 1m, 5m) requiring no code change, and bars are derived from the same underlying captured data as the HFT path.
3. **No custom simulation loop (FR11).** Given both backtest paths, when either runs, then no custom simulation/matching loop exists anywhere in `troll/` — both go through `BacktestNode`/`BacktestEngine` only.
4. **String-path strategy reference (FR11).** Given a strategy referenced for either timeframe, when it's configured, then it is referenced via `ImportableStrategyConfig` by string path, enabling parameter sweeps/time-range filtering with no code changes.

## Dev Notes

**This is the largest story in Epic 2 so far — it adds genuinely new capability (nothing here is "confirm-and-document" like Story 2.2's Task 1).** Two real, substantial pieces of new work: (1) a config-driven wall-clock candlestick timeframe added to the existing tick-bar backtest path, and (2) an entirely new strategy + backtest driver consuming a data type nothing currently consumes (`DydxSecondSnapshot`).

**Real architectural fork found during story research — already resolved above in Task 1, do not re-derive or second-guess it during implementation:** "candlestick bars derived from the same underlying captured data as the HFT path" has two non-overlapping possible implementations (Nautilus-native internal `TradeTick` aggregation vs. a new `DydxSecondSnapshot`-derived candle type + batch materialization job). The native-aggregation route was chosen for being simpler, already-proven in this codebase (`example_strategy.py`'s `bar_type` config field), requiring zero new Nautilus-Data-type infrastructure, and trivially satisfying AC3 (no custom sim/aggregation loop, since none is built). This directly determines `resample.py`'s fate (dead, delete it) — that decision is made, not open.

**`BacktestDataConfig`'s `bar_spec`/`bar_types` params only ever build an `-EXTERNAL` bar catalog query — they never aggregate anything.** Confirmed via `nautilus_trader/backtest/config.py`'s `BacktestDataConfig.query` property. `backtest_ofi.py`'s existing `BacktestDataConfig(data_cls=Bar, bar_spec="1-MINUTE-LAST")` + `OFIStrategyConfig.trend_bar_type_str` (`"-EXTERNAL"` suffix) queries for pre-existing `Bar` rows in the catalog — but **the collector never writes `Bar` objects** (confirmed: `catalog_stats.py:179`'s own comment says so explicitly, and no writer path exists anywhere in `troll/`). This means `ofi_strategy.py`'s 30-minute trend-EMA gate has silently never activated in any real backtest run against real collected data. **This is a real, pre-existing bug in `backtest_ofi.py`/`ofi_strategy.py`, discovered during this story's research — but `ofi_strategy.py` is out of scope for this story (per Project Structure Notes below) and this story's own new `bar_interval` work uses `-INTERNAL` bars, not `-EXTERNAL`, so it doesn't touch this bug's code path.** Log it to `deferred-work.md` as a separate, real finding — do not fix it here, and do not let it block this story.

**Precedent for `DydxSecondSnapshot` being backtest-ready:** it's already a correctly-registered Nautilus `Data` subclass (`register_arrow()`, `schema()`, `ts_event`/`ts_init` properties) and is already written to the catalog by the collector (`collector.py`'s `_second_loop`→`_on_data_unsafe`→`_flush_once`→`catalog.write_data()`, all pre-existing, unmodified by this story). The gap is purely on the consumption side — nothing subscribes to it as a `Strategy`. `Actor.subscribe_data`/generic `on_data` dispatch (`nautilus_trader/common/actor.pyx`) is the mechanism; verify its exact metadata-filtering convention against the real API before writing `SnapshotStrategy`, don't guess the signature.

**Why `MultiLevelOBI`/`MultiLevelOFI` are the right indicators for `SnapshotStrategy`:** both already expect exactly the list-shaped `bid_sizes`/`ask_sizes` (`MultiLevelOBI`) or `bid_prices`/`bid_sizes`/`ask_prices`/`ask_sizes` (`MultiLevelOFI`) input `DydxSecondSnapshot` provides natively — no adaptation needed, and Story 2.2's own audit found these two indicators had only one real consuming context (`dashboard.py`'s live monitor). This story's new strategy gives them a second (backtest), continuing Story 2.2's FR10 intent as a natural byproduct, not scope creep back into that story.

**Precision rule (AD-5) — not applicable.** This story constructs no new `Price`/`Quantity` re-stamping; `DydxSecondSnapshot`'s prices are already correctly captured by the collector.

**Architecture grounding:** FR11/FR12 (PRD §4.4, per epics.md's citations) are the primary rules. AD-6 (catalog access only through the official API) governs both new/modified `BacktestDataConfig` usages — neither introduces a hand-rolled schema or an unbounded `catalog.trade_ticks()`-style call. AD-4 (module boundary) is unaffected — no new collector↔ml_signals coupling beyond the existing, already-adopted `DydxSecondSnapshot` type import.
