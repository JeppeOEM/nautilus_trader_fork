# Story 4.4: Bots pane with start/stop control

Status: done

## Story

As the operator,
I want a live list of running bots with independent per-bot health, and the ability to start/stop one directly,
so that I can see which bots need attention and act on them without leaving the terminal.

## Acceptance Criteria

1. **Bots pane (`:bots`) shows one row per bot from `bots:status`.** Given the Bots pane, when it renders, then it shows one row per bot: bot_id, sign-colored PnL, strategy/symbol, mode (paper/live), position/exposure, uptime/last-heartbeat, win-rate-to-date (FR18, UX-DR4).
2. **A missed heartbeat stales exactly one row, never the whole pane.** Given a specific bot's `bots:status` heartbeat, when it is missed within the configured timeout, then that bot's row alone shows a stale badge -- a healthy bot next to a crashed one shows exactly one stale row, never a pane-wide flag (FR18, UX-DR7).
3. **`s` publishes a start/stop command with a footer-echo confirmation, never optimistic.** Given a bot row (in the Bots pane or Bot-detail), when the builder presses `s`, then it publishes `{bot_id, action: "start"|"stop"}` on `bots:control` -- never a mode/paper-live parameter -- and the row shows a one-line footer echo (`sent: start bot-07`) confirming the command was sent, not that it succeeded; there is no optimistic local state change (FR23, UX-DR4, architecture AD-10).
4. **The config-gate (paper vs. real-money) is unreachable from this control.** Given the start/stop control's config-gate, when the operator attempts to change whether a bot runs paper or real-money, then it is unreachable from this control -- that gate lives solely inside `live_paper`'s own separate config (FR15, FR23).

Bot-detail's own `s` (Story 4.5) is out of scope here -- this story covers the Bots-pane row-level control only.

## Dev Notes

### Judgment calls -- read before extending this story

1. **`bots:status`/`bots:control` did not exist before this story; building the `live_paper` publisher was in scope, not a blocker to escalate.** The epic's own architecture description already specified the exact wire contract (fields, heartbeat cadence, channel names) as a *given* -- treated here as the specification for `bot_status.py` to implement, not as evidence it already existed. Verified by grep before writing any code (zero matches for either channel name anywhere in `troll/`).
2. **The status/control loop lives outside the Strategy's own component lifecycle.** See Task 1's second bullet -- a Strategy-internal timer stops firing once `Stopped`, which would make `s` a one-way door (can stop, can never restart). Scheduled instead as a bare asyncio task on `TradingNode`'s own loop via `node.get_event_loop().create_task(...)`.
3. **Bots-pane scroll-position preservation was deliberately scoped out, unlike the Coins pane's Story 4.3 fix.** That fix existed because AC6 required surviving a `Coins -> Coin-detail -> Coins` round trip; this story has no equivalent round trip yet (Bot-detail's `Enter`/`esc` is Story 4.5). Building the persistence machinery speculatively ahead of an AC that requires it would be exactly the kind of premature abstraction `troll/CLAUDE.md`'s DESIGN-01 (YAGNI) warns against. Logged in deferred-work.md for Story 4.5 to revisit if it turns out to matter.
4. **`s`'s start/stop direction is decided from `bots_state`'s last-known `running` field**, which can be stale (see deferred-work.md) -- accepted because the alternative (disabling `s` on a stale row) is a real UX decision beyond this story's literal ACs, not attempted here.
5. **Total PnL for the row/color decision is `realized_pnl + unrealized_pnl`.** AC1 says "sign-colored PnL" without specifying which; combining both is the only reading that reflects the bot's actual current standing (realized alone would hide an open loss/gain).
6. **No manual/interactive smoke check this session** (see Task 5's last bullet) -- this is the one place this story's own verification falls short of Stories 4.1-4.3's documented precedent, and is called out explicitly rather than silently claimed as done.

### Testing strategy: pure logic vs. urwid/asyncio wiring (extends Stories 4.1-4.3's split)

Unchanged in shape: `bots_pane.py` is fully pure and fully unit-tested; `bots_state.py`/`bot_status.py` mirror the existing "stateful module-level Redis-connected reader/writer, unit-testable via direct function calls with synthetic messages, the actual listener/heartbeat coroutines left to a manual check" split. `build_status` is the one exception worth calling out: because it reads a real `Strategy.portfolio`/`.cache`, it's tested against a genuine `BacktestEngine`-run `DummyStrategy` (per TEST-03's "never mock Nautilus internals... or skip the test entirely") rather than being treated as pure/synthetic-input-only.

### Module boundary (AD-4/AD-8/AD-9/AD-10) -- restated and satisfied

`bot_status.py` lives in `troll/live_paper/`, the one place `TradingNode`/`Strategy` usage is sanctioned (AD-8) -- it imports `nautilus_trader.trading.strategy.Strategy` directly, which `test_ad8_boundary.py`'s reader-module guard would reject if it appeared in `bot_tui/`. `bots_pane.py`/`bots_state.py` (in `bot_tui/`) contain no such import -- both added to `test_ad8_boundary.py`'s `_READER_MODULES` tuple and pass the existing banned-substring check. Neither `bot_tui` module reaches into `live_paper` internals; both are pure Redis clients of the published `bots:status`/`bots:control` contract, exactly as AD-10 specifies.
