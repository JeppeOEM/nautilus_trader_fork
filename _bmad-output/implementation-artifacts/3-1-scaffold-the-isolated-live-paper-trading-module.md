# Story 3.1: Scaffold the isolated live/paper-trading module

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the builder/operator,
I want the paper-trading strategy to live in its own module, structurally separate from the data-collection/reading path, with real-money execution unreachable by any default or accidental config,
so that trading logic can safely be the one place `TradingNode`/`Strategy` is used without risking the collector's stability or accidentally trading with real funds.

## Acceptance Criteria

1. **Module isolation (FR15, AD-4).** Given the new live/paper-trading module, when its location and imports are reviewed, then it lives outside `dydx_collector/` and `ml_signals/` (a new top-level module under `troll/`), and depends only on shared data types and pure utilities from those packages — never their stateful internals.
2. **AD-8 boundary holds (FR15).** Given `dydx_collector` and `ml_signals`'s existing reader modules, when they are reviewed after this story, then none of them import `TradingNode`, `Strategy`, or `DataEngine` — that usage is confined entirely to the new module.
3. **Paper mode by default (FR15).** Given the new module's default configuration, when it starts with no explicit override, then it runs in paper mode only.
4. **Real money requires a deliberate, separate step (FR15).** Given a desire to enable real-money (non-paper) execution, when the operator attempts it, then it requires an explicit, separate configuration step that is not reachable by any default or accidental config state — a distinct field/file that must be deliberately set, never a flag flippable by a typo or default fallback.
5. **Docker deployment pattern (architecture spine).** Given the new module, when Docker deployment is considered, then it follows the existing two-image split pattern (thin layer on `nautilus-trader-base`), consistent with the architecture spine's deployment convention.

## Dev Notes

**This is a genuinely new module, not an extension of anything existing.** Per epics.md's own Epic 3 intro: "no live/paper-trading module exists yet (only `example_strategy.py`/`ofi_strategy.py`, both backtest-only) — this epic is genuinely net-new, the first sanctioned `TradingNode`/`Strategy` usage in `troll/`." Confirmed via `grep -rn "TradingNode\|DataEngine" troll/`: the only hits are `dydx_collector/client.py`/`collector.py` docstrings *explaining why they don't use it* — there is no existing `TradingNode`/`DataEngine` code to generalize or migrate. Note `grep -rn "import Strategy" troll/ml_signals` **does** find three real, pre-existing hits (`example_strategy.py`, `ofi_strategy.py`, `snapshot_strategy.py`) — these are the backtest-only `Strategy` subclasses epics.md itself names above; AD-8 does not restrict `Strategy` usage in general, only `TradingNode`/`DataEngine` misused as a data-capture mechanism in the named reader modules (see Task 1's regression-test scoping).

**AD-8 was deliberately amended to carve out exactly this exception — read it before designing anything.** `_bmad-output/planning-artifacts/architecture/architecture-nautilus_trader_fork-2026-07-01/ARCHITECTURE-SPINE.md`'s AD-8 binds `dydx_collector`/`ml_signals`'s *data collection and reading* paths only, and explicitly states: "`TradingNode`/`Strategy` used for their intended purpose — running an actual (paper or live) trading strategy — is in scope for a new, separate module outside `dydx_collector`/`ml_signals`'s data path. The prior incident was `TradingNode` misused as a recorder, not `TradingNode` used to trade; this distinction is load-bearing and must not collapse back into a blanket ban." Do not treat `troll/CLAUDE.md`'s "never instantiate `TradingNode`" project-context rule as applying to this new module — that rule documents the `dydx_collector`/`ml_signals` boundary this story is specifically, deliberately outside of.

**"Paper mode" for dYdX means live data + `SandboxExecutionClientConfig`, not a `DydxExecClientConfig` flag.** dYdX v4 is a DEX — `DydxExecClientConfig` signs and submits real on-chain transactions via a wallet private key and gRPC; there is no "paper" mode inside that client itself. The correct mechanism (already a working pattern in this repo, do not reinvent) is `examples/sandbox/dydx_sandbox.py`: live `DydxDataClientConfig` (market data only, no wallet) feeding an in-process `SandboxExecutionClientConfig`/`SandboxLiveExecClientFactory` simulated exchange. This structurally makes real money unreachable in the default path — there is no wallet address or private key anywhere in the paper-mode config at all, not merely a disabled flag. Contrast with `examples/live/dydx/dydx_market_maker.py`, which shows the real-money shape (`DydxExecClientConfig` + `DydxLiveExecClientFactory`, requires `DYDX_WALLET_ADDRESS`/`DYDX_PRIVATE_KEY` env vars) — that entire code path must live behind Task 2's deliberate, separate config gate, never constructed by default.

**AC4's bar is high: "not reachable by any default or accidental config state."** A single `paper: bool` toggle fails this — a typo'd `paper = flase` in TOML, or a missing key defaulting the wrong way, is exactly the accidental-state AC4 forbids. Design for **two independent signals that must both explicitly agree** (see Task 2) so no single mistake (wrong file, missing field, stale copy-paste) can silently produce a real-money start. When in doubt, fail closed to paper mode or hard-error — never fail open to real money.

**Precision rule (AD-5) — not directly applicable yet.** This story constructs no `Price`/`Quantity` values itself (no strategy logic). Story 3.2, which will process live tick data through indicators, is where AD-5 becomes load-bearing — flagged here so it isn't forgotten when that story starts.

**Native-abort mitigation is required, not optional, for the new test file.** `deferred-work.md`'s "Resolved: root cause..." entry explains the underlying `log`-crate-level `set_boxed_logger()`-can-only-succeed-once constraint and the session-scoped never-disposed-guard fixture that fixes it (already applied in `ml_signals/tests/conftest.py`). Because `live_paper/tests` is a **new, separate pytest collection root**, it does not automatically inherit that fixture — it must be added fresh to `live_paper/tests/conftest.py`, or the first `TradingNode`/`BacktestEngine` construction in this new test directory risks the same `Fatal Python error: Aborted` depending on collection order and process history. Read the full deferred-work.md entry before writing this test, not just this summary.

**Module dependency direction, extended for this story:** the existing convention (`ARCHITECTURE-SPINE.md`'s Consistency Conventions table) is `ml_signals` → `dydx_collector` (data types only), never the reverse. This story adds a third module: `live_paper` may depend on `ml_signals`'s and `dydx_collector`'s **shared data types and pure utilities only** (AC1) — never on `dydx_collector.collector`'s stateful buffer/flush-loop internals, never on `ml_signals.dashboard`'s live Redis/SSE server internals. For Story 3.1 specifically, the honest answer is this scaffold needs **zero** such imports yet (no strategy/indicator wiring until Story 3.2) — don't manufacture a dependency that isn't needed yet just to demonstrate the pattern.

**Docker pattern to mirror exactly, not reinvent:** `troll/collector.dockerfile` + its `docker-compose.yml` service entry. Same base image (`nautilus-trader-base:1.229.0`), same thin-layer shape, same `logging: *default-logging` anchor, same `network_mode: host`. Do not introduce a third build pattern.
