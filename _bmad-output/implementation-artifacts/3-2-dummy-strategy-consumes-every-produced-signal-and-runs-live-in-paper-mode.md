# Story 3.2: Dummy Strategy consumes every produced signal and runs live in paper mode

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an operator,
I want to start a `TradingNode`-based Dummy Strategy that wires together every indicator/signal produced by the research side and runs against live dYdX market data in paper mode,
so that I can see the full research → backtest → live loop actually close, proving every validated signal works end to end without risking real capital.

## Acceptance Criteria

1. **All Epic 2 signals consumed, no reimplementation (FR10, FR14).** Given the indicators/signals implemented in Epic 2 (`Microprice`, `OrderFlowImbalance`, `MultiLevelOBI`, `MultiLevelOFI`, `OnlineLogisticTrend`, and any others), when the Dummy Strategy starts, then it consumes all of them via the same shared implementation used in research/backtest — no reimplementation for the live context.
2. **Live paper execution via TradingNode (FR14).** Given the Dummy Strategy is running, when it processes live dYdX market data, then it does so via `TradingNode` in paper mode, placing paper orders driven by the wired-in signals.
3. **New indicators plug in without a strategy rewrite (FR10 consequence, restated for FR14).** Given a new indicator is added to `ml_signals/indicators.py` in the future, when the Dummy Strategy is next started (or reloaded per its config), then the new indicator becomes available to it without a rewrite of the strategy's data-plumbing code.
4. **Unattended resilience (NFR2).** Given the strategy runs continuously, when it operates unattended, then it satisfies NFR2 — capable of running in paper mode against live data for at least one week without manual intervention (handles reconnects/errors without crashing).
5. **Precision discipline (NFR5, AD-5).** Given the strategy touches `Price`/`Quantity` values from live data, when it processes them, then it follows AD-5's precision rules — no `Price(decimal, precision)` re-stamping, no `float` round-tripping before a value is safely inside a `Price`/`Quantity`.

## Dev Notes

**Read Story 3.1's story file (`3-1-scaffold-the-isolated-live-paper-trading-module.md`) and `deferred-work.md`'s Story 3.1 entries before starting** — `live_paper/config.py`/`node.py`'s existing shape, the paper/real-money config split's structural-isolation requirement, and the native-abort-mitigation fixture are all load-bearing context this story builds directly on top of, not background.

**This story's central, non-obvious design work is sourcing the right live data feed for each indicator — the backtest code does not show this directly, since it reads from `DydxSecondSnapshot`/`QuoteTick`/`Bar` rows already materialized in the catalog.** Live, there is no `DydxSecondSnapshot` object at all (that type is built by `dydx_collector.collector`'s own stateful 1-second-aggregation loop — importing that logic here would violate AD-4's "no stateful internals" boundary). The correct live equivalent for `MultiLevelOBI`/`MultiLevelOFI` is building the same shape (top-N bid/ask price/size lists) directly from `TradingNode`'s own live order book via `self.cache.order_book(instrument_id)`, sampled on a periodic 1-second timer to preserve the same cadence the indicators were calibrated against in backtest. Do not reach for Redis/`snapshots:1s` as a shortcut either — `live_paper` deliberately does not depend on the `dydx_collector` container being alive at all (Story 3.1's whole point was a `TradingNode` fed directly from dYdX, independent of the collector); introducing a live_paper→collector runtime dependency here would be a real, unflagged architectural regression.

**AD-4 applies to this story's imports just as much as Story 3.1's.** `ml_signals.indicators`'s five classes are the only import needed from either sibling package — they are pure, stateless-at-import, side-effect-free classes (confirmed in Story 3.1's Dev Notes for the module generally; re-confirm no indicator does I/O). Do not import `ml_signals.watchlist`, `ml_signals.dashboard`, or any `dydx_collector` module beyond what Story 3.1 already established.

**AD-5 (precision) becomes load-bearing in this story for the first time** — Story 3.1 explicitly deferred it ("constructs no `Price`/`Quantity` values itself"). Every indicator call in this story reads `.as_double()` off an existing `Price`/`Quantity` (never constructs a new one at a different precision), which keeps this story naturally compliant — but verify no code path re-stamps a value (e.g. when building the book-snapshot lists for `MultiLevelOBI`/`MultiLevelOFI`) via anything other than a plain `.as_double()` read.

**"Dummy Strategy" is deliberately unsophisticated** — the epic's own name for it, and its stated purpose ("proving the loop closes," `epics.md`'s Epic 3 intro), not a request for a well-tuned trading strategy. Resist the temptation to port `ofi_strategy.py`'s full multi-gate design; a simple, honest combination of 2-3 signals is the right scope.

**Module dependency direction is unchanged from Story 3.1**: `live_paper` → `ml_signals`'s shared data types/pure utilities only (now actually exercised, for the first time, by this story's indicator imports) — never `ml_signals`'s stateful internals, never anything from `dydx_collector` beyond what's already used.

**Precedent for live strategy attachment**: `examples/sandbox/dydx_sandbox.py`'s `node.trader.add_strategy(strategy)` — read and mirror this exact call shape, not the backtest `ImportableStrategyConfig` pattern.
