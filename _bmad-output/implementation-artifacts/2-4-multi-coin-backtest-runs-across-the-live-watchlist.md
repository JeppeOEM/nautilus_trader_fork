# Story 2.4: Multi-coin backtest runs across the live Watchlist

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a strategy developer,
I want to run a single backtest across every coin currently in the Watchlist, not just one hardcoded symbol,
so that I can validate a strategy's behavior across the full ranked opportunity set at once.

## Acceptance Criteria

1. **Watchlist as instrument universe (FR13).** Given the Watchlist API/function built in Story 1.3 (`ml_signals.watchlist.fetch_watchlist`), when a backtest run is configured, then it accepts the Watchlist's current coin-set as its instrument universe instead of a single hardcoded `symbol` parameter.
2. **No manual per-coin config editing (FR13).** Given a `BacktestNode` run configured this way, when it executes, then `BacktestDataConfig` (and the rest of the per-coin `BacktestRunConfig`) is built for each Watchlist coin programmatically — no manual per-coin config editing.
3. **Watchlist membership changes require no code change (FR13).** Given a coin enters or leaves the Watchlist between backtest runs, when the backtest is re-run, then its instrument set reflects the current Watchlist automatically.
4. **Per-coin results stay distinguishable.** Given a multi-coin run, when results are produced, then per-coin results remain distinguishable (not silently aggregated into a single undifferentiated result), so ranking-vs-performance can still be analyzed per coin.

## Dev Notes

**This story closes the exact gap epics.md names for Epic 2:** "`backtest_dydx.py` is single-symbol/single-timeframe only (no multi-coin, no raw-Snapshot-granularity path)" — Story 2.3 already closed the raw-Snapshot-granularity half (`backtest_snapshot.py`) and the configurable-timeframe half (`bar_interval`). This story closes the remaining multi-coin half, on the same `backtest_dydx.py` driver Story 2.3 already modified — read that story's Dev Agent Record/Completion Notes before starting, its findings about `BacktestNode.run()`'s reliable `list[BacktestResult]` return value and the native-crash test-file constraints both directly apply here.

**Story 1.3 already proved the exact compatibility this story needs.** `troll/ml_signals/tests/test_watchlist.py::test_watchlist_ids_are_backtest_data_config_compatible` already demonstrates that `fetch_watchlist()`'s returned instrument-ID strings feed directly into `BacktestDataConfig(instrument_id=InstrumentId.from_str(iid), ...)` with no per-coin editing — this story's Task 1 is essentially generalizing `backtest_dydx.py`'s existing single-symbol wiring to loop over this same already-proven list, not inventing a new integration.

**`fetch_watchlist()` has a hard runtime dependency this story must not paper over:** it requires a running `ml_signals` dashboard process reachable over HTTP (`watchlist.py`'s own docstring states this explicitly) — there is no other queryable store of "current live ranking" (Story 1.4's persisted `rank_history.py` is a *historical* query path, not a live one; do not conflate the two or try to use `rank_history` here, it is out of scope). This means:
- Any committed test must pass an explicit `symbols` list or monkeypatch `fetch_watchlist`/`urlopen` — never require a live dashboard in `ml_signals/tests`.
- The `run()` function's default behavior (Watchlist-driven, `symbols=None`) is the "no code change to add/remove a coin" mechanism (AC3) but is inherently only end-to-end-verifiable manually against a running dashboard+collector, same caveat Story 2.3 already accepted for its own manual verification steps.

**Per-coin independence is the simplest correct design, not a shortcut.** Building N fully independent `BacktestRunConfig`s (each with its own venue/portfolio/strategy instance) rather than trying to run multiple instruments through one shared venue/portfolio avoids any cross-coin state coupling, keeps AC4's "per-coin results remain distinguishable" trivially true (no aggregation logic to get wrong), and matches every existing single-symbol script's structure exactly (`backtest_dydx.py`, `backtest_ofi.py`, `backtest_snapshot.py` all build exactly one venue/one portfolio per run today) — this story scales that established shape to N coins via a loop, it does not introduce a new backtest architecture.

**`BacktestNode(configs=[...])` already supports multiple configs in one call — confirmed via the type signature and Story 2.2/2.3's own `BacktestNode` usage; this story's job is constructing the list, not extending `BacktestNode` itself.** Verify the exact `BacktestResult` return ordering (list order == input `configs` order) against the real pinned-version source before relying on positional zip — do not assume, check `nautilus_trader/backtest/node.py`'s `run()` implementation directly, same "verify against real source, don't guess" discipline Story 2.3 applied throughout.

**Precision rule (AD-5) — not applicable.** This story constructs no new `Price`/`Quantity` re-stamping; it only changes which/how-many `BacktestRunConfig`s are built from already-correct catalog instruments.

**Architecture grounding:** FR13 (PRD, per epics.md's citation) is the primary rule. AD-6 (catalog access only through the official API) is unaffected — no new catalog access pattern, just more `BacktestDataConfig` instances of the same already-correct kind. AD-4 (module boundary) is directly relevant: `backtest_dydx.py` (ml_signals) importing `ml_signals.watchlist.fetch_watchlist` is an intra-module import, not a boundary violation — `watchlist.py`'s own docstring already confirms it was deliberately kept dependency-light (no aiohttp/plotly/redis/indicator imports) specifically so a backtest script could import it cheaply; this story is the first real consumer of that design intent.
