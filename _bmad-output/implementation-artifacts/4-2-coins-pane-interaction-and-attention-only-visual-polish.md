# Story 4.2: Coins pane interaction and attention-only visual polish

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the builder,
I want the Coins pane to be filterable, mode-switchable, and visually quiet except when something needs my attention,
so that I can scan and narrow the ranked list quickly without the display fighting for my eye's attention on healthy state.

## Acceptance Criteria

1. **`/` opens an inline fuzzy-filter; `esc` clears it without leaving the pane.** Given the Coins pane, when the builder presses `/`, then an inline fuzzy-filter opens, narrowing visible rows by substring match against instrument ID as the builder types; `esc` clears the filter without leaving the pane; a filter with no matches renders `no matches` in place of rows rather than hiding the pane (FR21, UX-DR3).
2. **`m` toggles Ranking Mode via `ranking:control`, reflected once `ranking_engine` confirms.** Given the Coins pane, when the builder presses `m`, then the active Ranking Mode toggles between volume and volatility by publishing to `ranking:control` (Story 1.8) — reflected immediately once `ranking_engine` confirms the switch on `rankings:live` (FR19, UX-DR3).
3. **Rank order carries zero color; only the pane-level stale badge is colored.** Given the Coins pane's rows, when they render, then rank order itself carries zero color — only a per-pane stale badge (tied to the `ranking_engine` heartbeat) uses `{colors.attention-stale}`; every other row renders in the terminal's own inherited default foreground/background (FR22, UX-DR1, UX-DR7).
4. **General color/typography rule.** Given the TUI's color and typography implementation generally, when any state is rendered, then the base is the terminal's own default fg/bg (no fixed hex palette), monospace is the only typeface used, and size is never used for emphasis anywhere — emphasis is color-first, with bold/standout only ever as a secondary reinforcing channel (UX-DR1, FR22).
5. **`rankings:live` staleness detection → pane-level stale badge, last-known ranking keeps rendering.** Given `rankings:live` goes stale (no heartbeat within the configured timeout), when this is detected, then the Coins pane shows its own pane-level stale badge while continuing to render the last-known ranking — never silently frozen and never dropped (UX-DR7, architecture AD-9).

## Dev Notes

**This story extends, never replaces, Story 4.1's already-shipped, already-reviewed code.** All three of `bot_tui`'s production files (`ranking_state.py`, `coins_pane.py`, `app.py`) already exist and already pass their own tests; every task above is an addition to a specific existing function or a small number of new sibling functions in the same file, not a rewrite. The engineering risk here is concentrated in three places, each with its own explicit gotcha called out in the Tasks above: (1) `urwid.Edit`'s `"change"` signal is the only way to get live-narrowing-while-typing, and it's a genuinely different wiring shape than Story 4.1's command bar (which only reacts to `enter`/`esc`, never individual keystrokes); (2) the `m` key's "wait for real confirmation, never flip a local variable" discipline is easy to accidentally violate by reaching for the seemingly-simpler optimistic-update approach; (3) Story 4.1's `_redraw_loop`'s identity-diff-only trigger condition will silently swallow this story's stale-badge visibility unless its trigger condition is loosened — a bug that a quick manual check could easily miss (see Task 5's gotcha for why).

### Scope-boundary judgment calls — read before writing code

1. **No Coin-detail, no `Enter` key, in this story.** `/` and `m` are this story's only two new keybindings. `Enter` (drilling into Coin-detail) is Story 4.3's job entirely — the footer hint text this story writes must still not advertise it (see Task 3's footer-text subtask), extending Story 4.1's own "advertise only what works" discipline rather than relaxing it now that two more keys do work.
2. **Still no OFI/OBI/microprice/spread columns.** Re-checked against this story's actual AC text (all 5 ACs above, verbatim from `epics.md`): none of them mention indicator columns. Story 4.1's Dev Notes reasoning for why the mockup's extra columns are out of scope (a second live data source, `snapshots:raw` + `ml_signals.indicators`, that neither this story's ACs nor `EXPERIENCE.md`'s Coins-pane-list-row behavioral spec actually require) is unchanged and still governs — this story only adds filtering/mode-toggle/staleness on top of the same `{instrument_id, rank, volume24h, volatility_score}` fields Story 4.1 already renders.
3. **The stale badge is pane-level only — not per-row — even though the mockup shows individual rows tinted.** Detailed fully under Task 5 above; restated here because it's the single highest-risk "looks right in the mockup, wrong per the actual AC text" judgment call in this story. AC3's literal wording is unambiguous ("only a per-pane stale badge... every other row renders in the terminal's own inherited default") and the wire schema has no per-instrument staleness field to key row-level coloring off in the first place. Follow the AC text, not the illustrative mockup, per Story 4.1's own "mocks illustrate; spine/AC tables are the contract" precedent (drawn originally from `EXPERIENCE.md`'s Information Architecture section, which states this explicitly).
4. **`m` never locally flips a mode variable, even briefly.** Detailed fully under Task 4. The temptation is to re-render the list immediately with the assumed new mode for a snappier feel — resist it. `ranking_engine` is the sole computer/publisher of Coin Ranking (AD-9); a `bot_tui`-local guess about the active mode, even a well-founded one, is exactly the kind of "second computation surface" AD-9/AD-3 exist to prevent, and this UI-convenience corner is not worth the risk of ever showing something the shared engine didn't actually confirm (e.g. if the publish is dropped, or the toggle happens twice in quick succession and the two get reordered — `ranking_engine`'s own "last-write-wins on a near-simultaneous double-switch is acceptable" note in AD-9 already acknowledges this class of ambiguity exists at the engine level; a locally-optimistic `bot_tui` would compound it with a second, independently-wrong guess).
5. **Three now-distinct meanings of `esc`, all mutually exclusive, none of which ever exits the program.** Story 4.1 gave `esc` two meanings (cancel the open command bar; pop the view stack, no-op at root). This story adds a third (clear the open filter, without touching the view stack). Get the `_unhandled_input` branch ordering right — command-bar-active check first (unchanged), then filter-active check (new), then the general `:`/`/`/`m`/`esc`-pop-view fallback (unchanged, extended only with the new `/`/`m` branches) — so all three stay mutually exclusive. `:q` remains the only quit path; nothing in this story changes that invariant, and no test should ever need to check it does.
6. **`/` is Coins-pane-only, not global.** `EXPERIENCE.md`'s Interaction Primitives table states this explicitly ("the only pane FR-21 specifies filtering for"). Pressing `/` while on the Bots pane is a deliberate no-op, not an oversight — do not wire it to open a filter there (there is nothing there to filter yet, and Story 4.4 owns the Bots pane's own content and interactions).
7. **`_RANKING_STALE_SECONDS` is copied from `dashboard.py`'s already-shipped value, not re-derived independently.** Both `dashboard.py` and `bot_tui` are independent readers of the same `rankings:live` heartbeat; using the same threshold (15.0s = 3x `ranking_engine`'s 5s default) means both surfaces agree on what "stale" means for the same underlying signal, which is worth more than either surface picking its own number in isolation.

### Testing strategy: pure logic vs. urwid wiring (extends Story 4.1's split)

Story 4.1 established a hard split between pure, `urwid`-free functions (fully unit-tested) and the thin `urwid` wiring layer in `app.py` (verified by widget-construction-level tests where possible, manual smoke-check only where a real screen is genuinely required — e.g. `MainLoop`/`draw_screen()` itself). This story adds three new pure functions (`is_stale`, `filter_rows`, `toggle_mode`) that slot cleanly into the existing split and are fully unit-tested. It also adds two things that are **structurally** outside that split, same as Story 4.1's own async-redraw wiring was: `urwid.Edit`'s `"change"`-signal-driven live narrowing (needs actual keystroke-by-keystroke input events, not just a `_build_body()` call), and the redraw-loop's periodic staleness re-evaluation (needs actual wall-clock time to pass with a background task running). Both are covered by the Task 6 manual smoke check, not silently skipped — same discipline, not a new one.

### Precision rule (AD-5) — not applicable

Unchanged from Story 4.1: this story handles instrument-ID strings, mode-name strings, floats already computed by `ranking_engine`, and wall-clock timestamps for staleness comparison — no `Price`/`Quantity` construction or precision-sensitive arithmetic occurs anywhere in this story's scope.
