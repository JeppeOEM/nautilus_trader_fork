## Intent

**Problem:** Backtests on `.BYBIT`/`.HYPERLIQUID` instruments can only span the time the collectors have been alive, because the catalog holds nothing older than the first `DydxSecondSnapshot` those collectors wrote. Both venues serve their own historical 1-minute klines over REST that the pinned pyo3 bindings already expose, but nothing in `troll/` fetches them.

**Approach:** One offline operator CLI, `troll/collector_core/backfill_bars.py`, that walks a requested UTC range in bounded windows, calls `BybitHttpClient.request_bars` / `HyperliquidHttpClient.request_bars`, and writes the resulting Cython `Bar`s through `ParquetDataCatalog.write_data()`. It is report-only unless `--apply`, and it fetches only the catalog's *missing* intervals so re-runs write nothing.

## Boundaries & Constraints

**Always:** Write through `ParquetDataCatalog.write_data()` (NAUT-02) — never a hand-rolled Parquet schema. Derive the windows to fetch from the catalog's own interval API (`get_missing_intervals_for_request` / `get_intervals`), never from hand-parsed file names. Convert pyo3 bars with `Bar.from_pyo3_list` (`nautilus_trader/model/data.pyx:1997`) — never rebuild a bar from floats (NAUT-01/AD-5). Keep both venues on the **same** timestamp convention: bar `ts_event`/`ts_init` = bar **close** time. Pace venue calls with `await asyncio.sleep(0.2)` between requests and say in a comment which published limit that stays under. Type-hint every signature (`mypy --disallow-incomplete-defs`); `X | None`, absolute one-per-line imports, LGPL header, `ruff format` at line length 100.

**Block If:** The only remaining way to make re-runs idempotent would be to pass `skip_disjoint_check=True` or to delete/overwrite existing catalog files — that is data loss (DATA-05), not idempotency.

**Never:** Touch `nautilus_trader/` or `crates/` (FORK rule) — the Hyperliquid adapter's own `Price::new(f64, …)` kline parsing and its `limit`-truncates-the-oldest semantics are worked around from the Python side, not fixed upstream. Never import `bybit_collector`/`hyperliquid_collector` from `collector_core` (that inverts the dependency) — call `nautilus_pyo3` directly. Never touch the collectors, `ml_signals`, `candles_<venue>.db`, the chart, compose files or the Dockerfile. Never write a bar into the derived candle store.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Report-only default | `--instrument BTCUSDT-LINEAR.BYBIT --start 2026-09-01 --end 2026-09-03` (no `--apply`) | Logs each window it *would* fetch and each range already covered; writes nothing | No error expected |
| Fresh apply | Above `+ --apply`, catalog has no bars for that `BarType` | One `write_data()` call per fetch window; logs rows written per window | No error expected |
| Full re-run | Same command again | Zero windows to fetch, zero `write_data()` calls, "already covered" logged | No error expected |
| Partial overlap | Catalog covers day 2 of a 3-day request | Only the day-1 and day-3 gaps are fetched; written files stay disjoint | No error expected |
| Duplicate/out-of-range bars from venue | Venue returns bars outside the window or repeats a timestamp | Bars filtered to the window and deduped by `ts_init`, kept sorted, so no `ts_event` appears twice | No error expected |
| Hyperliquid older than retention | `--start` earlier than the last 5000 candles | Fetches what exists; logs a WARNING naming the earliest timestamp the venue actually returned and how many bars are missing at the front | Loud, never silent |
| Instrument absent from catalog | No `Instrument` written for the id | Exits non-zero before any fetch, telling the operator to run that venue's collector once | `SystemExit` with the message |
| Unsupported venue | `--instrument BTC-USD-PERP.DYDX` | Exits non-zero: dYdX bars come from its own 1 s archive | `SystemExit` with the message |
| Bad range | `--end` before `--start` | Rejected up front by `_windows` | `ValueError` |

A close-stamped bar belongs to the day it *opened* in, so for `--start D1 --end D2`: `start_ns = midnight(D1) + bar_ns`, `end_ns = midnight(D2) + _DAY_NS`. Using `midnight(D1)` and `midnight(D2) + _DAY_NS - 1` (the obvious reading) silently drops D2's `23:59` bar and pulls in D1−1's — verified, do not reintroduce. ## Spec Change Log

### 2026-09-20 — bad_spec loopback (review pass 2)

**Triggering findings.** Three defects, all traceable to instructions in the pass-1 amendment. (1) This spec told the implementation to `catalog.write_data(bars)` once per window; because `_write_chunk` names a file `[first.ts_init, last.ts_init]`, a window served with an **interior hole** is sealed as fully covered — the gap can never be re-planned or even found, and the only trace is a log line. That is precisely the DATA-05 loss the canary was added to report, and both the module docstring and the new D-53 row claimed the opposite. (2) This spec said the Hyperliquid retention short-circuit should fire when a window came back "empty **or short at the front**"; a single no-trade minute at a window's front boundary — ordinary for an illiquid perp — therefore abandons every older window permanently and reports a confident, wrong "below the venue's retention floor". (3) This spec's Design Notes asserted that "Bybit klines parse through `parse_price_with_precision` (string-based)" and so carry a guarantee Hyperliquid's f64 parse does not. **Verified false in this session:** `crates/adapters/bybit/src/common/parse.rs:1187-1198` is `value.parse::<f64>()` + `Price::new_checked(parsed, precision)` — the same f64 round-trip, differing only in range validation. That false claim had been written into `DATA_INTEGRITY_AUDIT.md` as a `DOCUMENTED` row, where a later reader would have over-trusted Bybit backfill for D-51's kline reconciliation.

**What was amended (all outside `<intent-contract>`).** The write path now writes **each contiguous run of bar closes as its own `write_data()` call**, so a hole stays a hole. The retention short-circuit fires only on a **fully empty** window and is logged as a heuristic observation, not a proven floor. Every document must now state that **both** venues are f64-round-tripped and claim no asymmetry. Folded in at the same time: a per-venue `(aggregation, step)` support table replacing the shape-only spec check — the epoch is a **Thursday**, so `1-WEEK` and `3-DAY` snap to a grid neither venue uses and would discard 100% of what they fetch; a precision check of each fetched bar against the catalog's own instrument definition before writing; per-instrument error isolation with the summary emitted from a `finally`; a delisted instrument skipped rather than aborting the batch; honest `--environment` wording (it picks the endpoint, it does **not** verify the catalog's environment); and mandatory tests of the fetch-and-write path through an injected fake fetcher.

**Known-bad state avoided.** An archive tool that silently seals data holes it has just warned about, that abandons a venue's entire older history on one quiet minute while blaming retention, and an integrity register carrying a verified-false precision claim.

## Design Notes

**The window domain must be bar-aligned — this is the invariant the whole design rests on.** The catalog's coverage is only ever known at bar granularity: `_write_chunk` (`parquet.py:368-370`) names each file `[first.ts_init, last.ts_init]`, i.e. the first and last *bar close* it holds. So a window that ends at a sub-bar boundary can never be fully covered by the data it produced, and `get_missing_intervals_for_request` will hand that sliver back forever:

```python
# window  [00:00:00, 16:39:59.999999999]  ->  file [00:00:00, 16:39:00]
# re-run: missing = [16:39:00.000000001, 16:39:59.999999999]   <- a fetch that can never be satisfied
```

Keeping every bound a multiple of `bar_ns` — the requested range, each gap after snapping, and each window — makes a completed window's file interval equal its window exactly, so the second run's diff is empty. `_bar_count` becomes exact for the same reason, which matters because it is both the operator-facing count and Bybit's `limit` argument.

**Why the catalog's missing-interval API rather than a covered/uncovered check per window.** `_write_chunk` (`parquet.py:377-384`) rejects any write whose `(min ts_init, max ts_init)` overlaps an existing file's interval, and the only escape hatches are `skip_disjoint_check=True` or deleting files — both forbidden here. Fetching strictly inside the snapped gaps makes the check structurally unreachable instead of suppressed.

**Timestamp domains.** Everything the script reasons about (windows, catalog intervals, dedup keys) is in **close-time** nanoseconds, matching what lands in `ts_init`. Only the two venue calls use open time:

```python
# Both venues' REST range params match the kline's OPEN time; our windows are close times.
bars = await http.request_bars(..., start=_dt(w_start - bar_ns), end=_dt(w_end - bar_ns), ...)
```

A close-stamped bar belongs to the day it **opened** in, which is why the day range is `midnight(D1) + bar_ns .. midnight(D2) + _DAY_NS` rather than the obvious `midnight(D1) .. midnight(D2) + _DAY_NS - 1`.

**Pacing.** Per-venue rather than a flat 0.2 s: Hyperliquid meters its info endpoint by aggregate request *weight* per IP per minute and `candleSnapshot` is one of the expensive ones, so 5 req/s could not honestly be described as far under its limit. Both constants come from the venues' published documentation and are **not** wire-verified in this environment — say so in the comment rather than implying a measurement (DATA-02).

**Hyperliquid re-stamp is exact.** The new `Bar` reuses the decoded `Price`/`Quantity` objects verbatim — no `Decimal`, no `float`, no precision change — so NAUT-01's `Price(decimal, precision)` trap is never touched. The adapter's own `Price::new(f64, precision)` kline parsing (`crates/adapters/hyperliquid/src/data.rs:1278`) is pre-existing upstream behaviour inside the fork boundary: record it as a `Known limit:` with the upstream fix as its upgrade path, and do **not** work around it by re-deriving prices in Python — that is precisely the precision laundering NAUT-01 forbids. **Correction (review pass 2, verified):** an earlier revision of this section claimed Bybit klines parse through a *string-based* `parse_price_with_precision` and so carry a guarantee Hyperliquid's does not. That is false. `crates/adapters/bybit/src/common/parse.rs:1187-1198` is `value.parse::<f64>()` followed by `Price::new_checked(parsed, precision)` — the same `f64` round-trip, differing only in range validation. **Both** venues' backfilled klines are f64-round-tripped upstream; no document may claim an asymmetry, because a reader would then over-trust Bybit backfill in D-51's kline reconciliation.

**Holes must stay holes.** `_write_chunk` names each Parquet file `[first.ts_init, last.ts_init]`, so writing a window that contains an interior gap as one batch produces a file whose interval spans the gap — and `get_missing_intervals_for_request` will then report the range as fully covered forever. Write each contiguous run of bar closes separately, so an un-servable minute stays a visible, re-plannable interval. The same reasoning is why an empty "covered" marker must never be written for a range the venue cannot serve.
