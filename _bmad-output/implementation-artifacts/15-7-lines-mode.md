# Story 15.7: Lines mode

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the dashboard operator,
I want to switch a coin's chart from candlesticks to a direct line comparison of bid/ask/mid/microprice/price,
so that I can read raw price-series behavior the way I do today, without losing my place in time when I switch.

## Acceptance Criteria

1. **`dashboard.py`'s existing Candles/Lines toggle is carried forward on the chart page.** This is `_render_chart_page`'s `#btn-candles`/`#btn-lines` pair (`ml_signals/dashboard.py:1330-1336`) — a two-button mode switch, not a checkbox/dropdown.
2. **`GET /api/snapshots/{instrument_id}` accepts `before_ns` + `limit` and returns `{"items": [...], "has_more": bool}` under the identical cursor-paginated contract as `/api/candles`** (spine AD-F3 explicitly binds `/api/snapshots` by name, not just `/api/candles` — an earlier spine draft naming only `/api/candles` was itself flagged as a bug). `data_api/routes/snapshots.py` is a new file, per the architecture spine's Structural Seed.
3. **Switching from Candles to Lines mode (or back) preserves the currently-viewed time range — it is never reset to a default window** (FR-43).
4. **A gap in the underlying snapshot data renders with the same AD-F6 gap-marker discipline as Story 15.3's candles** — never an interpolated flat line.
5. **Tests:** the same boundary/pagination test pattern Story 15.3 applied to `/api/candles` is applied to `/api/snapshots` (TEST-01, mirrors Story 15.3's coverage).

## Tasks / Subtasks

- [ ] Task 1 — `data_api/routes/snapshots.py` (new): cursor-paginated Lines-mode history route (AC: #2, #4)
  - [ ] Define `SnapshotSeriesPoint(t: int, bid: float | None, ask: float | None, mid: float | None, micro: float | None, price: float | None)` and `SnapshotSeriesResponse(items: list[SnapshotSeriesPoint], has_more: bool)` as Pydantic models (AD-F5 — frontend TS type generated from these). **`t` is milliseconds, matching `/api/candles`'s `CandleItem.t` exactly** (inherited from `candle_dicts_from_snapshots`'s existing `ts_open // 1_000_000` behavior, `ml_signals/candles.py:126` — confirmed by reading the function) — despite the spine's general "nanoseconds everywhere on the wire" convention, `/api/candles`'s response items are already ms in Story 15.3's shipped contract; `/api/snapshots` must match that unit exactly so both series land on the same chart time axis without a frontend-side unit mismatch. This is a pre-existing exception this story inherits, not a new deviation — do not "fix" it to ns in either route as part of this story (out of scope, and would break AC #2's "identical contract" requirement against whatever 15.3 actually shipped). The **request** cursor stays `before_ns` (nanoseconds, per its own name and AD-F3) — only the **response item timestamp field** is ms; confirm this dual-unit shape is what `/api/candles` actually does before writing this route, don't assume from this file alone.
  - [ ] `GET /api/snapshots/{instrument_id}?before_ns=<int>&limit=<int>` — no `bar_seconds` param (snapshots are per-second rows, no aggregation/bar concept). Own module-level `CATALOG_PATH` constant (same non-circular-import pattern `candles.py`/`redis_bus.py`/`indicator_series.py` established — **do not import `data_api.app`'s `CATALOG_PATH`**, that would be circular). Clamp the requested `limit` to a server-enforced `_MAX_SNAPSHOTS_LIMIT` module constant before anything else (MEM-01/AD-F3) — pick a value bounding response size the same way `_MAX_CANDLES_LIMIT` does, sized in rows-per-second terms (much larger than a candle limit since there's no bar aggregation); document the reasoning in a comment, exact number is implementation-owned.
  - [ ] Query the bounded window via `catalog_stats.query_second_snapshots(CATALOG_PATH, instrument_id, start_ns, before_ns)`, where `start_ns = before_ns - limit * 1_000_000_000 * <safety multiplier, e.g. 2>` (rows are ~1/second, unlike candles' `bar_seconds`-scaled window) — never an unbounded `start_ns=0` scan.
  - [ ] **Port `_price_series_rows` (`ml_signals/dashboard.py:1460-1508`) into this file as a private helper, verbatim relocation per AD-F1 — do not import it from `ml_signals.dashboard`.** `dashboard.py` is scheduled for deletion in Story 15.10 (same reasoning Story 15.6's Dev Notes already documented for `_merged_indicator_catalog()`); importing from it here would create a real runtime dependency the cutover can't safely remove. The ported copy keeps its existing behavior unchanged: build each row from a 7-key snapshot dict (`bid_prices`, `bid_sizes`, `ask_prices`, `ask_sizes`, `buy_volume`, `sell_volume`, `ts_event`) — build these dicts inline from the queried `DydxSecondSnapshot` objects the same way `dashboard.py`'s own `_historical_lines_json` does (`ml_signals/dashboard.py:1570-1588`), not by importing `app.py`'s private `_snapshot_to_dict` (cross-route-module private import, avoid). Keep unchanged: the crossed/touched-book skip (`bp >= ap` → drop the row, stale reconnect data), the CVD-weighted `price` formula, and the microprice/mid calculation (calls `ml_signals.indicators.microprice` directly — a real `ml_signals` module, safe to import normally, not a relocation case).
  - [ ] **Gap-marker detection needs no new logic — it's already inside the ported function.** Unlike Story 15.3's `candles.py` (which had to add new bar-boundary-spacing gap detection on top of `candle_dicts_from_snapshots`, which had none), `_price_series_rows` already inserts a null-valued gap row whenever consecutive valid snapshots are more than `_CHART_GAP_THRESHOLD_MS` (2500ms) apart (`ml_signals/dashboard.py:1483-1494`) — port this threshold as this file's own module constant (e.g. `_SNAPSHOT_GAP_THRESHOLD_MS = 2500`, matching `dashboard.py`'s exact value) and reuse the existing per-row logic unchanged. This satisfies AC #4 with no additional post-processing step.
  - [ ] Keep only rows with `t < before_ns // 1_000_000` (converting the ns cursor to the row's ms unit), take the most recent `limit` of them (after crossed-row filtering, so `limit` counts real rows, not skipped ones).
  - [ ] `has_more`: reuse the exact one-more-bounded-probe-query approach `candles.py` established in Story 15.3 (probe the equally-bounded window immediately preceding the page's earliest kept row; `has_more = True` iff that probe returns any snapshot) — do not invent a second design for the same already-solved problem (same reuse discipline Story 15.4's `indicator_series.py` already followed).
  - [ ] Register the router in `app.py` **above** the `/api/{full_path:path}` catch-all (same required ordering as every prior story's route registration).

- [ ] Task 2 — Frontend: generalize the scroll-back trigger so it is mode-aware (AC: #2, #3)
  - [ ] **Read this before touching `useCandles.ts`.** Per Story 15.4's own Dev Notes, the `subscribeVisibleLogicalRangeChange` scroll-back trigger is wired *inside* `useCandles.ts` (Story 15.3), and Story 15.4's `useIndicatorSeries` piggybacks on that same callback to co-page. This story adds a **third**, mutually-exclusive data source for the main pane (snapshot rows instead of candles) that must fire on the identical trigger when Lines mode is active — but `useCandles` should not be fetching at all while Lines mode is showing (wasted requests against a hook whose output isn't being rendered). Before writing this story's own hook, verify how Stories 15.3/15.4 actually implemented the trigger (don't assume from this file alone) and, if it is still owned inside `useCandles` as scoped, lift it to the chart-owning component (`ChartPage.tsx`/`LightweightChart.tsx` — the one component AD-F4 already designates as owning chart lifecycle) so it is a single mode-agnostic "near-edge" callback that dispatches to whichever hook(s) are currently active (indicator panes always; `useCandles` in Candles mode; this story's hook in Lines mode). This is a natural extension of AD-F4's existing "one component owns chart lifecycle" principle, not a new architectural rule — do not build a second, parallel trigger mechanism.
  - [ ] `frontend/src/hooks/useSnapshotSeries.ts` (new, filename implementation-owned): mirrors `useCandles.ts`'s cursor-pagination shape (React Query, keyed by `instrument_id`, calling `GET /api/snapshots/{iid}`) but is only enabled while Lines mode is active (`enabled: mode === 'lines'` — React Query's own gating, not a manual `if`). Initial page size: since snapshot rows have no bar-count concept, size the default `limit` to approximate `dashboard.py`'s existing Lines-mode chunk width (`_chunkSpanMs`'s 15-minute/900-row default for lines, `ml_signals/dashboard.py`'s `_LIVE_CHART_JS`) rather than reusing candles' bar-count constants (120/20), which don't apply here.
  - [ ] Feed gap-marker items (`bid`/`ask`/`mid`/`micro`/`price` all `null`) straight through as `lightweight-charts` whitespace data on each line series, same discipline as `useCandles`'/`useIndicatorSeries`' gap markers (Stories 15.3/15.4).

  - [ ] Add toggle buttons to `ChartPage.tsx`'s toolbar mirroring `dashboard.py`'s `#btn-candles`/`#btn-lines` (`ml_signals/dashboard.py:1330-1336`) — final terminal/ANSI styling is Story 15.9's job, this story only needs the two-state toggle to exist and work.
  - [ ] **The core mechanic, read carefully — this is the one thing that actually satisfies AC #3:** on mode switch, do NOT call `chart.timeScale().setVisibleLogicalRange(...)` or `fitContent()` — the visible time range is a property of the chart's time scale, not of any one series, so simply removing the old mode's main-pane series (candlestick) and adding the new mode's series (5 line series: bid/ask/mid/micro/price) on the *same* `IPaneApi`/main pane, then calling `setData()` on the new series, leaves the current view untouched by construction. This is the exact same "never touch the timescale on an add/remove" discipline Story 15.4's Task 2 already established for indicator-pane add/remove (AC #4 there) — reused here for a main-pane series swap instead of a sub-pane add/remove, not a new mechanism.
  - [ ] Before fetching data for the newly active mode, read the chart's current visible range (`chart.timeScale().getVisibleRange()`) and use its right edge (or "now" if the view is at the live edge) as the initial `before_ns` anchor, with a `limit` sized to cover that same visible span — this is what makes the newly-shown series actually cover the range the operator was already looking at, rather than a fresh default window that merely doesn't reset the axis labels. Mirrors `dashboard.py`'s own `setCoinMode` (`ml_signals/dashboard.py:210-215`), which deliberately keeps `_coinHistStart`/`_coinHistEnd` unchanged across a mode switch and just re-fetches the same date range under the new mode.
  - [ ] Indicator sub-panes (Story 15.4: OFI/OBI/microprice/spread/volume) are unaffected by this toggle — `dashboard.py`'s own mode switch only ever touched its single price pane (`#live-chart`), never its separate micro-panel; this story does not add, remove, or reconfigure any indicator pane.

- **Sequencing dependency, stated plainly: this story cannot start until Stories 15.3 and 15.4 are actually implemented, not just spec'd.** As of this story's creation, only Stories 15.1 and 15.2 have landed (confirmed by direct inspection: `data_api/routes/` contains only `rankings.py`; no `candles.py`, `indicator_series.py`, `indicators.py`, or `snapshots.py` exist yet; `frontend/src/pages/ChartPage.tsx` is still the Story-15.1-era placeholder — `"Chart — not yet implemented (Stories 15.3-15.7)."`; `lightweight-charts` is not yet in `frontend/package.json`). Sprint-status.yaml shows 15.3/15.4/15.5/15.6 all `ready-for-dev` (spec'd, not built) as of this story's creation. Task 1 (backend route) has no dependency on 15.3/15.4 landing and can be built/tested independently; Tasks 2-3 (frontend) assume `LightweightChart.tsx`'s single `createChart()` instance, `useCandles.ts`'s cursor pagination + scroll-back trigger (15.3), and the keyed pane registry (15.4) already exist — verify their actual shape before starting, don't assume from this file alone.
- **This is explicitly called out as depending on Story 15.3 in the architecture spine's own Cross-Story Dependencies:** "Story 15.7 (Lines mode) reuses 15.3's exact cursor-pagination contract on a new route (`/api/snapshots`)." Get AC #2's envelope shape and AC #3's view-preservation mechanism right — this is the last story to touch the chart page's main pane before Story 15.9 (visual identity) and Story 15.10 (cutover), so a wrong turn here is visible in the final product, not caught by a later story.
- **Why Lines mode only swaps the main pane, never touches sub-panes:** confirmed by reading `dashboard.py`'s existing `setCoinMode`/`_LIVE_CHART_JS` — the Candles/Lines toggle has only ever driven `#live-chart` (the single price pane); the separate micro-panel (imbalance/depth/spread, now Story 15.4's OFI/OBI/microprice/spread/volume panes) is untouched by a mode switch today. Do not couple this story's toggle to indicator-pane lifecycle — that would be new, unrequested scope (DESIGN-01/YAGNI).
- **The ms-vs-ns timestamp unit for `SnapshotSeriesPoint.t` is not a judgment call — it must match whatever `/api/candles`'s `CandleItem.t` actually is.** `candle_dicts_from_snapshots` (`ml_signals/candles.py:126`) emits `t: c.ts_open // 1_000_000` — milliseconds, not nanoseconds — despite the architecture spine's Consistency Conventions table stating "Nanosecond UNIX ints everywhere on the wire... never ms." This is a pre-existing inconsistency already baked into Story 15.3's shipped contract (its `CandleItem.t` type has no unit annotation, but the underlying function it calls unchanged is ms), not something this story introduces or should "fix" — AC #2's literal requirement ("identical cursor-paginated contract as `/api/candles`") is only true in practice if both routes' response item timestamps share the same unit, so both series land on the same chart time axis without a silent unit-mismatch bug. Confirm `/api/candles`'s actual shipped `t` unit by reading its code once Story 15.3 lands, rather than trusting this file's description of the spine's stated (but not fully honored) convention.
- **Reuse discipline — three things this story must NOT reinvent:** (1) `has_more`'s one-more-bounded-probe-query design (`candles.py`, Story 15.3) — no second design for the same already-solved problem, same reuse Story 15.4's `indicator_series.py` already applied; (2) the gap-marker threshold logic — it already lives inside `_price_series_rows`, being ported verbatim, so this story needs zero new gap-detection code (unlike Story 15.3, which had to add bar-boundary gap detection from scratch); (3) the CVD-weighted price/microprice math itself — `ml_signals.dashboard`'s own docstring states outright "the math must never be reimplemented a second time (SSOT-03)," which is exactly why Task 1 ports the existing function rather than rewriting it.
- **Do not import from `ml_signals.dashboard` at runtime.** `dashboard.py` is scheduled for deletion in Story 15.10 (AD-F1) — importing `_price_series_rows()` from it in `data_api` would create a real dependency the cutover can't safely remove. Port the function's logic into `routes/snapshots.py` instead (Task 1) — this is "verbatim relocation of business logic" per AD-F1, the same treatment Story 15.6 gave `_merged_indicator_catalog()`. The one sanctioned exception is Task 5's test-only oracle import, used purely to prove byte-identical output — never a runtime import.
- **The scroll-back trigger's ownership (Task 2) is the trickiest part of this story and is a real, not-fully-specified design point** — the architecture spine fixes the pagination *contract* (AD-F3) and the pane-ownership *principle* (AD-F4: "no child component may create or destroy a pane directly," "one component owns chart lifecycle") but does not itself dictate exactly how three mutually-exclusive/co-existing data sources (candles, snapshot-lines, indicator-series) should share one scroll-back callback. Task 2's "lift it to the chart-owning component" approach is this story's own reasonable extension of AD-F4's existing principle, not a mandate from a source document — flag any deviation from it in Completion Notes rather than silently doing something else.
- **`troll/CLAUDE.md` constraints that apply:** FORK-01/02 (nothing under `nautilus_trader/`/`crates/` touched); MEM-01 (bounded reads + `_MAX_SNAPSHOTS_LIMIT` clamp, Task 1); DATA-01/AD-F6 (gap markers ported unchanged, crossed-book rows still silently skipped — both pre-existing correctness behaviors, not new); SSOT-01 (`ml_signals.indicators.microprice` called unchanged, never reimplemented); SSOT-03 (the CVD-weighted price/microprice math ported once, proven byte-identical via Task 5's oracle test, never a second implementation); DESIGN-01/YAGNI (toggle does not touch indicator-pane lifecycle; no config UI); TEST-01/03 (real `DydxSecondSnapshot`/catalog objects in every test, never hand-typed dict mocks); minimize-dependencies preference (no new library — reuses `lightweight-charts` 5.2.1 already added by Story 15.3).
