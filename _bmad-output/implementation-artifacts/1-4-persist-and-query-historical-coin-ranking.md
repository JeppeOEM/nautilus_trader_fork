# Story 1.4: Persist and query historical coin ranking

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a researcher,
I want to see how a coin's ranking evolved over time,
so that I can decide whether it warrants opt-in Raw Delta Capture (FR-2).

## Acceptance Criteria

1. **Rank is persisted per cycle, not just overwritten (FR-8).** Given ranking is computed on an ongoing basis, when a ranking cycle completes, then the rank (and its contributing volume/indicator values) for each coin at that point in time is persisted, not just overwritten as the latest snapshot.
2. **Historical query by timestamp.** Given a past timestamp within the collector's retention window, when the user queries ranking history for a specific coin, then the historical rank/value at (or nearest to) that timestamp is returned.
3. **Bounded growth (NFR3).** Given the historical ranking store, when it accumulates data over time, then it does not grow unbounded — retention follows the same bounded/rolling-window discipline as other in-memory/catalog data, or is itself a bounded, prunable store.
4. **Delisted coins keep their history.** Given a coin not currently in the live Watchlist, when its past ranking history is queried, then historical data for it is still retrievable if it was previously ranked within the retention window — ranking history is not deleted merely because a coin drops out of the current Watchlist.

## Dev Notes

**This is a SQLite-store extension, not a new persistence mechanism — do not reach for Redis, the Parquet catalog, or a new file format.** `ml_signals/metrics_store.py` already implements exactly what AC #1-#4 ask for: a per-`(ts, instrument_id)` SQLite table, written every `DB_WRITE_INTERVAL_SECONDS` (60s) by `_slow_loop_task`, pruned to a bounded retention window (`retain_days=31`) on every write, queryable by instrument (`history()`) or most-recent (`latest()`). This story adds two columns (`rank`, `volume24h`) and one new query shape (`nearest()`); it does not invent new infrastructure.

**Why not the Parquet catalog:** `metrics.db` is not `ParquetDataCatalog` — it's always been a separate, dashboard-owned SQLite side-store (see `_slow_loop_task`'s existing, pre-this-story call to `metrics_store.write`). The Gatekeeper architecture rule (AD-1/AD-3: `dydx_collector/collector.py` is the only writer to the catalog/Redis, readers trust the gate) governs the *catalog*, not this store — `dashboard.py` has always owned `metrics.db` directly. This story does not touch `collector.py`, the catalog, or Redis at all.

**Why "a ranking cycle" = `_slow_loop_task`'s existing 60s tick, not a new loop:** The live rankings table (`_rankings_json()`/`_watchlist_ids()`, Stories 1.2/1.3) is computed fresh on every HTTP request from `_LIVE_FAST`/`_VOLUME_24H` — there is no discrete "cycle" there to hook into, and persisting on every 1s Redis ingest (`_ingest_batch`) would write far too many rows for a 31-day retention window across every instrument. `_slow_loop_task` already runs on a bounded, periodic cadence and already persists a snapshot per instrument every cycle — reusing it means "persist rank" costs one dict merge per cycle, not a new timer, a new write path, or a new pruning story.

**Existing gotcha found while reading `metrics_store.py` before writing tasks:** `_SCHEMA` uses `CREATE TABLE IF NOT EXISTS`, which does nothing if `snapshots` already exists — meaning simply adding to `COLS` breaks any already-deployed `metrics.db` with an `OperationalError: no such column`. Task 1 fixes this generally (a `PRAGMA table_info` + `ALTER TABLE ADD COLUMN` migration), not just for this story's two new columns, since the module's own docstring already invites future column additions and this bug would otherwise resurface every time.

**Why `rank`/`volume24h` are computed in `dashboard.py`, not `metrics_computer.py`:** `metrics_computer.compute_all()` is purely catalog-driven (reads `ParquetDataCatalog` order book deltas/trades for OFI/microprice/price-stats) — it has no access to live Redis-fed state (`_LIVE_FAST`, `_VOLUME_24H`). Rank is inherently live-ranking state, not a catalog-derived metric, so it's merged into the snapshot list inside `dashboard.py`'s `_slow_loop_task`, after `compute_all()` returns, keeping `metrics_computer.py` unchanged and the module boundary clean (AD-4).

**The `/history/{id}` page already exists and needs zero new handler code for the visual "how did ranking evolve" view.** `_render_history_page` (pre-existing, unrelated to this story) already iterates `RANKING_COLS` generically and plots whatever fields are present as non-`None` in `metrics_store.history()`'s rows. Adding `"rank"`/`"volume24h"` to `RANKING_COLS` is sufficient — do not build a new page or chart for this.

**Explicit non-goal:** adding a live "current rank" column to the rankings table UI. `RANKING_COLS` is shared with `_rankings_json()` (live table cell rendering, sourced from `_LIVE_FAST`/`_merged_live`, which has no `rank` key) — adding `"rank"` there would either render permanently empty or (worse) leak a stale, once-per-60s value if `_LIVE_SLOW` ever carried one. Implementation used a separate `_HISTORY_ONLY_COLS` list, read only by `_render_history_page`, instead of extending `RANKING_COLS` — see Task 2/4's notes. Adding a "Rank" column to the live table is not required by any AC and is scope creep — the live table's row order already shows rank.

**Precision rule (AD-5) — not applicable.** This story only threads plain floats/ints (rank position, volume) and SQLite storage; it constructs no `Price`/`Quantity`.

**Architecture paradigm (must not violate):** this story adds no new writer to the catalog and no new invariant-checking logic (AD-1, AD-2, AD-3 untouched — `metrics.db` is dashboard-owned, always has been). Confined entirely to `ml_signals/`; `dydx_collector/` is not touched.
