# Story 4.3: Coin-detail drill-down with collapsible order-book depth

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the builder,
I want to drill into a coin's live indicators and order book, with the book collapsed by default and expandable on demand,
so that I can check a coin's health at a glance without a wall of price levels, and go deep only when I actually need to.

## Acceptance Criteria

1. **Enter opens Coin-detail full-screen with live indicators via `ml_signals.indicators`.** Given a highlighted row in the Coins pane, when the builder presses `Enter`, then Coin-detail opens as a full-screen replace (not a split-pane, not a modal), showing live indicators (Microprice, spread, OFI, OBI) computed via the shared `ml_signals.indicators` code path — never reimplemented locally (FR20, UX-DR5).
2. **Order book opens collapsed to top-of-book every time.** Given Coin-detail's order-book region, when the view is entered, then it opens collapsed to a single top-of-book row (best bid/ask) every time — it never remembers an expanded state from a prior visit (FR20, UX-DR5).
3. **`d` toggles the full depth ladder, scoped to the ladder region only.** Given the collapsed order-book region, when the builder presses `d`, then it expands to the full depth ladder (up to 20 levels/side, bid left / ask right); `d` again re-collapses it — this toggle is scoped entirely to the ladder region and does not affect the breadcrumb, indicators, or what `esc` does (FR20, UX-DR5).
4. **Thin books end short; a zero-level side renders `no bids`/`no asks`.** Given an expanded ladder on a thin book (fewer than 20 levels on one or both sides), when it renders, then the ladder simply ends short — no padding rows, no placeholder glyphs, no error styling; a side with zero levels renders `no bids`/`no asks` (FR20, UX-DR5).
5. **`o` opens the web dashboard to this coin's graph view.** Given Coin-detail is open, when the builder presses `o`, then the web dashboard opens in the browser to this exact coin's graph view at the same time-window/zoom context — not a generic landing page (FR25).
6. **`esc` returns to Coins pane, preserving scroll position and active filter.** Given Coin-detail, when the builder presses `esc`, then it returns to the Coins pane, preserving scroll position and any active filter, regardless of whether the order-book ladder was collapsed or expanded at the time (FR20).
7. **No time-scrubbing or historical replay anywhere in this view.** Given Coin-detail's indicators and order-book ladder, when either is displayed, at any expansion state, then no time-scrubbing or historical replay control exists anywhere in this view — both always show current/latest market-data state only; historical/graph analysis for market data stays the web dashboard's job via the `o` deep-link above (FR24).

This story's `_redis_listener` therefore receives the **full** multi-instrument batch continuously for the whole app session (started once in `BotTuiApp.run()`, same lifetime as `ranking_state`'s listener), and `_handle_snapshot_batch` discards every row except the one matching `_CURRENT_INSTRUMENT_ID` — typically ~19 of ~20 rows in a full watchlist-sized batch, and *all* of them whenever no coin is open at all. ## Dev Notes

**This story is the largest yet in `bot_tui` — a whole new full-screen view, not an extension of an existing pane's behavior (unlike Story 4.2).** It touches every existing production file (`ranking_state.py` is untouched, but `coins_pane.py`'s rows are now wrapped differently in `app.py`, and `app.py` itself grows substantially) and adds two new ones. The engineering risk is concentrated in three places, each with its own verified finding above: (1) Coins-pane rows were never selectable before this story — verified directly against the installed `urwid==4.0.6` that focus genuinely cannot move without this fix, not merely inferred from documentation; (2) the Coins-pane body has always been rebuilt from scratch on every view switch, which AC6 is the first requirement to actually expose as a problem; (3) AC5's "browser" requirement runs headfirst into a real, verified headless-container constraint that this story resolves explicitly rather than assuming away.

### Judgment calls and scope-boundary decisions — read before writing code

1. **`o`'s browser-open mechanism: attempt `webbrowser.open()`, always also show the URL as footer text — never conditional on the attempt's success.** Verified via `troll/docker-compose.yml`'s `bot_tui` service block (lines ~104-131): `network_mode: host`, no `DISPLAY`/X11 passthrough of any kind — there is no browser reachable from inside the container, ever. But `ARCHITECTURE-SPINE.md`'s Deployment & Environments section explicitly describes a second, real deployment shape: "launched directly over SSH... **or run on the host against the same Redis instance**" — i.e. an on-host, non-Docker execution path genuinely exists where `webbrowser.open()` *would* reach a real desktop browser. Since both shapes are real and this story cannot know at runtime which one it's running under (short of an unreliable, over-engineered environment-sniffing check that isn't worth building), the only honest behavior is: attempt the open (free, harmless, occasionally actually useful), and unconditionally *also* render the exact URL as visible text so the on-Docker/SSH case (almost certainly the common one) always has a real, usable affordance — copy the URL, open it in whatever browser is on the builder's own machine. This mirrors Story 4.4's own explicitly-specified `s` (start/stop) footer-echo idiom ("confirms the command was sent, not that it succeeded") applied to a dispatch-and-display action instead of a dispatch-and-wait one — the same underlying pattern (show what happened, don't guess at what the environment did with it), reused rather than invented fresh for this story.
2. **AC5 vs. AC7 tension on "same time-window/zoom context," resolved by omitting query params entirely.** `dashboard.py`'s `chart_handler` genuinely supports `?start=<iso>&end=<iso>` (confirmed by reading `dashboard.py:1205-1223` directly), so AC5's wording is not unimplementable in principle — but AC7 forbids Coin-detail from ever tracking a time-window value of its own, meaning there is, by design, nothing for this story's code to read *out* to put into those query params. The chosen resolution — build the deep-link URL with no `start`/`end` params, deferring entirely to `chart_handler`'s own sensible default (trailing 4 hours) — is the closest honest interpretation of "same... context" available to a view that has no time-window state at all: it's what "current" looks like from a view that only ever shows current state. A fabricated or guessed window would misrepresent a precision this view was never built to have.
3. **`esc`-preserves-Coins-pane-state landmine, fixed structurally, not with a special case.** Verified directly: every `_switch_view` call to date (Stories 4.1/4.2) unconditionally rebuilds the Coins pane's `ListBox` from scratch via `_build_body()`, discarding scroll/focus position every time — invisible until now because nothing previously needed to survive a round-trip through a different view. The fix (Task 6) makes the Coins-pane body widget a **persistent object** that is only ever mutated in place when its own underlying data changes (new ranking, filter change), never rebuilt merely because the active view changed — this single structural change satisfies both halves of AC6 (scroll position *and* active filter both survive automatically, since neither is touched by entering/leaving Coin-detail) with no separate "remember these two things across the round-trip" bookkeeping needed. It also incidentally fixes a related, previously-undetected scroll-reset-on-every-`rankings:live`-heartbeat issue in the existing redraw loop, as a direct side effect of the same change — noted explicitly as a welcome consequence, not scope creep pursued on its own.
4. **No content from this story bleeds into Story 4.4's Bots-pane scope.** Confirmed by re-reading Story 4.4's own AC text (`epics.md` lines ~647-664, immediately following this story's): Story 4.4 owns the Bots pane's own list rows (`bots:status`), its own `s` start/stop keybinding, and its own footer-echo idiom for that action — this story only *borrows* the same footer-echo *pattern* for `o` (per judgment call 1 above), it does not touch `:bots`, the Bots-pane stub body, or any `bots:status`/`bots:control` wiring. `s` and `o` are different keys bound in different views for different purposes; nothing here pre-empts or duplicates Story 4.4's own work.
5. **No time-scrubbing/historical-replay control anywhere in this view (AC7), confirmed by construction (Task 7), not just by omission.** Every value Coin-detail renders is always the single most-recent `snapshots:raw` row for the open instrument — there is no stored history, no time-index, no "as of" state anywhere in `coin_detail_state.py`'s module-level variables (`_LATEST_SNAPSHOT` is singular, overwritten in place on each new matching message, never appended to a list). A future Bot-detail-style day/week/month/all preset toggle (Story 4.5's own pattern, for a *different* data domain — bot PnL/trade history, not market data) must not be grafted onto Coin-detail; FR24's split between "market data stays live-only in the TUI" and "bot/trade performance history is in-scope" is a deliberate domain boundary, not an oversight to "fix" by generalizing Bot-detail's toggle back onto this view.
6. **`snapshots:raw` filtering: client-side, to exactly one instrument, on a session-long always-subscribed connection — not a dynamic per-visit subscribe/unsubscribe.** Detailed fully in Task 3. The channel itself carries every instrument's batch every second regardless (there is no per-instrument channel to selectively join); `bot_tui`'s own dedicated `snapshots:raw` connection (started once, alongside `ranking_state`'s `rankings:live` listener, in `BotTuiApp.run()`) receives the full batch for the entire app session and discards all but the currently-open instrument's row via a simple `if _CURRENT_INSTRUMENT_ID is None: return` / per-row `instrument_id` match — the cheapest, most race-free design available given the channel's actual shape, at the cost of a bandwidth/CPU trade-off judged acceptable for a personal, single-operator tool. A future story could revisit this only if `bot_tui` ever needs *simultaneous* multi-instrument live indicators (e.g. a small multi-coin comparison view) — not a need this story's 7 ACs create.
7. **Separate connection from `ranking_state.py`'s, even though `dashboard.py` itself multiplexes both channels on one connection.** `dashboard.py:1281-1284` subscribes to `snapshots:raw` **and** `rankings:live` on a single shared connection — a real, working precedent for combining them. This story deliberately does *not* follow that precedent and instead gives `coin_detail_state.py` its own, separate connection. Reasoning: `ranking_state._redis_listener` is already-shipped, already-reviewed Story 4.1/4.2 code that Story 4.2's own Dev Notes described as something this codebase "extends, never replaces" — reaching into it to add a second subscribed channel and a second per-message dispatch branch is a larger, riskier change to already-settled code than adding one new sibling module with its own independent connection and lifecycle. The Redis/network cost of a second long-lived pub/sub connection from the same process is negligible for a single-user interactive tool; the code-boundary and blast-radius benefit of keeping `coin_detail_state.py` fully independent (testable, revertable, reviewable in isolation) outweighs the minor duplication.
