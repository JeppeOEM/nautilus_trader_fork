# Story 10.1: Custom-indicator catalog, category-tagged picker, and a histogram panel type

Status: done

## Story

As a user of the chart page's indicator picker,
I want native `nautilus_trader` indicators and dYdX-specific custom indicators presented as two clearly labeled groups, with a histogram rendering option for indicators that aren't a line,
so that I can tell at a glance which indicators come from the standard library versus this project's own signal work, and so a signal like Cancel Pressure (which isn't naturally a line) renders in a way that actually reads as its own metric.

## Acceptance Criteria

1. A new `ml_signals/custom_indicators.py` module exists, mirroring `chart_indicators.py`'s shape (a spec dataclass, a catalog dict, `catalog_json()`, a replay function) but for indicators that are not `nautilus_trader.indicators` classes and are not fed from OHLCV candle fields alone. Its spec dataclass (`CustomIndicatorSpec`) carries: a name, JSON-safe default params, a panel classification, and a replay callable whose signature accepts whatever raw window context it needs (candles, plus instrument/window identifiers a replay function can use to fetch its own `DydxSecondSnapshot`/`TradeTick`/`OrderBookDelta` rows — see Dev Notes' "Signature problem" for why this can't just be `(candles, params)` like the native path) and returns `dict[str, list[float | None]]` aligned 1:1 with the candle list — identical output shape to `chart_indicators.replay_indicator`.
2. `chart_indicators.py`'s `Panel` type (`Literal["overlay", "oscillator"]`) gains a third value, `"histogram"`. The type is extracted to one shared location both `chart_indicators.py` and `custom_indicators.py` import (not duplicated) — decide the location during implementation (a natural option: keep it in `chart_indicators.py`, imported by `custom_indicators.py`, since `chart_indicators.py` already exists and this avoids a new file for one type alias; do not create a `types.py` unless a real second reason emerges — YAGNI).
3. `GET /data/indicators/catalog` (`indicators_catalog_handler`, `dashboard.py:1681-1682`) merges `chart_indicators.catalog_json()` and `custom_indicators.catalog_json()` into one JSON object. Every entry — native and custom — gains a `category` field (`"native"` or `"custom"`) alongside its existing `params`/`panel` fields.
4. `_indicators_json`/`coin_indicators_handler` (`dashboard.py:1630-1656`, `1659-1678`) dispatch a requested spec entry to whichever catalog registers its name: `chart_indicators.INDICATOR_CATALOG` → `chart_indicators.replay_indicator` (unchanged behavior), `custom_indicators.CUSTOM_INDICATOR_CATALOG` → `custom_indicators.replay_indicator` (new). A name in neither catalog still returns the existing 400 "Unknown indicator" response, unchanged.
5. `_renderIndicatorPicker`'s add-list (`dashboard.py:405-414`), currently one flat alphabetical list, renders as two labeled groups — "Nautilus Indicators" and "Custom Indicators" — built from the merged catalog response's `category` field. The existing search box (`#ind-picker-search`) filters across both groups.
6. An indicator classified `"histogram"` renders as Plotly `type:'bar'` traces (not `'scattergl'` lines) inside the *existing* oscillator panel (`_renderOscillatorPanel`, `dashboard.py:586-615`) — sharing its per-instance overlaid-axis machinery from Story 9.1 (`_oscillatorOverlayAxis`, `dashboard.py:583-585`), not a fourth new Plotly panel.
7. This story registers no real custom indicator (no CVD/Cancel Pressure/OFI — those are Stories 10.2/10.3/10.4). Its own test coverage uses one placeholder/fake custom-indicator entry to prove dispatch, category-tagging, and histogram rendering work end-to-end.
8. `cd troll && python -m pytest ml_signals/tests/test_dashboard_chart.py ml_signals/tests/test_dashboard_chart_pan_js.py ml_signals/tests/test_chart_indicators.py -q` passes, plus a new `ml_signals/tests/test_custom_indicators.py`.

### Review Findings

- [x] [Review][Patch] Native/custom catalog name collision silently diverges: `_merged_indicator_catalog` would last-write-wins onto whichever catalog's `catalog_json()` ran second, while `_indicators_json`'s dispatch checks the native catalog first — a future indicator name registered in both would show one implementation in the picker and silently execute the other [troll/ml_signals/dashboard.py:_merged_indicator_catalog] — fixed: raises `ValueError` immediately on any name collision, with a regression test.
- [x] [Review][Patch] `_renderOscillatorPanel`'s layout never set `barmode`, so Plotly's default (`"group"`) would offset multiple simultaneous bar traces sideways at each x tick, misplacing a histogram indicator's bars away from their true timestamp the moment a second bar trace is active [troll/ml_signals/dashboard.py:_renderOscillatorPanel] — fixed: `layout.barmode='overlay'`, asserted in the histogram JS test.
- [x] [Review][Patch] `ReplayWindow`'s `start_ms`/`end_ms` could disagree with which candle path (live vs. historical) `coin_indicators_handler` actually used, if a query string had only one of `start`/`end` parseable — the window would carry one real bound into what was actually the live window, misleading a future custom replay's own live-vs-historical check [troll/ml_signals/dashboard.py:coin_indicators_handler] — fixed: extracted a pure `_indicator_replay_window()` helper that normalizes both bounds together, with 3 unit tests.
- [x] [Review][Patch] Bar traces carried a no-op `mode:undefined` (enumerable own-property, not a genuinely absent key) and a dead `line:{width:1}` (meaningless on a Plotly `bar` trace, which styles via `marker`) [troll/ml_signals/dashboard.py:_renderOscillatorPanel] — fixed: trace object is now built conditionally so `mode`/`line` are only ever present on line traces; bar traces get a light `marker.opacity` instead. Asserted via `"mode" in trace`/`"line" in trace` checks in the JS test (not just value checks, which wouldn't have caught the enumerable-undefined case).
- [x] [Review][Patch] Module docstring claimed `custom_indicators.py` "never imports from chart_indicators.py" directly above a `from ml_signals.chart_indicators import Panel` line, and claimed to mirror `chart_indicators.py`'s shape without noting it deliberately excludes `enum_params` round-tripping [troll/ml_signals/custom_indicators.py] — fixed: corrected wording to describe the actual (correct) boundary — catalog *contents* stay mutually unaware, the `Panel` type alias is the one intentional shared import — and noted the `enum_params` exclusion as deliberate/YAGNI.
- [x] [Review][Patch] The two new JS test harnesses used inconsistently-shaped `_indicatorCatalog` fixtures (one included `category`, the other omitted it), risking a real shape drift going unnoticed [troll/ml_signals/tests/test_dashboard_chart_pan_js.py] — fixed: both harnesses now include `category` on every entry.
- [x] [Review][Defer] `CustomIndicatorSpec` has no runtime enforcement that a registered `panel` value is one of the three valid `Panel` literals, or that `replay`'s actual arity/return shape matches `ReplayFn` — a typo'd panel value would render on no panel with no error surfaced. Pre-existing, symmetric gap on the native `IndicatorSpec` too (neither catalog validates at registration time) — not introduced fresh by this story, and no real custom indicator exists yet to trigger it. `troll/ml_signals/custom_indicators.py`, `troll/ml_signals/chart_indicators.py`.
- [x] [Review][Defer] `_indicators_json`'s single broad `except Exception` reports a future custom `replay` function's own programming bugs (e.g. output length not matching `candles`) identically to malformed user input — both collapse to a 400 logged at `logger.info`, which under-reports real implementation bugs once Stories 10.2-10.4 add real replay logic with real failure modes. No real custom indicator exists yet to trigger this. `troll/ml_signals/dashboard.py:_indicators_json`.

## Dev Notes

- **Signature problem — the one real design decision this story must make, not previously resolved by the epic text:** `coin_indicators_handler` (`dashboard.py:1659-1678`) builds `candles` via `_historical_candles_json`/`_live_candles_json` and calls `_indicators_json(candles, spec_str)` (`dashboard.py:1630`) — that function's only inputs are the candle list and the raw spec string. `chart_indicators.replay_indicator(candles, name, params)` needs nothing else because every native indicator is a pure function of OHLCV. A custom indicator is NOT: CVD/Cancel Pressure/OFI (Stories 10.2-10.4) each need `DydxSecondSnapshot`/`TradeTick`/`OrderBookDelta` rows for the *same window* the candles cover, which means a custom `replay` function needs `instrument_id` and the window bounds (`start_ms`/`end_ms` for historical, or access to the live rolling buffers for the live case — compare how `_historical_candles_json`/`_live_candles_json` themselves already split this exact live-vs-historical distinction, `dashboard.py`). `coin_indicators_handler` already has `symbol`, `bar_seconds`, `start_ms`, `end_ms` as locals (`dashboard.py:1660-1667`) — thread them through to `_indicators_json` and onward to `custom_indicators.replay_indicator`, but do NOT change `chart_indicators.replay_indicator`'s own signature or its call site — only the custom-dispatch branch needs the extra context. Keep this proportionate (DESIGN-01): a small typed context (e.g. a 4-field dataclass or just passing the extra params) is enough, not a generic "replay context" abstraction with hooks for hypothetical future needs.
- **Read before touching anything:** `ml_signals/chart_indicators.py` in full (`IndicatorSpec` `chart_indicators.py:41-51`, `INDICATOR_CATALOG` `54-287` — don't need to read every entry, just the shape of a few), `replay_indicator` `295-315`, `_feed_values` `328-337` (note: custom indicators do NOT reuse `_feed_values` — it's candle-field-specific), `catalog_json` `340-349`.
