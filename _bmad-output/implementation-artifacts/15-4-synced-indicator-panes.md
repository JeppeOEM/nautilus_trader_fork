# Story 15.4: Synced indicator panes

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the dashboard operator,
I want OFI, order-book imbalance, volume, microprice, and spread panes stacked beneath the candlestick chart and moving in lockstep with it,
so that I can read a coin's technical structure without the panes drifting out of sync the way ad-hoc event wiring would risk.

## Acceptance Criteria

1. **A pane is added via `chart.addPane()` + `addSeries`/`addCustomSeries` on its own `IPaneApi` — never a second `createChart()` instance.** Story 15.3 establishes the one `lightweight-charts` `createChart()` instance (`LightweightChart.tsx`); this story adds N sub-panes onto that same instance (spine AD-F4).
2. **Panes are keyed by `dashboard.py`'s existing `_indicator_id(name, params)` scheme (`ml_signals/dashboard.py:1889`, reused/ported, not reinvented), held in a single `Map<indicatorId, IPaneApi>` owned by the one component that calls `createChart()`.** No child component creates or destroys a pane directly.
3. **Panning or zooming any one pane moves every other pane on the page in lockstep, in the same interaction, via the charting library's native multi-pane time-scale sync — no custom event-relay code** (the exact class of thing `dashboard.py`'s hand-rolled `_syncChartXRange`/`_SYNCED_CHART_IDS` Plotly-relayout logic did, and which AD-F4 exists to retire).
4. **Adding, removing, or reconfiguring an indicator never resets the chart's current zoom/pan position** — the exact regression Story 14.3 exists to fix, and this epic's own trigger.
5. **Indicator panes co-page with the candlestick pane's scroll-back in the same interaction — never blank, never lagging.** When Story 15.3's `useCandles` scroll-back triggers the next `before_ns`/`limit` page, each visible indicator pane's own underlying data is fetched for that same window as part of the same interaction (not a separately-triggered, independently-timed fetch).
6. **Touch parity:** on a touch-driven phone/tablet viewport, dragging to pan or pinching to zoom any pane produces every consequence above identically to mouse/trackpad (FR-39, NFR-B).
7. **Up to five indicator panes visible at once, each gets a distinct, consistently-assigned series color.** Exact palette values finalize in Story 15.9 — this story builds the assignment logic (indicator id → color slot) so panes are never visually indistinguishable in the interim.
8. **Pane data is computed by calling `ml_signals.indicators`' existing OFI/OBI/microprice/spread functions/classes unchanged — never a reimplementation** (AD-F2). See Dev Notes for which specific classes/functions and why (this is *not* the same OFI as the existing chart-page indicator picker's "OrderFlowImbalance" custom indicator — see the naming-collision warning below).
9. **Tests:** a Vitest test exercises the keyed pane registry (add/remove by indicator id, re-adding an id after removal), and a pan/zoom-propagates-to-a-sibling-pane check is verified — see Task 7 for why this specific mechanism needs a real-browser check, not just a jsdom/mocked unit test.

## Dev Notes

- **Sequencing dependency, stated plainly: this story cannot start until Story 15.3 is actually implemented**, not just planned. As of this story's creation, Story 15.3's own Dev Agent Record is empty (`lightweight-charts` is not yet in `frontend/package.json`, `ChartPage.tsx` is still the placeholder, `data_api/routes/candles.py` does not exist yet) — sprint-status.yaml shows 15.3 as `ready-for-dev`, meaning spec'd but not yet built. This story's every task assumes 15.3's `LightweightChart.tsx` (one `createChart()` instance), `useCandles.ts` (cursor-pagination hook + `subscribeVisibleLogicalRangeChange` wiring), and `CandleItem`/`CandlesResponse` types already exist — verify they do before starting, don't assume from this file alone.
- **This is the load-bearing pane-sync mechanism the rest of the epic builds on** (per `epic-15-context.md`'s Cross-Story Dependencies): Story 15.6's keyed pane set (add/remove via the general indicator picker UI) and Story 15.9's final color palette both extend what this story builds — get the `Map<indicatorId, IPaneApi>` ownership model and the `_indicator_id` naming-collision avoidance right here, or both later stories inherit the bug.
- **Why `MultiLevelOFI`/`MultiLevelOBI`, not `custom_indicators.py`'s existing "OrderFlowImbalance"/CancelPressure/CVD:** those three replay raw `OrderBookDelta` catalog rows, which `dydx_collector` only persists per-instrument when raw-delta capture is opted in (default off, per `ml_signals/chart_data.py`'s own module docstring) — this is the *exact* bug class Story 11.1 already root-caused and fixed once for the imbalance/depth/spread panes (`chart_data.compute_chart_series` was rewritten to read always-persisted `DydxSecondSnapshot` rows instead of raw deltas for that reason). `MultiLevelOFI`/`MultiLevelOBI` are explicitly documented (`ml_signals/indicators.py:241,276-277`) to be fed via `update_raw(...)` directly from `DydxSecondSnapshot`-shaped fields — always available, consistent with `troll/CLAUDE.md`'s Signal Architecture (SIGNAL-01: 1s-snapshot-based, not raw-delta-based). Do not reach for the custom-indicator picker's OFI for this story's fixed panes.
- **`ml_signals.indicators.microprice`/`spread` are the stateless, single-snapshot functions** (`ml_signals/indicators.py:409-439`, SSOT-01) — the same functions `chart_data.compute_chart_series` already calls for the (unpaginated, start_ns/end_ns-bounded) microfeatures panel. This story does not touch or reuse `compute_chart_series` itself (its shape is a non-paginated one-off `dict[str, list[dict]]`, incompatible with AD-F3's `{items, has_more}` envelope) — it calls the same underlying `ml_signals.indicators` primitives from a new, properly cursor-paginated route instead.
- **`lightweight-charts` 5.2.1's multi-pane API (`chart.addPane()`, `IPaneApi`, `addSeries`/`addCustomSeries` per-pane) is already `[VERIFIED lightweight-charts 5.2.1, 2026-09-13]`** in the architecture spine, 2 days before this session — no new library or version is introduced by this story (same `lightweight-charts` 5.2.1 dependency Story 15.3 already adds; same FastAPI/Pydantic already in use), so no further external research was done for this story.
- **Testing `lightweight-charts` under Vitest/jsdom is a known pitfall, same as Story 15.3's note:** `jsdom` has no real `<canvas>` 2D context. Mock the library at the module boundary for the keyed-registry unit test (assert `addPane`/`addSeries`/removal calls happened with the right arguments); do not add the `canvas` npm package (dependency-minimization preference) — and see Task 7's note on why the *native sync* claim itself needs a real-browser check regardless.
- **No Dockerfile changes needed this story** — `troll/data_api.dockerfile` already `COPY`s `ml_signals`/`data_api` wholesale (same reasoning as Story 15.3's Dev Notes).
- **`troll/CLAUDE.md` constraints that apply:** FORK-01/FORK-02 (nothing under `nautilus_trader/`/`crates/` touched), MEM-01 (bounded reads extended to the new route, Task 1), NAUT-02/SIGNAL-01 (snapshot-based indicator classes reused unchanged, no new hand-rolled OFI/OBI math), DATA-01 (gap markers, Task 1), SSOT-01/03 (microprice/spread computed exactly once via the shared function; before adding this new route, confirmed no existing route already serves cursor-paginated per-bar OFI/OBI — it doesn't, `compute_chart_series` is the closest existing thing and is a different, incompatible shape), DESIGN-01 (volume reuses the already-fetched candle field, no new query; color-assignment logic stays a small pure function, no premature config system).
