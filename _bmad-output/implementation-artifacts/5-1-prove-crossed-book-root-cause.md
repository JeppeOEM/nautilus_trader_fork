## Story

As a maintainer of the dYdX collector's data-integrity gate,
I want to trace live "Crossed book" episodes back to the exact wire message our pipeline lost (using the `[WS_RAW]` trace log already added at `crates/adapters/dydx/src/websocket/handler.rs:215`),
so that the 72% "our pipeline's fault" bucket (41/57 episodes) is root-caused with hard evidence rather than resting on pattern-inference from a single byte-level example, satisfying `troll/CLAUDE.md`'s DATA-02 standard.

## Acceptance Criteria

1. **Trace visibility confirmed.** Given trace-level logging is enabled for `nautilus_dydx::websocket::handler` and the collector is running against live dYdX data, when any WS text message is received, then a `[WS_RAW] <raw json>` line appears in the collector's logs for it (verified by manually triggering at least one known message, e.g. a subscription ack).
2. **New episodes captured with raw trace active.** Given `reference_ws_check.py` is running concurrently with `[WS_RAW]` trace enabled, when at least 5 new "Crossed book" episodes occur, then each has both (a) a `docker logs` window containing surrounding `[WS_RAW]` lines and (b) a corresponding `reference_check_out/episode_*.json` file from the existing reference-client tooling.
3. **Per-episode classification.** Given each of the 5+ new episodes, when its `[WS_RAW]` log window is diffed against the reference client's `messages_touching_frozen_prices` for the same instrument/timeframe, then it is classified as exactly one of:
   - **(a) Received-but-lost** — the message the reference client got (e.g. the delete/update touching the frozen price) IS present in our `[WS_RAW]` log, meaning the loss is downstream of the socket (parse, `handle_feed_message`, msgbus, Python callback, book-apply).
   - **(b) Never received** — the message is ABSENT from our `[WS_RAW]` log despite the reference client receiving it, meaning the loss is at or before the socket layer (this specific connection, `tokio-tungstenite`, reconnect/replay).
4. **Root-cause doc updated.** Given the classification results, when the investigation concludes, then `troll/.planning/debug/crossed-book-root-cause.md`'s "Open question" section (currently lines 78-91) is replaced with either (a) a confirmed mechanism cited to specific evidence (episode file + log line), or (b) an explicit statement of the classification split (e.g. "N received-but-lost, M never-received") with a recommended next step for whichever locus dominates — never left as a re-assertion of the same open question. This satisfies DATA-02's requirement that an ingestion-correctness question end in one of its two acceptable states, not a quieter version of the same mystery.
5. **Fork-safety cleanup.** Given the investigation's conclusion, when the story is done, then the temporary `ponytail:`-tagged `log::trace!("[WS_RAW] {txt}")` line at `handler.rs:215` is either removed (default) or explicitly kept with a one-line justification recorded in Dev Notes — `crates/` must not carry silent, unexplained debug scaffolding per FORK-01/FORK-02.
6. **No regressions.** Given the `crates/` change already made (a single added trace log line, no logic change) and any Python-side changes this story makes (if a correlation script is written), when `python3 -m pytest troll/dydx_collector/tests -q` and the Rust adapter's own test suite are run, then all pass with zero regressions.

### Debug Log References

- **AC #1 first attempt failed:** after `make build-base` + `make up`, zero `[WS_RAW]` lines appeared in `docker logs dydx-collector` despite `component_levels={"nautilus_dydx::websocket::handler": "TRACE"}`. Root cause: root `Cargo.toml:186-191`'s `log = { ..., features = ["release_max_level_debug"] }` compiles `log::trace!` calls out of the binary entirely in release builds (`.docker/nautilus_trader.dockerfile:67` builds `cargo build --release`) — not a runtime filtering issue, the trace call site never exists in the compiled binary. No `component_levels`/runtime config can revive a call that was stripped at compile time.
- **Fix v1 (incomplete):** changed `handler.rs:216` from `log::trace!` to `log::debug!` and `collector.py`'s `component_levels` value from `"TRACE"` to `"DEBUG"`. Caught before rebuild: `component_levels` alone still wouldn't surface it — `Logger::enabled()` (`logger.rs:748-756`) gates on the *global* `stdout_level` (`WARNING`) before component/module overrides are ever consulted, so a `debug!` call stays invisible on stdout no matter what `component_levels` says. Confirmed by reading `enabled()`, `should_filter_log_inner`, and `FilterPolicy::from_config` directly rather than assuming — user explicitly asked "are you sure" before triggering a second rebuild, which is exactly what caught this.
- **Fix v2:** removed `component_levels` entirely (it cannot help here); added `level_file=DEBUG`, `directory="/tmp/nautilus_logs"`, `file_name="ws_raw_debug"`, `file_rotate=(100_000_000, 3)` to `collector.py`'s `init_logging()` call. `[WS_RAW]` must be read via `docker exec dydx-collector`, not `docker logs`.
- **v2 still produced 0 bytes after 90+ seconds of live 26-instrument market data** (file existed, config printed correctly via a temporary `print_config=True`). Ruled out via direct empirical tests rather than more theorizing: (a) confirmed `"[WS_RAW]"` literal present in the rebuilt `.so` via `grep` on the binary -- code was compiled in; (b) added a periodic explicit `nautilus_pyo3.logging_sync_to_disk()` call -- still 0 bytes, ruling out simple `BufWriter` lag; (c) decisive test: called `nautilus_pyo3.logger_log(WARNING, ...)` directly from the running process (a guaranteed-good WARNING-level call, unrelated to `handler.rs`) -- **also produced nothing on stdout**, despite `stdout_level=WARNING` which should have passed it.
- **Fix v3 (actual root cause, in `collector.py`'s `main()`):** `nautilus_pyo3.init_logging(...)` returns a `LogGuard` that `collector.py` was calling as a bare statement, discarding the return value. `LogGuard::drop()` (`crates/common/src/logging/logger.rs:1343-1379`): when the *last* `LogGuard` is dropped, it sets a global `LOGGING_BYPASSED` flag, calls `log::set_max_level(Off)`, sends `Close`, and joins the logging thread -- i.e. it treats "guard dropped" as "shut down the whole subsystem." Since nothing held a Python reference to the returned guard, CPython garbage-collected it within microseconds of the call returning, on *every single collector startup*. This means Rust-side logging has been silently dead this entire investigation (and likely since `nautilus_pyo3.init_logging()` was first added) -- the earlier conclusion "zero Rust-side errors fired across many real episodes" was based on a dead pipe, not a clean result. Fixed by assigning the guard to `_log_guard` (kept alive for `main()`'s whole lifetime, which is the process lifetime). This is a real production bug fix, not debug scaffolding, and stays after this story's `[WS_RAW]` line is removed -- it permanently restores the Rust-side error visibility DATA-02's earlier work believed it already had. Verified: 317+ `[WS_RAW]` lines (connected/subscribed/markets/deltas) within 30s of restart.
- **Fix v4 (retention window too short, found while checking the first captured episode):** `file_rotate=(100_000_000, 3)` was a guess, not a measurement. Actual `[WS_RAW]` volume is ~1MB/s across the subscribed instruments, so 100MB backups rotate every ~90s and 3 backups retain only ~6 minutes of history — confirmed the hard way: `episode_BTC-USD_1788603936.json` (10:25:36) could not be correlated because its covering log file had already rotated away by the time it was checked. Removed `file_rotate` entirely — `FileWriter`'s rotation only triggers for a custom-named log when `file_rotate` is explicitly set (`writer.rs`'s `should_rotate_file`), so omitting it keeps ONE ever-growing file (`ws_raw_debug.log`, no timestamp suffix) with full history for the rest of the investigation. ~1MB/s over several hours is a few GB; 217GB free on disk, no concern. All episodes from 2026-09-05 10:34 UTC onward are correlatable; `episode_BTC-USD_1788603936.json` is not and should be excluded from the classification tally in Task 3/4 (it was a category-1 genuine-crossing match anyway — reference book exactly matched the collector's claim — so its loss doesn't affect the category-2 pipeline-bug count this story cares about).
