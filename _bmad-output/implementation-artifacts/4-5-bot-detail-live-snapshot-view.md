# Story 4.5: Bot-detail live snapshot view

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the operator,
I want to drill into a bot and see its current PnL, position, mode, and health at a glance,
so that I can assess a bot's live state in one keypress before deciding whether to investigate further.

## Acceptance Criteria

1. **`Enter` on a highlighted Bots-pane row opens Bot-detail full-screen with a live snapshot header.** Given a highlighted row in the Bots pane, when the builder presses `Enter`, then Bot-detail opens full-screen (not a split-pane, not a modal), showing a bordered live-snapshot-header region with PnL, position/exposure, mode, uptime/last-heartbeat, win-rate-to-date, and strategy/symbol — all sourced live from `bots:status`, the same shared data `bots_state.py` already accumulates for the Bots pane (FR18, UX-DR6).
2. **`esc` returns to the Bots pane.** Given Bot-detail is open, when the builder presses `esc`, then it returns to the Bots pane (FR21).
3. **`s` acts on the open bot without leaving the view.** Given Bot-detail, when the builder presses `s`, then start/stop acts on the open bot exactly as Story 4.4's control does from the Bots pane — publishes `{bot_id, action: "start"|"stop"}` on `bots:control`, footer-echoes `sent: {action} {bot_id}`, no optimistic local state change (FR23, reuses Story 4.4's `bots_state.publish_control`).
4. **Only the live-snapshot-header region ships in this story.** Given this story ships before Story 4.7, when Bot-detail is viewed, then it shows only the live-snapshot-header region — the trades blotter and PnL-over-time regions (and their `t`/`o`/`j`/`k` keybindings, which operate on those two regions) are added in Story 4.7 and are not required for this story's completion. Do not stub placeholder blotter/chart regions or advertise their keybindings in the footer before they exist — this codebase's own established convention (Story 4.3 Task 4: "advertise only what's actually bound in this view").

## Dev Notes

### Judgment calls made while writing this story — read before implementing

1. **`bots:status` gains one new field (`closed_trades`), not a new channel or a restructured payload.** The mockup's win-rate display (`41% (63 trades)`) needs a trade count that `build_status()` already computes internally (`len(closed_positions)`) but doesn't currently return. Adding one key is the minimal change; there was no reasonable alternative that avoided touching `bot_status.py` at all, since no other existing field carries this count.
2. **Bot-detail has no `open_bot()`/`close_bot()` subscription-lifecycle pair, unlike Coin-detail's `open_coin()`/`close_coin()`.** Coin-detail needed that pair because `coin_detail_state.py` filters a shared multi-instrument channel (`snapshots:raw`) down to one instrument client-side, and fresh per-visit `Microprice`/`MultiLevelOFI`/`MultiLevelOBI` instances matter for OFI's diff-against-previous-tick correctness (Story 4.3 Dev Notes item 3). `bots_state.py` has neither concern — it already accumulates every bot's latest status unconditionally (Story 4.4's design, one message per bot, no aggregation/diffing state to reset). Opening/closing Bot-detail is therefore just a view-stack push/pop plus one instance attribute, nothing else.
3. **The Bots-pane row's own win-rate text (`bots_pane.format_win_rate`/`format_bot_line`, both Story 4.4-shipped) is deliberately left untouched**, even though the UX mockup for the Bots pane itself (`mockups/key-bots-pane.html` line 122: `58% (142)`) also shows a trade count that Story 4.4's shipped implementation omits. That's a pre-existing gap versus the mockup in already-reviewed, already-`done` Story 4.4 code — fixing it is out of this story's scope (this story's own AC set says nothing about the Bots-pane row) and risks touching tested/reviewed code for a cosmetic parity fix. If this bothers the operator, it's a one-line follow-up (`format_win_rate` gaining a `closed_trades` parameter, `format_bot_line` passing it through) that can be done as its own tiny fix, not smuggled into this story.
4. **No `o` deep-link and no `t`/`j`/`k` in this story (AC4).** The mockup's full footer (`j/k scroll  t time-range  s stop bot  o dashboard  esc back  :q quit`) belongs to the *complete* Bot-detail view with all three regions built (Story 4.7) — `o` deep-links to "the dashboard's fuller trades/PnL view for the same bot" (EXPERIENCE.md), which has no meaning, and quite possibly no corresponding dashboard route yet, before Story 4.6/4.7 exist. Advertising or wiring any of these now would be exactly the kind of speculative-ahead-of-need work `troll/CLAUDE.md`'s DESIGN-01 (YAGNI) warns against, and would violate this codebase's own established "advertise only what's actually bound" footer discipline (Story 4.3 Task 4).
5. **`_toggle_bot()` is retargeted via a new `_active_bot_id()` helper, not duplicated.** The alternative — a second, near-identical `_toggle_bot_detail()` method — would fork one piece of logic (which bot to act on, and how to report it) into two copies that could drift. `_active_bot_id()` is a one-line-bodied, trivially testable seam between "which view am I in" and "which bot does `s` act on," reusable by both `_handle_global_key`'s `s`-in-`"bots"` branch and `_handle_bot_detail_key`'s `s`-in-`"bot_detail"` branch.
6. **Stale-badge source for Bot-detail's breadcrumb is `bots_state.is_stale(bot_id)` (Story 4.4's existing per-bot function), not `ranking_state.is_stale`** (which Coin-detail's own badge reuses, per Story 4.3's `_coin_detail_stale_badge_active`). These are different heartbeat producers on different channels (`bots:status` vs. `snapshots:raw`) with different staleness thresholds (`_BOT_STALE_SECONDS = 15.0` vs. `ranking_state`'s own constant) — do not reuse `ranking_state.is_stale` here even though the *pattern* ("append `(stale, "~ STALE")` to the breadcrumb") is identical to Coin-detail's.
7. **A missing-status `None` guard in `_build_bot_detail_body()` is defensive, not expected to ever trigger in practice** — `Enter` is only reachable from `_highlighted_bot_id()`, which only ever returns a `bot_id` that's already backing a rendered `_SelectableBotRow`, which itself only exists because `bots_state._LATEST_STATUSES` already has an entry for it. Written anyway because, unlike `_build_coin_detail_body` (whose every field-read line already threads an optional `snapshot`), this method has no pre-existing shape to inherit that discipline from, and a short explicit early-return is cheaper than auditing every downstream `bots_pane.bot_detail_lines(status, ...)` call for a `None`-safety guarantee it doesn't otherwise need.
