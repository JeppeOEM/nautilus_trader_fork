# Story 1.8: Volatility-based ranking mode via a dedicated ranking engine

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the researcher/builder,
I want a second, user-selectable Ranking Mode based on cross-sectional volatility, computed and published by one shared ranking engine alongside the existing volume mode,
so that I can switch between "what's loud" (volume) and "what's moving" (volatility) with the dashboard, backtests, and any future reader always agreeing on the order, never computing it independently.

## Acceptance Criteria

1. **`ranking_engine` becomes the sole computer/publisher of Coin Ranking, publishing `rankings:live`.** Given the existing inline ranking logic in `dashboard.py`, when this story is implemented, then it is extracted into a new `ranking_engine` module that becomes the sole computer/publisher of Coin Ranking — both volume and volatility — publishing on Redis channel `rankings:live` a JSON message with `mode` (`"volume"` | `"volatility"`), `updated_at`, and an ordered `ranks` list of `{instrument_id, rank, volume24h, volatility_score}` objects, with both score fields always present regardless of active mode (FR16, architecture AD-9).
2. **Cross-sectional volatility with a configurable lookback (default 1h).** Given subscribed coins' captured price/return data, when the ranking engine computes volatility, then it uses standard deviation of price/returns over a configurable lookback window, defaulting to 1 hour, ranking coins by relative (cross-sectional) volatility against all other subscribed coins — changing the lookback requires no code change (FR16).
3. **Global, atomic mode switching via `ranking:control`.** Given the ranking engine is running with an active Ranking Mode, when a mode-switch request is published to Redis channel `ranking:control`, then the active mode changes atomically for every reader — Ranking Mode is global shared state, not per-viewer, and last-write-wins on a near-simultaneous double-switch is accepted (architecture AD-9).
4. **Publish on change + heartbeat.** Given the ranking engine's publish discipline, when it publishes to `rankings:live`, then it publishes on both rank-change and a fixed heartbeat interval, so readers can distinguish a missed heartbeat (stale) from "nothing changed" (architecture AD-9).
5. **No regression to Story 1.4's historical ranking view.** Given the relocated ranking-history store (SQLite `metrics_store`), when historical ranking queries are made (FR8, Story 1.4), then they continue to work identically post-extraction — no regression to Story 1.4's historical-ranking-view behavior.

## Dev Notes

**This is an extraction/relocation story first, a new-feature story second — read the "what currently exists" section before writing any new code.** The bulk of the engineering risk here is *not* volatility math (a one-line `statistics.stdev` call, already precedented three times over in this codebase) — it's correctly untangling `dashboard.py`'s ranking logic from its display logic, and correctly relocating a shared SQLite writer without creating two writers or breaking Story 1.4's still-must-work historical view.

### Three pre-existing, unrelated "volatility" computations already in this codebase — do not confuse any of them with FR16's new `volatility_score`

This is the single easiest mistake to make in this story, found only by reading `dashboard.py`/`catalog_stats.py`/`metrics_computer.py` in full:

1. **`catalog_stats.price_stats()`** (`catalog_stats.py:190-224`) — `np.std(returns)` over a catalog-driven, time-bounded (25h via `PRICE_LOOKBACK_HOURS`, `metrics_computer.py:48`) price series read from `ParquetDataCatalog.trade_ticks()`/mark price. Feeds `metrics_computer.compute_snapshot()`'s `"volatility"` key (`metrics_computer.py:106`), which `_slow_loop_task` persists to `metrics_store`'s `"volatility"` column and displays via `_LIVE_SLOW`.
2. **`dashboard._ingest_batch`'s live calc** (`dashboard.py:1052-1057`) — `statistics.stdev(rets)` over `_second_rolling[iid]`'s mid-price returns, a **300-entry, ~5-minute** rolling window (`dashboard.py:146`, `maxlen=300`) — *not* configurable, *not* 1h, *not* cross-sectional. This value wins over #1's in the live table via `_merged_live`'s `{**_LIVE_SLOW, **_LIVE_FAST}` fast-wins merge (`dashboard.py:162-164`), so in practice the rankings table's existing "Vol" column (`RANKING_COLS`, `dashboard.py:110`) has *always* shown #2, not #1, once the first Redis batch arrives.
3. **This story's new `volatility_score`** (`ranking_engine/volatility.py`, Task 4) — cross-sectional, configurable lookback (default 1h = 3600s), computed independently of #1 and #2, published only in `rankings:live`'s `ranks[]` entries and never displayed as a `RANKING_COLS` cell (that column already exists and already means something else — see next point).

**Do not touch `RANKING_COLS`'s existing `("volatility", "Vol", ...)` entry (`dashboard.py:110`) or `metrics_store.COLS`'s existing `"volatility"` column (`metrics_store.py:33`) as part of this story** — both are pre-existing, unrelated, and this story's ACs do not ask for their consolidation or removal. Reconciling all three into one computation is a plausible, reasonable future cleanup (arguably even a good idea) but is explicit scope creep beyond this story's 5 ACs — flag it as a candidate Deferred item in this story's Change Log/Completion Notes if you notice it while working, do not attempt it inline.

### Heartbeat/staleness discipline — the exact rule, not just "publish periodically"

AD-9: *"`ranking_engine` publishes on `rankings:live` on both rank-change and a fixed heartbeat interval... `dashboard`/`bot_tui` treat absence of a heartbeat within a configurable timeout as `unknown/stale`, never as 'last known ranking is still current.'"* This is the same discipline already established for `bots:status` (AD-10) — a `ranking_engine` crash/restart must show up as visibly stale to every reader, not as a silently-frozen last-good ranking. Task 6 implements the publish side; Task 8 implements the reader side (`_LATEST_RANKING_RECEIVED_AT` + a threshold). Neither side is optional — a publisher with no heartbeat, or a reader that never checks one, both defeat AC4.

#### Heartbeat interval default — checked against the relocated code, not guessed

Neither AC4 nor AD-9 gives `RANKING_HEARTBEAT_SECONDS` a number ("a fixed heartbeat interval" only). Before treating this as unknowable, every timer-driven loop actually being relocated by this story was checked for a reusable cadence:

- `_volume_loop_task` — `VOLUME_POLL_SECONDS = 60` (`dashboard.py:79`).
- `_slow_loop_task` — `DB_WRITE_INTERVAL_SECONDS = 60` (`dashboard.py:77`).
- The collector's own `flush_interval_seconds` (default `60`, `dydx_collector/config.py:75`) and `snapshot_interval_seconds` (default `0.5`, `dydx_collector/config.py:66`).

**None of these is evidence for the heartbeat value**, because none of them is the loop being relocated into a "publish regardless of change" role: `dashboard.py` today never publishes anything to Redis at all — its only "live" surface is the browser polling `/api/rankings` over HTTP (`_INDEX_HTML`'s `showRankings()`: `setInterval(pollRankings, 2000)`, i.e. every 2s), which is a client-pull pattern with no server-side heartbeat concept, not a pub/sub publish-on-timer loop. `RANKING_HEARTBEAT_SECONDS` is therefore a genuinely new interval constant this story introduces, not a relocation — confirmed by grepping this codebase for any existing "heartbeat" concept (`grep -rn heartbeat troll/` returns only `dydx_collector/client.py:89`'s unrelated WebSocket ping keepalive).

**Firm default: `RANKING_HEARTBEAT_SECONDS = 5`.** Rationale: it must be short enough that a `ranking_engine` crash becomes visibly stale within a few seconds (this project's existing urgency precedent: `_CHART_GAP_THRESHOLD_MS = 2500`, `_WATCHLIST_STALE_NS = 30s` for raw-feed staleness — a derived-data staleness signal should not lag far behind those), and long enough not to flood Redis with near-duplicate heartbeat messages on top of the rank-change publishes that already fire roughly once per second-cadence ingest batch. `5` sits just above the dashboard's own existing 2s browser-poll interval (so a normal poll cycle sees at least one heartbeat even during a quiet market) while staying an order of magnitude below the 60s persistence-loop cadence (so staleness detection doesn't take up to a minute to trip). Document this default in the Completion Notes as-implemented; a future story may tune it.

### Module boundary rule (AD-4) — restated precisely for this story

`bot_tui`/`dashboard` (future and present readers) may only import shared data types and pure, side-effect-free utilities from `ranking_engine` — never its internals (the live `_LAST_SEEN`/`_VOLUME_24H`/`volatility.py` tracker state, the Redis subscriber tasks, `_ACTIVE_MODE`'s mutation path). `metrics_store`'s query functions are the one deliberately-carved-out exception, reasoned through explicitly in Task 2 above (mirrors AD-10's precedent for `live_paper`'s Cache-history query functions being the sanctioned read path over Nautilus's Cache, never its raw internal encoding) — everything else in `ranking_engine` is off-limits to direct import from `dashboard.py`/any future `bot_tui` code; those consumers talk to `ranking_engine` only via `rankings:live`/`ranking:control` (live path) or `metrics_store`'s read functions (historical path), never a direct import of `engine.py`'s live state.
