# Story 4.1: Scaffold the TUI shell and live Coins pane

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the builder,
I want to launch a keyboard-only urwid terminal UI that opens directly to a live-mirrored Coins pane,
so that I have a working, navigable foothold to build every other view on top of.

## Acceptance Criteria

1. **Own asyncio loop + `redis.asyncio` subscriptions, launched interactively, never a daemon.** Given the `bot_tui` module (new, per architecture structural seed), when it starts, then it runs its own asyncio event loop alongside `redis.asyncio` pub/sub subscriptions, launched interactively (e.g. `docker compose exec`/`run` or on-host) — never as a `restart: always` daemon (FR17, UX-DR2).
2. **Defaults to a live-mirrored Coins pane.** Given the running TUI, when it opens, then it defaults to the Coins pane, showing a breadcrumb header (`Coins`), a footer hint bar with available keybindings, and the ranked coin list read live from `rankings:live` (Story 1.8) — with no separate data pipeline and no local recomputation of rank (FR17, FR19, UX-DR2).
3. **`:` command bar navigates by name, rejects unknown commands loudly.** Given the `:` command bar, when the builder types `:` then `coins` or `bots` and presses Enter, then it jumps to the named pane; an unrecognized command echoes `unknown command: {input}` and stays open for correction rather than silently no-op'ing (FR21, UX-DR2).
4. **`esc` pops back one level, never exits; only `:q` quits.** Given any non-default view, when the builder presses `esc`, then it pops back exactly one level and never exits the program; quitting is only reachable via `:q` (FR21, UX-DR2).
5. **Cold-open state before the first live message.** Given the Coins pane's live feed, when no `rankings:live` message has arrived yet, then it renders a `waiting for rankings:live…` state in the neutral/quiet color, not a blank screen or a skeleton row (EXPERIENCE.md State Patterns: Cold open).

## Dev Notes

**This is a greenfield scaffolding story, not an extraction/relocation story** (unlike Story 1.8) — `bot_tui` is entirely new code with no prior inline implementation anywhere to relocate. The engineering risk here is concentrated in two places: (1) getting `urwid`'s asyncio integration and manual-redraw requirement right (a background-task-updates-state-but-screen-never-refreshes bug is easy to ship and easy to miss in a hasty smoke test), and (2) drawing the scope line for this "scaffold" story correctly against four adjacent things the mockup/architecture doc show or imply but that belong to *later* Epic 4 stories — get any one of these four wrong and either this story balloons into Story 4.2/4.3/4.4's work, or a later story's own AC (e.g. Story 4.2's `m`/`/` keys, Story 4.4's `:bots`) turns out to have no scaffolding to attach to.

### Four scope-boundary judgment calls — read before writing code

1. **No OFI/OBI/microprice/spread columns on the Coins pane in this story.** `mockups/key-coins-pane.html`'s "normal / at rest" state shows `vol24h`, `ofi(10)`, `obi(10)`, `microprice`, `spread` columns per row. This story's actual AC2 text only requires "the ranked coin list read live from `rankings:live`" — and `rankings:live`'s wire schema (`ARCHITECTURE-SPINE.md` AD-9/Consistency Conventions) carries only `{instrument_id, rank, volume24h, volatility_score}`. Rendering the indicator columns would require a *second* live data source (`snapshots:raw` + `ml_signals.indicators`' `Microprice`/`MultiLevelOFI`/`MultiLevelOBI` classes) that neither this story's AC list nor `EXPERIENCE.md`'s behavioral "Component Patterns" table for the Coins-pane list row actually specifies ("One row per ranked coin, sorted by the active Ranking Mode... Row order never re-sorts locally" — no mention of indicator columns). `EXPERIENCE.md`'s own Information Architecture section states explicitly: **"Spine tables remain the contract; mocks illustrate."** The mockup is one concrete illustrative rendering of the *finished* Coins pane (post-Epic-4), not a per-story scope spec. The architecture spine's own citation of where `bot_tui` uses `ml_signals.indicators` is scoped to Coin-detail (FR-20, Story 4.3): "`bot_tui` imports `ml_signals.indicators` directly for its per-coin live-indicator view" — the live-indicator *view* is Coin-detail, not the Coins pane list. This is exactly what the story's own framing ("a working, navigable foothold to build every other view on top of") describes.
3. **Only cold-open, not post-heartbeat-loss staleness.** AC5 covers exactly one state: no message has *ever* arrived (`_LATEST_RANKING is None`). ### Testing strategy: pure logic vs. urwid wiring

This codebase has zero existing precedent for testing a real `urwid.MainLoop`/screen (there is no prior TUI anywhere in `troll/`), and there's no reasonable way to unit-test actual terminal rendering without a fake terminal harness this project doesn't have and doesn't need. The design in Tasks 2–4 above deliberately separates **pure, side-effect-free logic** (message validation, row extraction, command parsing, view-stack pop-back — all plain functions over dicts/strings/lists, zero `urwid` imports) from the **thin `urwid` wiring layer** (`app.py` — widget construction, `MainLoop`, the async event loop glue) that wraps it. Every behavioral claim in AC1–5 that *can* be expressed as a pure function is tested directly (mirrors this project's existing pattern of testing `dashboard.py`'s `_rankings_json`/`_merged_rows` as pure functions while never unit-testing `aiohttp`'s actual HTTP routing). The one thing that genuinely can't be verified this way — that the screen actually redraws when a background Redis message arrives — is called out explicitly in Task 6 as a manual smoke-check, not silently skipped.

### `urwid` asyncio integration — confirmed pattern, cite before deviating

Per `urwid`'s own documentation (Main Loop / Event Loops, urwid.org, fetched during this story's research): `evl = urwid.AsyncioEventLoop(loop=asyncio.get_event_loop())`, then `urwid.MainLoop(widget, event_loop=evl)`. The same source states explicitly: *"If you make any changes to the urwid state outside of it handling input or responding to alarms (for example, from `asyncio.Task` running in background), and wish the screen to be redrawn, you must call `MainLoop.draw_screen()` manually."* This is the exact mechanism Task 4 depends on — get it wrong (or skip it) and the Coins pane will look correct on first paint but freeze silently thereafter, a bug that a rushed manual check could easily miss since the *first* render (built from whatever `_LATEST_RANKING` already held) can look fine even when subsequent updates never reach the screen.

### Why bot_tui gets its own Redis connection, never dashboard's or ranking_engine's

`bot_tui`, `ml_signals.dashboard`, and `ranking_engine` are three separate OS processes/containers (per `ARCHITECTURE-SPINE.md`'s Structural Seed and Deployment sections) — none can share an in-process pub/sub subscription with another. This is the identical reasoning `ranking_engine`'s own Dev Notes (Story 1.8) already established for why it needs its own `snapshots:raw` subscriber rather than piggybacking on `dashboard.py`'s; it applies unchanged to `bot_tui` needing its own `rankings:live` subscriber here.

### Module boundary (AD-4/AD-9) — restated for this story

`bot_tui` is a pure reader/client of `rankings:live` (AD-9) — it must never recompute rank, volume24h, or volatility_score locally, and it never imports `ranking_engine.engine`'s internals (its live `_LAST_SEEN`/`_ACTIVE_MODE` state, its Redis subscriber tasks). The only sanctioned cross-namespace surface `bot_tui` may ever touch is (a) the `rankings:live`/`ranking:control` Redis channels themselves (live path, this story) and (b) `ml_signals.indicators`' pure Indicator classes (Coin-detail, Story 4.3 — not used anywhere in this story). `bot_tui`'s only future path to `live_paper`'s trading runtime is the `bots:status`/`bots:control` Redis channels (AD-10, Story 4.4+) — never a direct import of `live_paper` internals.
