# platform/ Working Rules

These rules govern all code under `platform/`: the contexts (`capture/` with its venue packages
`capture/venues/{dydx,bybit,hyperliquid}/` -- Story 26.2; the migration's last re-export shims
were deleted in Story 26.3 --, `kernel/`,
`observability/`, `candles/`, `archive/`, `views/`, `alerting/`, `research/`, `ranking/`, `bots/`, `collection_control/`, `verification/` -- the independent reference side of Epic 31, which never imports the code it checks, Story 31.1; its one exception is `verification/subject/`, the code under test the catalog tool drives (`ParquetDataCatalog`, `BacktestNode`, the archive's consolidation), imported only by `verification.catalog`, Story 31.7), `data_api/` +
`frontend/` and `bot_tui/`.
`nautilus_trader` is consumed as a library only — never as a live runtime — in all of
them. **Exception:** `platform/bots/` (the bots context, `python3 -m bots`; its own context
since Story 25.3) is a separate, structurally isolated context (architecture spine's AD-8 amendment,
DDD spine AD-D15) where `TradingNode`/`Strategy` usage is sanctioned — it is the one place in
`platform/` this file's `TradingNode`/`DataEngine` ban does not apply, and inside it only
`bots/infrastructure/nautilus_host.py` imports `TradingNode` (`platform/tests/test_boundaries.py`
fails any other importer, tests included). See `platform/bots/infrastructure/nautilus_host.py`'s
and `platform/bots/__init__.py`'s module docstrings for the full rationale `[amended 2026-09-26: Story 25.3]`.

## Operator Actions (VPS and other manual steps)

- **OPS-01: A story never parks `awaiting-operator`.** Any step only a human can do (a VPS deploy
  or redeploy, a crontab or `.env` change, a one-off migration or recompress run, a profiling
  session, a live-trading check) is appended to `docs/DEPLOY_CHECKLIST.md`'s "Deferred operator
  actions" section as one entry headed with the story key and commit, as unchecked `- [ ]` items,
  and the story finalizes `done` through the normal review path. Never write `operator_actions:`
  frontmatter or set `awaiting-operator`. Why: the operator batches VPS work at deploy time, a
  park stops nothing but still skips bmad-loop's independent review session, and a later story
  must never wait on a manual step (use the best available evidence and record what is owed).

## Fork Safety

- **FORK-01** — Never modify `nautilus_trader/` or `crates/`. All `platform/` code is additive-only. The fork must stay untouched so upstream merges remain possible.
- **FORK-02** — `nautilus_trader` is a library here: use its domain types (`Price`, `Quantity`, `InstrumentId`, …) and `ParquetDataCatalog.write_data()`. Never instantiate `TradingNode` or `DataEngine` in any `platform/` module. **Why:** the live `DataEngine` has a documented unbounded-queue-growth + shutdown-wedge bug under sustained high-message-load that OOM-crashed the earlier `Strategy`/`TradingNode`-based recorder on the `gg` branch. **Does not apply to `bots/`** (Story 25.3) — that context's entire purpose is running an actual (paper or, behind an explicit separate gate, real) trading strategy via `TradingNode`, which AD-8 explicitly carves out as a distinct, sanctioned usage from the recorder-misuse this rule prevents.

## Network Security

- **SEC-01** — **Every Docker port is localhost-only. No exceptions, ever.** `ports:` entries must be `"127.0.0.1:HOST:CONTAINER"` — never a bare `"HOST:CONTAINER"`/`"PORT"` (that publishes to `0.0.0.0`). If a service needs no host access at all, use `expose:` instead of `ports:`, or nothing. Remote access is via SSH tunnel (`ssh -L`) only, never a publicly reachable port — including reverse proxies. **Why:** Docker inserts its own `iptables` `ACCEPT` rules ahead of ufw's chain, so a bare port mapping is reachable from the public internet even with `ufw deny <port>`/`ufw default deny incoming` active — ufw never sees the connection, since Docker never routes it through ufw's INPUT chain. Enforced unconditionally by the `check-docker-port-binding` pre-commit hook (`.pre-commit-hooks/check_docker_port_binding.sh`) — no escape-comment override. `platform/docker-compose.yml`'s services already follow this: `redis`/`dozzle` bind `127.0.0.1:PORT:PORT`; `collector`/`bybit_collector`/`hyperliquid_collector` `[amended 2026-09-20: Epic 22 story 22.8, review pass — the two Epic 22 collector services were missing from this enumeration; `platform/docker-compose.yml:83`/`:106`]`/`data_api`/`ranking_engine`/`bot_tui`/`live-paper` use `network_mode: host` with the app itself binding `127.0.0.1` (e.g. `data_api`'s `uvicorn --host 127.0.0.1`) instead of a `ports:` mapping.

## Data Integrity

- **DATA-01** — **Correct data is the #1 priority. Never display stale or fabricated values as live market data.** If data is genuinely unavailable (e.g., during WS reconnect recovery when the Rust client re-subscribes instruments at 2/sec), the gap must be flagged visually rather than papered over with a flatline. **Implementation:** the per-second gate `capture/domain/sampler.py`'s `SecondSampler.sample` (run by `CaptureService._sample_tick`, called by `_second_loop`; the four checks are `LiveBook.snapshot_top`, `capture/domain/live_book.py`) `[amended 2026-09-26: Story 26.1]` uses `config.stale_book_seconds` to skip snapshot emission when no `OrderBookDeltas` have arrived for an instrument — 5 s is only `CoreConfig`'s default, and is set per venue from measured push cadence through the one venue loader, `capture.infrastructure.config.load_venue_config` — Hyperliquid runs 12 s (its `VENUE_SCHEMAS` default, `capture/venues/hyperliquid/config.py`'s `STALE_BOOK_SECONDS`, justified in its `config.toml`). Since Story 25.4 dYdX's `config.toml` goes through that same loader too, so every core threshold set there (`stale_book_seconds`, `crossed_resync_seconds`, `stale_trade_seconds`, `seen_trade_ids`, `feed_stale_seconds`, `book_crosscheck_seconds`) is honoured, an unknown key refuses start, and `trade_feeds` other than 1 refuses start (dYdX's client opens one trade feed); before it, dYdX's older key-by-key loader (in the dYdX collector's own config module) ignored them all silently `[amended 2026-09-26: Story 25.4]`; `views/chart_series.py` breaks the Lines-mode series at timestamp gaps > `SNAPSHOT_GAP_THRESHOLD_MS` (2500 ms) so the chart renders an honest gap instead of a misleading horizontal line -- a *rendering* rule; the reader never re-validates a row the gate wrote (a crossed second renders, an empty-top second fails its request loudly, Story 24.2) `[amended 2026-09-25: Story 24.2 -- moved from `data_api/routes/snapshots.py`, whose reader-side skips were deleted]`. When adding new data sources or display paths, apply the same principle: skip or flag, never silently perpetuate stale state. **Two clocks** (story 22.13): every archived `TradeTick` keeps `ts_event` (the venue's trade time) and `ts_init` (our receive time) untouched -- aggregates bucket on `ts_event` (the nightly `rebuild_seconds`), backtests replay on `ts_init`; the live 1 s snapshot is provisional until its day is rebuilt and reconciled (`verified_days`). It is arrival-timed on dYdX (its book deltas carry no venue time, audit D-49) and exchange-timed on Bybit/Hyperliquid (`book_time_source = "venue"`, story 22.12): second `S` closes at wall `S + 1 + hold_back_seconds` from the deltas with `ts_event < S+1` and the trades with `ts_event` in `[S, S+1)`, stamped `ts_event = S + 0.5 s`, `ts_init` = when it was sampled; a trade arriving after its second closed is archived and counted (`collector.late_trade`), never folded live -- the rebuild places it. Anything judging liveness (watchdog, `ranking_engine` freshness) compares arrival, never a row's `ts_event`.

- **DATA-02** — **No mysteries in data ingestion. Maximum assurance that ingested data is correct and lossless is non-negotiable — this is the most critical part of the system.** When ingestion produces wrong or missing data (a desynced book, a dropped message, a stale value), detecting it fast and recovering automatically is necessary but is **never sufficient on its own** — treating fast recovery as "solved" is symptom treatment, not a fix. The investigation is not done until the exact mechanism is known. No guessing, no stopping at "probably the venue's fault" or "probably fine now" without hard evidence.
  - **Standard of proof:** rule out hypotheses with real evidence, not code-reading alone. Cross-check against an independent source of truth before concluding anything — e.g. the venue's own REST API, or a second independent client with zero shared code path with our pipeline (both used in production to prove a local order-book desync was real and not venue-side crossing).
  - **The reference never shares code with what it checks** (`verification/`, Epic 31): the oracle side imports no `nautilus_pyo3`, `capture`, `candles`, `ranking`, `views`, `kernel.fold`, `kernel.second_snapshot`, `kernel.open_interest` or `kernel.catalog_files`, however deep. **One exception, `verification.subject` (Story 31.7):** a check whose subject *is* a reader or writer (every file opening through `ParquetDataCatalog`, the archive's own consolidation, a `BacktestNode`) drives it from that package, the only non-test verification code that may import `nautilus_trader`, `kernel.second_snapshot`, `kernel.open_interest` and archive consolidation; it may import `verification.domain` (one row digest for both sides), is imported only by the `verification.catalog` root, reaches no `capture`/`candles`/`ranking`/`views`/`research`/`bots`, and the oracle never imports it -- the stored side is read raw, the reader's objects are re-encoded by the subject and digested alike (`tests/test_boundaries.py`, including a runtime probe that the oracle modules load no `nautilus_trader`; `docs/DATA_DICTIONARY.md` §1.20) `[amended 2026-09-29: Story 31.7]`.
  - **Close observability gaps permanently, don't patch around them.** If a whole class of failure was invisible for lack of instrumentation (e.g. Rust-side `log::error!`/`warn!` calls being silently dropped because `nautilus_pyo3.init_logging()` was never called in a standalone script that doesn't go through `TradingNode`/Kernel startup), fix that gap once, permanently — don't work around not being able to see the failure.
  - **A staleness/health canary on your own detection loop is required, not optional**, wherever a detection-and-recovery mechanism depends on a periodic check running promptly (e.g. `_second_loop`'s wall-clock tick-lag warning) — otherwise the safety net's own reliability becomes exactly the kind of invisible failure this rule exists to prevent.
  - **Only two acceptable end states for an ingestion-correctness question:** (1) the exact mechanism is identified, and either fixed or proven — with hard, independently-verified evidence — to be outside our control (e.g. genuinely lost upstream of our client); or (2) it is still genuinely open, and must be labeled and tracked as such, never quietly treated as resolved just because the visible symptom got smaller, quieter, or faster to recover from.

- **DATA-03** — **A forced resync (unsubscribe/resubscribe to force a fresh snapshot, the core's `CaptureService._resync` (`capture/application/capture_service.py`), which executes a `ResyncRequested` the venue's `CrossedBookPolicy` returned or a resync queued on the `LiveBook` (`resync_pending`: a `SequenceCanary` break, a pending-delta overflow, a failed or lock-deferred resync) -- every venue's since Story 26.1, which folded dYdX's own `_resync_book` into it `[amended 2026-09-26: Story 26.1]`) is a destructive, worst-case recovery — never a fix, and never evidence the underlying problem is understood or solved.** It throws away local state and rebuilds from scratch, which hides the actual data loss it's papering over (during the resync window that instrument has no book at all) and, if triggered often, indicates the root cause is still live and recurring, not resolved. Every forced resync is ledgered `collector.resync` (dYdX's too since Story 26.1). Treat a high or rising forced-resync rate as an open DATA-02 incident, not as "the safety net is working." Prefer a resync-avoiding fix at the actual loss point over tuning the resync trigger (the threshold is now the config field `CoreConfig.crossed_resync_seconds` in `capture/application/config.py`, read by the crossed-book policies; it was the module constant `_CROSSED_RESYNC_NS` before story 22.2 moved it) tighter/looser — tuning the trigger changes how fast the worst case is reached, not whether it's needed.

- **DATA-04** — **A crossed dYdX v4 orderbook is expected, architectural, and unpreventable by any client — confirmed via dYdX's own official docs and Indexer source, not inference.** dYdX v4 has no centralized orderbook: each validator holds its own in-memory, off-chain, pre-consensus book, matched against whichever block proposer's mempool is currently active (rotates every block). dYdX's own integration guide states outright that a client cannot prevent seeing a crossed book. Treat a crossed book as a normal, expected condition to correct — not a symptom that, absent other evidence, implies a local pipeline bug (contrast with DATA-02's standard, which still applies to a book that *never* uncrosses at all — see below).
  - **The correct resolution is dYdX's own, from its Indexer's `Roundtable` service (`uncross-orderbook.ts`), not a full resync:** tag every price level, when applied, with the message-id of whichever WS update last touched it (dYdX's own docs: `OrderBookDelta.sequence`/the WS envelope's connection-global `message_id`, applied **per price level**, not per-instrument — a different, valid use of the same field the per-instrument gap-detection removal in commit `944891bbba` correctly ruled out). When crossed, delete only the level with the older message-id (loop until uncrossed), via a synthetic `BookAction.DELETE` — never wipe the whole book for this. Implemented as the policy values `capture/venues/dydx/policies.py`'s `DydxLevelTagger` and `DydxUncrossPolicy` (was `uncross.py` plus two `DydxCollector` hook overrides), run by the core's `LiveBook`; a one-sided book left by an uncross is an empty top of book and writes no row `[amended 2026-09-26: Story 26.1]`.
  - **Forced resync (DATA-03) is a fallback only** — for when a level can't be tagged (e.g. immediately after a resubscribe) or a book stays crossed for far longer than active uncrossing should ever take. It is not the first response to an ordinary crossed book.
  - See `_bmad-output/planning-artifacts/research/technical-dydx-v4-orderbook-crossing-resolution-research-2026-09-06.md` for full sourcing (dYdX docs + Indexer source + this repo's own wire captures).

- **DATA-05** — **No data loss, where it can be prevented. Never accept a silent gap as "small" or "just a cache."** This covers derived data too (the SQLite candle store, `candles/infrastructure/sqlite_store.py`): a missing second understates the bar built from it, so it counts. Any seam that can drop data (restart, shutdown, chunk/range boundary, a failed write) must be closed by design or have a documented, tested way to fill it. A loss that genuinely can't be prevented must be named explicitly, with how to detect and repair it -- never left implicit. **Why / how it is closed:** raw 1s snapshots in Parquet are the ground truth; the store is derived from them and applies each second exactly once (per-instrument watermark), so a restart just means fewer observed seconds in that bucket (`seconds_observed`, and `partial` when under 90% of the span) -- there is no minute-close seam. A failed store write is loud (`collector.candle_store` in the error ledger) and is repaired by `python -m candles.rebuild`, which recomputes whole UTC days from raw 1s and is idempotent. Story 24.1's `SecondSink.apply` commits per instrument, so one instrument's failure no longer discards the flush -- but the *ledger* line is still one per flush, naming every instrument that failed, every distinct exception type with how many instruments it hit, and carrying the traceback of whichever cause hit the most; one line per instrument would exceed the 60-lines-per-site-per-minute write cap exactly during the store-wide fault whose detail matters most. A mis-wired venue that injects no sink at all is `collector.no_second_sink`, recorded once per start. Open edges, by design: the store can hold up to ~30 s the archive lost after a crash (a rebuild of that day drops them), and a hole filled into the archive later reaches the store only through `candles.rebuild`. **A live-fold error is filled by the rebuild, never patched at read time** (story 22.13): raw trades are archived (`data/trade_tick/`), and `python -m archive.rebuild_seconds --day D --apply` re-derives a closed day's snapshot trade columns from them with the same exact fold (`kernel/fold.py`), then `python -m candles.rebuild --day D` refolds the store and `archive.compare_klines` proves the day against the venue's klines -- all chained by `make nightly VENUE=...`, the `archive.nightly` saga, which carries the rebuild's proof to the reconcile (`--rebuilt-by`: a day the run did not rebuild is never judged, `reconcile.not_rebuilt`) `[amended 2026-09-25: Story 25.1 -- the archive tools moved from the collector core to the `archive/` context]`. **The one place this maintenance is scheduled is the compose service `archive`** (`python -m archive.scheduler`, `archive/application/scheduler.py`; no host crontab): every night it runs each venue's saga for every missed closed day (per-venue watermark in `data/archive/state.json`, a scheduler cursor that is never a day status -- `verified_days` is), then `consolidate_catalog`, then `archive.backup_catalog` when `archive/config.toml`'s `backup_enabled` is true (off until off-site storage exists: one start WARNING and `"backup": "disabled"` in `archive:status`, never a nightly failure; enabled without an rclone target refuses start) `[amended 2026-09-26: Story 26.1b]`, and every `intraday_consolidate_hours` it merges the current day's closed hours of the small types; a reboot or redeploy no longer loses a night, and `archive:status` shows each step's exit. `make nightly`/`consolidate`/`backup-catalog` stay as manual tools `[amended 2026-09-26: Story 25.1b]`. Rows inside an archive-gap marker keep their live values and are counted `in gap`; archive never changes a row of the current UTC day (a whole-file write, merge or delete of a file reaching it is refused; the rebuild may rewrite such a file -- the midnight-crossing one, or one starting after midnight that holds yesterday's last rows -- only with every open-day row verified identical, `RewriteMode.KEEP_OPEN_DAY_ROWS`), and every in-place rewrite is `CatalogFiles.rewrite` (verified temp-then-rename). Every file archive writes itself (merges, the rebuild, migrations, `archive.tools.recompress`; not `archive.backfill_bars`/`archive.repair_catalog`, which write through Nautilus's `write_data` and keep its encoding) takes its Parquet write options from the one function `archive.infrastructure.compact_parquet.compact_write_options` (zstd 16, delta-packed timestamps, dictionary leaves, capped row groups with statistics), and the rewrite's read-back verification compares every value in order before the rename `[amended 2026-09-29: Story 30.1]`. Trades that had no sampled second (collector not sampling) are counted as orphans, never dropped silently. Minute rollups no longer exist (retired 2026-09-20; see `docs/DATA_INTEGRITY_AUDIT.md` D-35).

- **DATA-06** — **Never count venue-replayed history as live data, and never store a price the same second's book cannot contain.** dYdX's `v4_trades` subscribed reply carries up to 1000 historical trades; counting them as live created fake ~$850-range, ~21 BTC candles after every (re)subscribe (proven against the raw indexer feed). Any new channel must be checked for a subscribe-time snapshot/replay before its rows are treated as live. Guards: the `stale_trade_seconds` age filter + per-instrument `trade_id` dedup (`seen_trade_ids`), both configured in `capture/application/config.py` and applied by `capture/domain/trade_intake.py`'s `TradeIntake.accept` (from `CaptureService._process_data`) `[amended 2026-09-26: Story 26.1]`. Age is judged on arrival, `ts_init - ts_event` (the Rust receipt stamp), never at processing time: an ingest backlog must not turn live trades into history (a 15 s stall dropped all 573 trades of a recorded Bybit burst, audit D-70). Stale drops are ledgered once per flush (`collector.stale_trade`) and recorded as coverage `trades_dropped`. The dedup window is time-bounded: an id leaves only when the window is over `seen_trade_ids` **and** it is older than `DEDUP_HORIZON_NS` (`MAX_TS_INIT_SKEW_NS` + `READ_SPAN_MARGIN_NS`). At start the window is seeded from the archive's own trades over that horizon (first feed `archive`), so neither eviction nor a restart can archive an id twice (D-72) `[amended 2026-09-29: Story 31.2]`. Also guarded by `kernel.second_snapshot.ohlc_outside_book` (trade high/low must lie inside that second's own top-20 book range), which serves as both a live canary (ledgered per occurrence at `collector.ohlc_outside_book` since Story 31.2, with the row kept) and the detector for `archive.repair_catalog` `[amended 2026-09-25: Story 25.1 -- moved from the collector core's integrity module]`. **Reconnect gaps and duplicate classes** (story 22.14): the dedup map remembers which feed (WS connection) delivered each id first -- a repeat from the *same* feed is a replay (`duplicate`; after the startup grace it is also a reconnect signal), from *another* feed or the REST backfill source `rest` it is `duplicate_feed` (the dual-feed union, `trade_feeds = 2`); both are counted each flush, never folded twice. Trades a reconnect missed are recovered over REST by each venue's `capture/venues/<venue>/trade_history.py` (`ports.VenueTradeHistory`, scheduled by the `CaptureService` from `FeedGroup` requests) `[amended 2026-09-26: Story 26.1]` (one `collector.trade_backfill` ledger entry per reconnect), archived only -- never folded into the live second -- and never older than the 300 s `kernel.clocks.MAX_TS_INIT_SKEW_NS` the rebuild depends on; what the venue's depth cannot cover is reported `unrecoverable`, never silent (`docs/DATA_DICTIONARY.md` §1.1 capability table). When wrong rows already exist, repair with `python -m archive.repair_catalog` (report first, `--apply` after a backup and with that venue's collector stopped -- it refuses, `repair.capture_running`, while the collector holds `<catalog>/.capture-<VENUE>.lock`) rather than hiding them at read time. The nightly rebuild that re-derives a closed day's trade columns from the raw archive is scheduled only by the `archive` service (DATA-05), which never takes a capture lock: its steps write closed days and closed hours only `[amended 2026-09-26: Story 25.1b]`. The full register of known wrong-data dangers, with status, is `platform/docs/DATA_INTEGRITY_AUDIT.md` — add every new one there.
- **DATA-07** — **Never filter, drop, clamp, mute or hide an error that malfunctioning code caused. Find the malfunction and fix it.** A validator that discards a bad candle, a read-time guard that skips bad rows, a log filter that mutes a noisy error, a retry/restart that papers over a crash — each is a symptom treatment that leaves the bug live and the data (or the process) still wrong. Checks are allowed only as **loud canaries** (ERROR log + counter + visible in the UI/audit) that *prove* the fix holds; they never replace it, and they must not silently change what the operator sees. Filtering is legitimate only for input that is not a fault of ours — e.g. classifying a venue's documented subscribe-time replay (DATA-06) — and that classification must itself be evidenced. **Specifically: no OOM kills.** The collector being OOM-killed (audit D-06) is a bug to fix at its cause (unbounded queue/buffer growth, oversubscribed host), never something to live with because restarts are handled by backfill or dedup. A restart-tolerant pipeline does not make a crash-looping one acceptable. **Mechanism:** every site that must continue past a failure calls `observability.error_ledger.record(site, detail, exc)` (ERROR + traceback + per-site count; the generic `observability/` context, standard library only, that every context except `kernel` may import -- Story 23.1 moved it into that context, and Story 24.1 deleted the re-export shim that stood in for it at its old path); `GET /api/errors` exposes the counts and the frontend's non-dismissible `<ErrorBar>` shows them together with every browser `console.error`/uncaught error, so a failure is visible without reading Dozzle. Outbound notification goes through the one transport `observability.notify(channel, title, body)` (ntfy, Telegram, webhook), whose failed sends are themselves ledgered (`observability.notify.<transport>`), never logged-and-forgotten. **Durable per service (Story 23.3):** besides the in-memory count, `record()` appends one JSON line (`ts_ns`, `service`, `pid`, `site`, `detail`, `exc_type`, `suppressed`) to `<ERROR_LEDGER_DIR>/<ERROR_LEDGER_SERVICE>.jsonl` when `ERROR_LEDGER_DIR` is set (`docker-compose.yml` sets it to the shared `./data/errors:/app/errors_dir` mount for all eight services calling `record()`: `collector`, `bybit_collector`, `hyperliquid_collector`, `archive` `[amended 2026-09-26: Story 25.1b]`, `ranking_engine`, `data_api`, `live-paper`, `bot_tui`), so a day's failures survive a restart, an image rebuild or Redis loss (Redis here has no volume and `appendonly no`, on purpose). Each process writes a `process_start` line via `observability.error_ledger.start()` at boot, so a reader can tell a zero-error window from a restarted one. `GET /api/errors`'s `services` block reads every service's file back (per-site counts since its last restart and since an optional `?since_ns=`); `python3 -m archive.crosscheck_errors` cross-checks a whole window's ledgers against the archived catalog's own gaps (`platform/docs/DEPLOY_CHECKLIST.md` §6). **Known limit:** the write cap (`ERROR_LEDGER_MAX_LINES_PER_SITE_PER_MIN`, default 60/site/minute, with a `suppressed` carry that is exact over a whole file set, and approximate at a bounded window's edge because it is stamped with the reporting line's time, not the storm's — upgrade path: carry the bucket's start timestamp once the frozen line schema can take a version-detectable field) and size rotation (`ERROR_LEDGER_MAX_BYTES` per file, `ERROR_LEDGER_BACKUP_COUNT` *backups* kept alongside the live file, default 20 MB and 10 backups — 11 files retained — mirroring the compose `x-logging` policy) mean a sustained storm can still age a day's lines out of the window before anyone reads them; and the in-memory `counts()` the `<ErrorBar>` polls is still only `data_api`'s own process. Upgrade path: raise the two env vars, or ship the files to object storage alongside the catalog backup (story 22.11's rclone remote); for *live* cross-process visibility, the `errors:ledger` Redis channel (`observability/infrastructure/redis_ledger.py`, DDD spine AD-D16) that `/api/errors` aggregates. A bare `logger.warning(...); continue` at a data-dropping site is not acceptable. `tests/test_boundaries.py::test_no_capture_site_logs_quietly_and_skips` enforces this for non-test `capture/`: it fails any `logger.warning/debug(...)` directly followed by `continue`/`return`. **Explainable, not just counted:** every second without a snapshot row and every trade dropped, backfilled or unrecoverable is written to the durable coverage record `<catalog>/../coverage/<venue>.jsonl` (`capture/domain/coverage.py`, append + fsync per flush). `python3 -m verification.conservation --venue V --day D` reconciles the reference recorder's trade ids and all 86 400 seconds against the archive, that record and the gap markers. Unexplained must be 0 (`docs/DATA_DICTIONARY.md` §1.16) `[amended 2026-09-29: Story 31.2]`. `python3 -m verification.trades --venue V --day D --stage live|rebuilt` goes further: every archived trade's price, size, side and `ts_event` equal the venue's, and every second's eight trade columns equal the reference's own fold, with no tolerance (`docs/DATA_DICTIONARY.md` §1.17) `[amended 2026-09-29: Story 31.4]`. **How to apply:** when you find yourself writing `if bad: skip/drop/None`, stop and trace where `bad` is produced; when a symptom is muted, the story is not done until the producer is fixed and the audit register (`docs/DATA_INTEGRITY_AUDIT.md`) says so; when a fix is not possible in this session, register it OPEN — never present a filter as the fix.

- **DATA-08** — **A venue's book "sequence" field means something different at every venue — never gap-check one without that venue's own evidence.** The same-looking `OrderBookDelta.sequence`/update-id is three different things across the three venues collected here: dYdX's is the WebSocket envelope's **connection-global `message_id`**, shared by subscribe-acks and every other market on that connection, so per-instrument gap-detection false-positives on essentially every message once more than a handful of instruments share the socket (removed in commit `944891bbba`; the reasoning is in `platform/capture/venues/dydx/policies.py`'s `DydxLevelTagger` docstring `[amended 2026-09-26: Story 26.1]`, and the same field is still legitimately used *per price level* for DATA-04 uncrossing). Bybit's `u` **is** a genuine per-topic sequence, measured contiguous in a healthy stream (31,860 of 31,860 steps exactly +1 over an 800 s BTCUSDT capture), so a gap or a regress is real message loss/reordering — used as a canary by `capture/venues/bybit/policies.py`'s `BybitSequenceCanary` (`sequence_verdict`/`message_u`), run inside the core's `LiveBook.apply`; the core ledgers `collector.book_sequence`, drops the book and queues a resync `[amended 2026-09-26: Story 26.1]`. **Carry that evidence's scope with it:** D-41 measured one instrument on one topic (`BTCUSDT` linear `orderbook.50`); Story 31.5's reference recorder then measured every collected topic, **spot included** (its `orderbook.50` *delta* frames over 2026-09-29 12:59:19-16:12Z): linear BTC/ETH 481,524 / 507,908 and spot BTC/ETH 403,606 / 312,005, each after one snapshot, `u` exactly +1 at every step, 0 breaks, 0 `seq` regressions, 0 `collector.book_sequence` entries -- so a spot `u` break is lost or reordered messages too (audit D-98), and `python3 -m verification.book` re-measures it daily (`u_breaks`, `docs/DATA_DICTIONARY.md` §1.18). The canary has two deliberate no-verdict cases: it returns `ok` when there is no baseline yet (`last_u is None`) and re-baselines on a snapshot or `u == 1`, so the first messages after a connect or a resync are not gap-checked. **Zero levels, corrected with the Rust evidence (audit D-96):** a zero-level *delta* never reaches Python -- `parse_orderbook_deltas` yields an empty vector, `OrderBookDeltas::new_checked` refuses it (`crates/model/src/data/deltas.rs:88`) and the Bybit client only `log::error!`s the failure (`crates/adapters/bybit/src/python/websocket.rs` ~1416) -- so its `u` is simply missing and the next delta reads as a gap: a `collector.book_sequence` entry and a DATA-03 resync for a message that carried no change. That is a `Known limit:` (FORK-01: not fixable this side of the bindings; loud, never silent; measured **0** zero-level deltas on the wire over the window above; upgrade path: the adapter forwards an empty sequenced message). A zero-level *snapshot* does reach Python, as a lone `Clear` with no `u` to read (`message_u` None); `LiveBook._check_sequence` used to return before re-baselining it, keeping the old `u` so the venue's next delta read as a gap -- fixed: a snapshot always resets `last_u` (`capture/domain/live_book.py`). The REST book cross-check's blind spot (a level the live book lost below the best read as agreeing) is closed too: `capture/application/book_check.py`'s `top_levels_mismatch` also reports REST levels absent from live, with the tolerance applied per direction, the same count each way (audit D-97) `[amended 2026-09-29: Story 31.5]`. Hyperliquid sends a **full authoritative snapshot** every message and keeps no sequence bookkeeping at all, so there is nothing to gap-check and no `resync_orderbook` on its client; but its first `l2Book` after a (re)subscribe is a reply to that connection only, off the broadcast cadence, so two clients can briefly hold different books (audit D-101) `[amended 2026-09-29: Story 31.5]`. **Rule:** before wiring any sequence/update-id check for a new venue, capture that venue's own raw frames and show what the field actually counts — never port another venue's interpretation, and never assume the absence of a check is an oversight. Evidence: stories 22.2, 22.5 and 31.5; `docs/DATA_INTEGRITY_AUDIT.md` D-41, D-96..D-98, D-101.

## Observability Rules

- **OBS-01** — **Zero book updates across N liquid instruments is a failure mode, not market behavior.** BTC/ETH/SOL perpetuals trade 24/7. If `buy_count == 0` and `sell_count == 0` and bid prices are frozen for all subscribed instruments for more than 30 seconds, the data pipeline has failed — diagnose it, do not accept it as "quiet market." Root cause seen in production: (a) `classify_liquidity` using `openInterest` (token units) instead of `volume24H` (USD), causing BTC=458 tokens to fail a `>= 100_000 USD` threshold; (b) `_bar_builder._books` only updated every 60s at flush time, making `_second_loop` read a 60-snapshot-old book. `_second_loop` now lives in the shared core as `capture.application.capture_service.CaptureService._second_loop` (with the gate it calls, `_sample_tick` -> `SecondSampler.sample` `[amended 2026-09-26: Story 26.1]`), run unchanged for every venue (no venue subclasses the service, Story 26.2); `_bar_builder` no longer exists at all — minute rollups were retired 2026-09-20 (`docs/DATA_INTEGRITY_AUDIT.md` D-35), so (b)'s mechanism is gone rather than moved `[amended 2026-09-20: Epic 22 story 22.8, review pass — the earlier wording said "both loops now live in the shared core", which implied a deleted symbol had been relocated]`.
- **OBS-02** — **OFI z-score changing while price is frozen does NOT prove the data pipeline is healthy.** The OFI z-score is a rolling 3600-point window mean/std — it evolves as historical values age off even when current OFI input is zero. A changing z-score with a frozen price is consistent with a dead book feed. Check `buy_count`, `sell_count`, and raw bid/ask changes across consecutive snapshots, not derived indicators.
- **OBS-03** — **Liquidity classification must use volume (USD), not open interest (tokens).** `openInterest` from dYdX's indexer is in base-token units. BTC at 458 tokens looks "illiquid" against a $100k threshold. Always classify by `volume24H` (already USD) or by `openInterest × oraclePrice`. The config key `liquidity_min_oi_usd` means "minimum USD liquidity" — enforce it with a USD-denominated field.

## Design Principles

- **DESIGN-01** — **No abstraction without a named invariant.** A class, aggregate, port, interface, factory or config value is admitted only if its docstring names the specific invariant it protects and the commands that could violate it; anything that cannot state one stays a plain function or dataclass. No scaffolding for hypothetical future use. Ports are `typing.Protocol`, wired explicitly at composition roots; no DI container, no event-bus library. **Why:** this is how the DDD spine (`_bmad-output/planning-artifacts/architecture/architecture-ddd-platform-2026-09-21/`, AD-D4) keeps tactical patterns from becoming ceremony — `LiveBook` earns its place by naming "a delta applies at most once, only after a baseline"; a `RankChanged` event nothing consumes does not. Replaced the earlier YAGNI wording on 2026-09-21.
- **DESIGN-02** — Decouple at natural seams: `collector` / `book_features` / strategy / backtest. Components depend on shared data types, not each other's internals. Never import a collector class from a strategy file.
- **DESIGN-03** — Prefer deletion over addition when simplification is possible. Prefer boring over clever. A function you can read in 10 seconds is better than one that needs a comment.

## Adding a venue

A venue is one package, `capture/venues/<v>/`, of named files wired into the one `capture.application.capture_service.CaptureService` -- no new gate, no new loop, no service edit, and **never a subclass**: `platform/tests/test_boundaries.py` fails any class anywhere in `platform/` deriving from `CaptureService` (or its old name `Collector`), so venue variance is policy values and composition-root loops only `[amended 2026-09-28: Story 26.2 -- was a `<venue>_collector/` package holding a `Collector` subclass]`. `capture/venues/hyperliquid/` is the smallest whole reference; `bybit/` adds policies and a REST poll; `dydx/` adds a liquidity-pinned, capped plan (every venue wires the control plane since Story 29.4) `[amended 2026-09-28: Story 29.4]`.

1. **Investigate the wire behaviour first, before deciding which policy values and loops the venue needs.** Read that venue's adapter under `crates/adapters/<venue>/` and capture raw frames for: crossed-book semantics (is a cross corruption, or architectural as on dYdX?), sequence semantics (see DATA-08), price/quantity precision (does it need re-stamping, as dYdX's mark/index feed does?), open-interest availability (WS, REST poll, or dropped by the bindings?), subscribe-time replay (DATA-06), and rate/subscribe limits. Stories 19.3 (Bybit), 19.4 (Hyperliquid) and 22.5 are the precedent — each one's Task 1 is exactly this investigation, and each one's answers decided what the venue supplies. `platform/scripts/capture_hl_ws.py` is the capture harness to copy, **not one you can point at a new venue**: its `--venue` is a closed `choices=("hyperliquid", "bybit")` and its subscribe payload is a hard two-way branch, so passing a fourth venue's `--url` sends Hyperliquid's subscribe JSON. Extend it (a third branch plus the `choices` entry) as part of step 1; that extension is the one code change this recipe expects before the package exists.
2. **`capture/venues/<v>/client.py`** implementing the duck-typed client contract — the contract is the `VenueFeed` Protocol's docstring in `platform/capture/application/ports.py` (plus the optional capabilities it lists), satisfied structurally `[amended 2026-09-26: Story 26.1]`. The client's **constructor** takes `on_data` (the `OnData` port: every decoded message is pushed to it) and, for a client with a redundant trades-only socket, `ledger=` (capture's `Ledger`, since the `CaptureService` is capture's only ledger caller -- Story 26.1). The service builds the client itself, from the factory the composition root hands it (step 5), with its own `_on_data` and `_ledger` `[amended 2026-09-28: Story 26.2]`. No *market-data message* comes back through the five methods below; miss the callback and the service connects, writes the instrument definitions (`CaptureService.run`'s `self._archive.write_instruments(converted)`, the one write that does not go through the client callback) and then nothing else, logs `Started: N subscribed`, and the watchdog fires 30 s later with no clue why. All eight methods are **coroutines** — the core `await`s every one of them (`fetch_instruments`, `connect` and `subscribe_global` in `CaptureService.run`, `subscribe`/`unsubscribe` in `CaptureService.apply` and its retry loop, `disconnect` in `_disconnect`, `resync_orderbook` in `_resync_wire`, `fetch_book_snapshot` in `_crosscheck_round`), and a plain `def` raises `TypeError: object ... can't be used in 'await' expression` inside `run()`, which `run_forever` then retries forever with backoff — a permanent restart loop whose traceback points at the core, not at the new client. Five required methods: `fetch_instruments()`, `connect(loop, instruments)`, `disconnect()`, `subscribe(iid)`, `unsubscribe(iid)`. Three optional (four with the synchronous `feed_states()`): `subscribe_global()` (venue-wide channels), `fetch_book_snapshot(iid)` (enables the periodic REST-vs-live book cross-check; Bybit's and Hyperliquid's live in the venue's `book_snapshot.py`), `resync_orderbook(iid)` — expose `resync_orderbook` **only** for a venue whose local book can drift; a full-snapshot venue must not have it (Hyperliquid deliberately does not). **The client is also where per-channel idempotency and the per-venue subscribe pacing belong** — `CaptureService.apply` subscribes every planned instrument back-to-back with no spacing and offers no hook in between, and a retry, a re-add of a lingering id or a runtime plan change repeats `subscribe`/`unsubscribe` after a partial failure. Route every channel call of the client through one `capture.application.wire_channels.WireChannels` (one held reference per (channel, id); each call passes its inverse as `undo` wherever the Rust client changes its own bookkeeping before the fallible send -- verify it in `crates/adapters/<venue>/`: Bybit's topic reference count and Hyperliquid's `asset_context_subs` are both updated first, Hyperliquid's `trades`/`l2Book` keep no state, so they pass none) at a `<VENUE>_WS_FRAMES_PER_SECOND` constant in the client -- a chosen margin under what `scripts/measure_ws_limits.py` (extend it for the venue) observed live and the venue documents, recorded with date, method and numbers in `docs/DATA_DICTIONARY.md` §1.14. A per-IP channel limit the venue enforces only asynchronously is counted and refused in the client's `subscribe` before sending (Hyperliquid's `HYPERLIQUID_MAX_WS_CHANNELS`), never as a plan cap. A failed trades-only-twin subscribe is optional (ledgered); a failed twin unsubscribe raises, so capture retries it. dYdX relies on its Rust client's built-in 2/sec throttle and keeps its own `_hold`/`_release`. The Rust clients' reconnect replay is not paced by us (a `Known limit:` in each client) `[amended 2026-09-28: Story 29.4 -- was "a per-venue subscribe throttle belongs in the client's subscribe()"]`. A subscribe that fails on the wire does not restart the collector: it is ledgered (`collector.subscribe_failed`), shown `pending` and retried by capture's `_subscription_retry_loop` (Story 25.4). A cap on *how many* instruments a venue collects is not the client's: it is the collection plan's `cap`, one `VENUE_SCHEMAS` row (dYdX's `DYDX_MAX_COLLECTED_INSTRUMENTS = 30` in `capture/venues/dydx/config.py`, against dYdX's 32-per-channel-per-connection server limit; Bybit and Hyperliquid are uncapped, `cap` None, operator decision 2026-09-26), enforced by `collection_control.domain.plan.CollectionPlan` at load and on every command `[amended 2026-09-26: Story 25.4; 2026-09-28: Story 29.4]`.
3. **`capture/venues/<v>/trade_history.py` and, when step 1 found a need, `capture/venues/<v>/policies.py`.** `trade_history.py` is the venue's `VenueTradeHistory` (`capture.application.ports`): the REST fetcher, a pure parser tested against a recorded payload under the venue's `tests/fixtures/` (exact text into `Price`/`Quantity`, never through `float`: `capture.domain.trade_history`'s shared conversions, NAUT-01), and its `BackfillCapability` (how far back and how deep the venue's REST reaches; what it cannot cover is reported `unrecoverable`, never silent -- `docs/DATA_DICTIONARY.md` §1.1). `policies.py` holds the policy values step 1 justified, each with that evidence in its docstring: a crossed-book rule is a `CrossedBookPolicy` (dYdX's uncross ladder), a sequence check a `SequenceCanary` (Bybit's `u`), per-level tagging a `LevelTagger` -- the protocols and core defaults are `capture/domain/policies.py`. A policy file is domain code wherever it lives: stdlib, `kernel` and Nautilus value types only, no logging, ledger, `await` or clock (`test_boundaries.py`). A venue that needs none has no `policies.py` (Hyperliquid) and takes the core defaults `[amended 2026-09-26: Story 26.1; 2026-09-28: Story 26.2]`.
4. **`capture/venues/<v>/config.py`, a `config.toml` next to it, and one `VENUE_SCHEMAS` row in `capture/infrastructure/config.py`** — there is one venue loader, `load_venue_config(path, venue) -> (CoreConfig, CollectionPlan)`, and no venue writes its own (Story 25.4: dYdX's old key-by-key loader is gone). The row names the venue's environments, the keys it adds to the core's (`extra_keys`), the defaults it overrides (Hyperliquid's `stale_book_seconds`, its measured cadence, `capture/venues/hyperliquid/config.py`'s `STALE_BOOK_SECONDS`), its plan keys and a `build` function returning the thresholds -- a `CoreConfig` (`capture/application/config.py`) **subclass**, in the venue's `config.py`, only for keys the core does not have (`BybitConfig`'s `open_interest_poll_seconds`, `DydxConfig`'s cadences) -- plus the plan (a flat `instruments` list, plus an optional flat `exclude` written only when non-empty, is an uncapped plan with no liquidity pin; the row's `plan_keys` name both, so `TomlPlanStore.save` drops an emptied `exclude`) `[amended 2026-09-28: Story 29.4]`. Everything goes through `core_config_from_dict`, which rejects an unknown key instead of silently defaulting it: the rejection is `set(raw) - (_CORE_KEYS | set(extra_keys))`, so a venue key the row does not declare makes the venue's own valid `config.toml` raise `ValueError: unknown config keys [...]` at startup `[amended 2026-09-26: Story 25.4 -- was a per-venue `config.py` exposing `load_config(path)`]`. The venue's `config.py` also defines `CONFIG_PATH = Path(os.environ.get("<VENUE>_COLLECTOR_CONFIG", Path(__file__).parent / "config.toml"))` — without that env var (and its compose counterpart in step 6) the container reads the config baked into the image and every host edit is ignored. dYdX is the exception: its plan is operator data, so no `config.toml` is committed beside `capture/venues/dydx/config.py`, whose `CONFIG_PATH = Path(os.environ.get("DYDX_PLAN_PATH", "/app/dydx_collector/config.toml"))` defaults to the frozen container path (published language, AD-D12, shared with the `archive` service and `make nightly`) where compose mounts the host's `platform/data/dydx_config.toml`; a run with nothing mounted fails on the missing file `[amended 2026-09-28: Story 26.3 -- the 0-byte placeholder under the deleted dYdX collector package is gone]`. For every venue, an env var naming a path nothing mounts fails at start on the missing file; it is an *unset* `<VENUE>_COLLECTOR_CONFIG` that silently reads the baked file `[amended 2026-09-28: Story 26.3 review -- was "silently falls back to the baked file", which no loader does]`.
5. **`capture/venues/<v>/__main__.py`, the composition root** (`python3 -m capture.venues.<v>`; the three venues' files are the pattern). `build_capture(config, plan_ids)` returns one `CaptureService(config, lambda on_data, ledger: XClient(on_data=on_data, ..., ledger=ledger), (candle_prune_loop(store),), venue="<VENUE>", plan=plan_ids, archive=ParquetArchiveWriter(config.catalog_path), live_stream=RedisLiveStream(redis_url_from_env()), second_sink=CandleSink(store), policies=CapturePolicies(...), trade_history=XTradeHistory(...))` -- `venue` is the `kernel.venues` code whose capture lock `run_forever` takes, `plan` the plan's ids (`plan.collected`), applied by `run()` through `CaptureService.apply` (Story 25.4); the adapters come from `capture/infrastructure/`, importable only from these roots (`test_boundaries.py`). **Since Story 24.1 the service does not open the candle store, so the root must wire it — three things, none of them optional:** `store = store_from_env(config.catalog_path)` (`candles.infrastructure.sqlite_store`), `second_sink=CandleSink(store)` (`candles.application.sink`) and `candle_prune_loop(store)` (`candles.application.prune.loop`) among the extra loops. That ledger is no AD-4 writer→reader deviation: `observability/` is the generic context every context except `kernel` may import (Story 23.1, `platform/tests/test_boundaries.py` enforces it), so a new venue adds no boundary deviation and never a second error path `[amended 2026-09-21: Story 23.1]`. `build_capture_from_file(config_path=CONFIG_PATH)` does `config, plan = load_venue_config(config_path, "<VENUE>")` and returns `build_capture(config, plan.collected)`, and the module ends with `if __name__ == "__main__": asyncio.run(run_forever(build_capture_from_file))`. ## Memory Discipline

- **MEM-01** — Never load full catalog slices into memory. The anti-pattern is `catalog.trade_ticks()` with no time bounds — this will OOM on a large catalog. Always use time-bounded queries or `BacktestDataConfig` streaming instead.
- **MEM-02** — Non-configured coins are in-memory rolling-window only. No unbounded accumulation. If a coin is not in the config, its data must age out.
- **MEM-03** — Use generator/iterator patterns for large data pipelines. Do not materialize full instrument sets into lists when iteration suffices.

## Testing

- **TEST-01** — Tests are **required** for:
  - Any function doing financial calculations: OFI, imbalance, microprice, precision conversion.
  - Integration paths that touch Nautilus types or the catalog.
- **TEST-02** — Tests are **not required** for trivial glue code: config parsing, logging setup, simple data routing. YAGNI applies to tests too. If the function has no branching logic and no arithmetic, skip the test.
- **TEST-03** — Test style:
  - Never mock Nautilus internals — use real `Price`, `Quantity`, `OrderBook`, etc. objects, or skip the test entirely.
  - Use `pytest`; no class-based tests; minimal fixtures (helper functions with `_` prefix).
  - One assertion per logical claim. Return type `-> None` on all test functions.
- **TEST-04** — **Warnings and deprecation notices are not noise — never dismiss them as cosmetic.** A deprecated API gets removed in some future dependency bump (pandas, nautilus_trader, etc.), silently breaking the code at the worst possible time — usually mid-upgrade, far from the original context. A warning is also often the only visible symptom of a real latent bug (a resource never cleaned up, a coroutine never awaited, a type coerced somewhere it shouldn't be). Treat every new warning surfaced by a test run the same as a failing test:
  - Identify its exact source (don't guess "probably from a dependency") and either fix it at that source, or if it's genuinely upstream (a library's own internal deprecated call with no workaround), record it explicitly — file/line, the warning text, and why it can't be fixed here yet — rather than letting it scroll by unacknowledged.
  - Never add a blanket `filterwarnings("ignore")` or similar suppression to make output quieter — that hides the next new warning too, not just the one you're currently looking at.
  - This is what "long-running, easy to maintain" means in practice: the software should still build and run cleanly after routine dependency upgrades, years from now, not accumulate deprecated-API debt that turns every future upgrade into an archaeology project.

## bot_tui / urwid Patterns

- **TUI-01** — **A `urwid.ListBox` (or any `Filler`) that gets a brand-new `SimpleListWalker`/widget object on every redraw tick silently resets the user's scroll/focus position to the top.** `urwid.ListBox` and its `.focus_position` are properties of the walker *object* — swap in a fresh one and the old scroll state is simply gone, even though the visible rows look the same as before. This has been found and fixed twice independently in this codebase (Collector pane, Story 6.1; Bots pane, this incident) — both reported in production as "the page jumps [back] to the top" / "can't scroll." **The fix, in both cases:** never rebuild the `ListBox` itself on a routine per-tick refresh. Keep it as a persistent instance attribute (`self._foo_body`) plus a `self._foo_shape` sentinel (`None` / `"cold_open"` / `"rows"`); only swap the widget's *type* when the shape genuinely changes (empty ↔ populated); for a same-shape update, mutate the existing walker in place via slice-assignment (`listbox.body[:] = new_widgets`) — this is what actually preserves `.focus_position` across ticks. See `app.py`'s `_refresh_collector_body`/`_refresh_bots_body` for the reference implementation. **Any new scrollable pane in `bot_tui` must follow this pattern from the start** — a "no round-trip needs it yet" YAGNI deferral here specifically has already caused the same bug to ship twice; don't defer it a third time.
- **TUI-02** — **A fixed-width text column must truncate, not just pad.** Python's `f"{text:<N}"` only left-pads a *short* string to width `N` — it does not clip a *longer* one, so any field whose length isn't from a small closed vocabulary (an operator-chosen `bot_id`, an instrument ticker whose length varies, e.g. `RENDER-USD-PERP.DYDX` at 20 chars vs `BTC-USD-PERP.DYDX` at 17) will overflow its intended column width on some rows and push every column after it out of alignment for that row only — other rows still line up, so the table looks randomly, inconsistently broken rather than obviously wrong in one place. Use a real fit-to-width helper that truncates-with-ellipsis when over length (see `bots_pane.fit()`) for any field without a small fixed set of possible values; plain `:<N`/`:>N` remains fine for genuinely bounded fields (short enums like `mode`/`running`/`position_side`).

## Nautilus Usage Patterns

- **NAUT-01** — **Known silent bug:** `Price(decimal, precision)` silently returns a wrong value for some inputs. Example: `Price(Decimal("61090.59855"), 16)` returns `61090.5985500000026624`. **Never use this constructor for re-stamping.** Always re-stamp via:
  ```python
  raw = int(value.scaleb(new_precision))   # Decimal.scaleb() — exact integer arithmetic
  price = Price.from_raw(raw, new_precision)
  qty   = Quantity.from_raw(raw, new_precision)
  ```
  Use `Decimal.scaleb()` + `Price.from_raw()` / `Quantity.from_raw()` whenever setting a value at a different precision. Never round-trip a market-data value through `float` before it is safely inside a `Price`/`Quantity`.

- **NAUT-02** — All data written via `ParquetDataCatalog.write_data()`. No hand-rolled Parquet schemas. The catalog API owns the Arrow schema and partitioning; working around it breaks catalog reads.

- **NAUT-03** — Backtests use `BacktestNode` + `BacktestDataConfig`. No custom simulation engine. Reference strategies via `ImportableStrategyConfig` by string path so parameter sweeps and time-range filtering require no code changes. Since Story 24.4 the strategies, runners, watchlist client and notebooks live in the `research/` context, so the path is `research.strategies.<module>:<Class>` (e.g. `research.strategies.ofi_strategy:OFIStrategy`; the old strategy paths' re-exports were deleted in Story 25.2). Research reads market-data rows only through `kernel.catalog_files`, `BacktestDataConfig`, a typed catalog `query` bounded by both `start=` and `end=`, or the candle store's query service (`research/tests/test_research_reads.py`), and a notebook runs a backtest only through `research.application.backtest_runner.NodeRunner` (the `BacktestRunner` port: `RunSpec`, `run`, `sweep`; `research/README.md`'s "Backtesting & Strategy Development") `[amended 2026-09-25: Story 24.4]` `[amended 2026-09-26: Story 25.2]` `[amended 2026-09-28: Story 27.1]` `[amended 2026-09-28: Story 27.9]`.

## Signal Architecture: 1s-Based, Not Event-Driven

HFT signals are computed from **1-second sampled snapshots** (`DydxSecondSnapshot`), not from raw order book delta events.

**What is stored in Parquet (`DydxSecondSnapshot`):**
- Top-20 bid/ask levels: `bid_prices`, `bid_sizes`, `ask_prices`, `ask_sizes` (lists)
- Per-side trade volume: `buy_volume`, `sell_volume`
- All as exact integer units at the row's `price_precision`/`size_precision`, book prices as the best
  level plus gaps; `kernel/second_snapshot.py` is the one encoder/decoder, and the formulas below
  read its decoded floats (`docs/DATA_DICTIONARY.md` §1.7) `[amended 2026-09-29: Story 30.2]`.

**What is NOT stored — computed on read via `kernel/indicators.py`:**
- `microprice` = `Microprice().update_raw(bp, bs, ap, as_)` — derivable from level 0
- `spread` = `ask_prices[0] - bid_prices[0]` — derivable from level 0
- `ofi_N` = `MultiLevelOFI(levels=N)` replayed over consecutive snapshots
- `obi_N` = `MultiLevelOBI(levels=N).update_raw(bid_sizes, ask_sizes)`

**- SIGNAL-01** — If a value can be derived exactly from stored level data, do not store it. Store raw inputs; compute signals. Keeps the schema minimal and lets strategies try any N-level variant without re-collecting.

## Metrics Single Source of Truth (Web Dashboard)

Rankings, the ranking-mode switch and the single-coin view are web-only since Story 25.1a (operator decision 2026-09-26): `bot_tui` is the control surface for the bots and the collector, reads only `bots:*`/`collector:status`/`archive:status` and `markets:live` (each venue's market names for the Collector pane's market browser: no volume, price or metric), and must never re-grow a rankings view or a `rankings:live`/`snapshots:raw` subscription (`bot_tui/tests/test_no_rankings_feed.py`; every subscribed channel is recorded in `platform/tests/test_boundaries.py`'s `BOT_TUI_REDIS_CHANNELS`) `[amended 2026-09-26: Story 25.1a]` `[amended 2026-09-29: Story 29.5]`. The rules below still bind the web UI and any future renderer: every metric/indicator shown in the web UI (`frontend/` via `data_api`) must trace back to exactly one calculation — never two independent implementations of the same formula, and never two independently-running instances of the same stateful indicator class. **Since Story 24.2 the one place is `views/`** (the read-model context, DDD spine AD-D11): every market value a UI shows comes from one `views` function over one input, and `data_api` routes only format and transport it (`bot_tui` shows no market values at all; `platform/tests/test_boundaries.py` fails a `data_api`/`bot_tui` import of `ranking`, `capture` or `candles`, and any hand-indexing of a `snapshots:raw` payload outside the kernel).

- **SSOT-01** — Stateless, single-snapshot derivations (spread, mid price, CVD, volume_delta, avg_trade_size, microprice) live as plain functions/classes in `kernel/indicators.py`. - **SSOT-02** — Stateful/rolling/windowed metrics (OFI/OBI and their z-scores, volatility, pct_1h/pct_24h, EMA trend, `book_features` depth/imbalance/cancellation/cum_delta) must be computed exactly once, by exactly one long-running process, and published (Redis pub/sub or a shared store) for every other reader to consume verbatim. The `ranking/` context (the `ranking_engine` service, `python3 -m ranking`) is the sole owner of this class of computation (architecture AD-9, DDD spine AD-D10): its `RankingBoard` holds the one tracker set per instrument, and `ranking/domain/metrics.py`'s `price_stats_from_series` is the one pct-change/volatility formula in `platform/` (`platform/tests/test_boundaries.py` fails a second definition). `data_api` is a pure reader of its published output (`bot_tui` reads none of it since Story 25.1a), never independent computers of it -- through `views.rankings_bus` (`rankings:live`) and `views.coin_detail.metrics_history`/`metrics_nearest` (`metrics.db`, via ranking's query service `ranking.application.queries`); `views` and `research` never recompute a ranking metric (pct-change, volatility) -- research reads them over HTTP (`research.watchlist`, `research.rank_history`) `[amended 2026-09-26: Story 25.2]`.

## Desktop ↔ VPS Connection

The web UI (`data_api` serving the React SPA, Story 15.10 retired the old `dashboard`
service) and `bot_tui` normally run *on* the VPS (`nifelheim`) alongside `collector`,
inside Docker (`make up`). From the desktop there is exactly **one tunneled web surface,
`data_api`** — it serves the UI and its API from the same port, so no local process is
needed for the browser. Shell functions in `~/.zshrc` (outside this repo):

- **`_troll_tunnel_ensure`** — opens one background SSH tunnel to `$TROLL_VPS_HOST`
  (`nifelheim`) forwarding two ports: `6379` (Redis — live snapshots/rankings pub/sub,
  needed by `bot_tui`) and `9100` (`data_api`: the React UI, REST/WebSocket API, the
  Parquet catalog + `metrics.db` read-only, and the picker's own `chart_indicators.toml`
  config writes, Story 15.6). Idempotent — checks `fuser 6379/tcp` first, so repeated
  calls don't stack tunnels.
- **`troll-web`** — ensures the tunnel, then opens Firefox at `http://localhost:9100`
  (the tunneled `data_api`). There is no local dashboard process any more, so no
  `WEB_PORT` to keep in sync between desktop and VPS `.env` files.
- **`troll-tui`** — same tunnel dependency, plus starts `scripts/open_listener.go`
  locally (`$TROLL_OPEN_LISTENER_PORT`, `8901`) so that pressing `o` in `bot_tui`'s Bot-detail
  (which itself runs via `make tui`, rebuilding only the thin `bot_tui` Docker layer) can pop
  the bot's dashboard page open in the desktop's browser. `bot_tui` only needs live Redis;
  its deep-link targets `DASHBOARD_BASE_URL` (defaults to `data_api`'s port).
- **`troll-logs`** — a separate, independent tunnel (`-L 8080:localhost:8080` to
  `nifelheim`) for Dozzle, the container log viewer; unrelated to the Redis/`data_api`
  tunnel above. Opened with plain `xdg-open`, not Firefox directly.
- **`troll-down`** — tears everything back down: kills the `open_listener` process and any
  `ssh.*nifelheim` tunnel (both the Redis/`data_api` one and the Dozzle one).

**Migration note (Story 15.10):** `_troll_dashboard_ensure`, `$TROLL_WEB_PORT` and
`make dashboard` no longer exist in the repo — `~/.zshrc` must drop the first two and
point `troll-web` at `http://localhost:9100`, or it will poll a port nothing listens on.

**Why this exists:** running the web UI/TUI on the desktop instead of the VPS gets a
real browser and better interactivity without exposing any VPS port publicly — SEC-01
still holds, since nothing new is bound to `0.0.0.0` on `nifelheim`; the connection is
entirely outbound SSH from the desktop.
