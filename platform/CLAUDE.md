# platform/ Working Rules

These rules govern all code under `platform/`: `collector_core/`, the venue collectors
(`dydx_collector/`, `bybit_collector/`, `hyperliquid_collector/`), `common/`,
`ml_signals/`, `ranking_engine/`, `data_api/` + `frontend/` and `bot_tui/`.
`nautilus_trader` is consumed as a library only — never as a live runtime — in all of
them. **Exception:** `platform/live_paper/` is a separate, structurally isolated module
(architecture spine's AD-8 amendment) where `TradingNode`/`Strategy` usage is sanctioned —
it is the one place in `platform/` this file's `TradingNode`/`DataEngine` ban does not apply.
See `platform/live_paper/node.py`'s module docstring for the full rationale.

---

## Fork Safety

- **FORK-01** — Never modify `nautilus_trader/` or `crates/`. All `platform/` code is additive-only. The fork must stay untouched so upstream merges remain possible.
- **FORK-02** — `nautilus_trader` is a library here: use its domain types (`Price`, `Quantity`, `InstrumentId`, …) and `ParquetDataCatalog.write_data()`. Never instantiate `TradingNode` or `DataEngine` in any `platform/` module. **Why:** the live `DataEngine` has a documented unbounded-queue-growth + shutdown-wedge bug under sustained high-message-load that OOM-crashed the earlier `Strategy`/`TradingNode`-based recorder on the `gg` branch. **Does not apply to `live_paper/`** — that module's entire purpose is running an actual (paper or, behind an explicit separate gate, real) trading strategy via `TradingNode`, which AD-8 explicitly carves out as a distinct, sanctioned usage from the recorder-misuse this rule prevents.

## Version Control

- **GIT-01** — Never run `git push` (including force-push) without asking the user first and getting explicit confirmation, regardless of permission mode. Always state what would be pushed (branch, commits) before asking.

## Network Security

- **SEC-01** — **Every Docker port is localhost-only. No exceptions, ever.** `ports:` entries must be `"127.0.0.1:HOST:CONTAINER"` — never a bare `"HOST:CONTAINER"`/`"PORT"` (that publishes to `0.0.0.0`). If a service needs no host access at all, use `expose:` instead of `ports:`, or nothing. Remote access is via SSH tunnel (`ssh -L`) only, never a publicly reachable port — including reverse proxies. **Why:** Docker inserts its own `iptables` `ACCEPT` rules ahead of ufw's chain, so a bare port mapping is reachable from the public internet even with `ufw deny <port>`/`ufw default deny incoming` active — ufw never sees the connection, since Docker never routes it through ufw's INPUT chain. Enforced unconditionally by the `check-docker-port-binding` pre-commit hook (`.pre-commit-hooks/check_docker_port_binding.sh`) — no escape-comment override. `platform/docker-compose.yml`'s services already follow this: `redis`/`dozzle` bind `127.0.0.1:PORT:PORT`; `collector`/`bybit_collector`/`hyperliquid_collector` `[amended 2026-09-20: Epic 22 story 22.8, review pass — the two Epic 22 collector services were missing from this enumeration; `platform/docker-compose.yml:83`/`:106`]`/`data_api`/`ranking_engine`/`bot_tui`/`live-paper` use `network_mode: host` with the app itself binding `127.0.0.1` (e.g. `data_api`'s `uvicorn --host 127.0.0.1`) instead of a `ports:` mapping.

## Data Integrity

- **DATA-01** — **Correct data is the #1 priority. Never display stale or fabricated values as live market data.** If data is genuinely unavailable (e.g., during WS reconnect recovery when the Rust client re-subscribes instruments at 2/sec), the gap must be flagged visually rather than papered over with a flatline. **Implementation:** `collector_core/collector.py`'s per-second gate `_sample_tick` (called by `_second_loop`) uses `config.stale_book_seconds` to skip snapshot emission when no `OrderBookDeltas` have arrived for an instrument — 5 s is only `CoreConfig`'s default, and is set per venue from measured push cadence **by the venues whose loader reads it** — Hyperliquid runs 12 s, justified in its `config.toml`. dYdX is the exception: `dydx_collector/config.py`'s older key-by-key loader never reads `stale_book_seconds` (nor `crossed_resync_seconds`, `stale_trade_seconds`, `seen_trade_ids`, `feed_stale_seconds`, `book_crosscheck_seconds` or `trade_feeds` -- dYdX always runs one trade feed) and ignores unknown keys, so putting any of them in dYdX's `config.toml` has no effect and raises no error; `data_api/routes/snapshots.py` breaks the series at timestamp gaps > `_SNAPSHOT_GAP_THRESHOLD_MS` (2500 ms) so the chart renders an honest gap instead of a misleading horizontal line. When adding new data sources or display paths, apply the same principle: skip or flag, never silently perpetuate stale state. **Two clocks** (story 22.13): every archived `TradeTick` keeps `ts_event` (the venue's trade time) and `ts_init` (our receive time) untouched -- aggregates bucket on `ts_event` (the nightly `rebuild_seconds`), backtests replay on `ts_init`; the live 1 s snapshot is provisional until its day is rebuilt and reconciled (`verified_days`). It is arrival-timed on dYdX (its book deltas carry no venue time, audit D-49) and exchange-timed on Bybit/Hyperliquid (`book_time_source = "venue"`, story 22.12): second `S` closes at wall `S + 1 + hold_back_seconds` from the deltas with `ts_event < S+1` and the trades with `ts_event` in `[S, S+1)`, stamped `ts_event = S + 0.5 s`, `ts_init` = when it was sampled; a trade arriving after its second closed is archived and counted (`collector.late_trade`), never folded live -- the rebuild places it. Anything judging liveness (watchdog, `ranking_engine` freshness) compares arrival, never a row's `ts_event`.

- **DATA-02** — **No mysteries in data ingestion. Maximum assurance that ingested data is correct and lossless is non-negotiable — this is the most critical part of the system.** When ingestion produces wrong or missing data (a desynced book, a dropped message, a stale value), detecting it fast and recovering automatically is necessary but is **never sufficient on its own** — treating fast recovery as "solved" is symptom treatment, not a fix. The investigation is not done until the exact mechanism is known. No guessing, no stopping at "probably the venue's fault" or "probably fine now" without hard evidence.
  - **Standard of proof:** rule out hypotheses with real evidence, not code-reading alone. Cross-check against an independent source of truth before concluding anything — e.g. the venue's own REST API, or a second independent client with zero shared code path with our pipeline (both used in production to prove a local order-book desync was real and not venue-side crossing).
  - **Close observability gaps permanently, don't patch around them.** If a whole class of failure was invisible for lack of instrumentation (e.g. Rust-side `log::error!`/`warn!` calls being silently dropped because `nautilus_pyo3.init_logging()` was never called in a standalone script that doesn't go through `TradingNode`/Kernel startup), fix that gap once, permanently — don't work around not being able to see the failure.
  - **A staleness/health canary on your own detection loop is required, not optional**, wherever a detection-and-recovery mechanism depends on a periodic check running promptly (e.g. `_second_loop`'s wall-clock tick-lag warning) — otherwise the safety net's own reliability becomes exactly the kind of invisible failure this rule exists to prevent.
  - **Only two acceptable end states for an ingestion-correctness question:** (1) the exact mechanism is identified, and either fixed or proven — with hard, independently-verified evidence — to be outside our control (e.g. genuinely lost upstream of our client); or (2) it is still genuinely open, and must be labeled and tracked as such, never quietly treated as resolved just because the visible symptom got smaller, quieter, or faster to recover from.

- **DATA-03** — **A forced resync (unsubscribe/resubscribe to force a fresh snapshot, e.g. `DydxCollector._resync_book` (`dydx_collector/collector.py`, dYdX-only) or the core's own `Collector._resync` (`collector_core/collector.py`), reached from `_handle_crossed_book` or a queued `_resync_pending`) is a destructive, worst-case recovery — never a fix, and never evidence the underlying problem is understood or solved.** It throws away local state and rebuilds from scratch, which hides the actual data loss it's papering over (during the resync window that instrument has no book at all) and, if triggered often, indicates the root cause is still live and recurring, not resolved. Treat a high or rising forced-resync rate as an open DATA-02 incident, not as "the safety net is working." Prefer a resync-avoiding fix at the actual loss point over tuning the resync trigger (the threshold is now the config field `CoreConfig.crossed_resync_seconds` in `collector_core/config.py`; it was the module constant `_CROSSED_RESYNC_NS` before story 22.2 moved it) tighter/looser — tuning the trigger changes how fast the worst case is reached, not whether it's needed.

- **DATA-04** — **A crossed dYdX v4 orderbook is expected, architectural, and unpreventable by any client — confirmed via dYdX's own official docs and Indexer source, not inference.** dYdX v4 has no centralized orderbook: each validator holds its own in-memory, off-chain, pre-consensus book, matched against whichever block proposer's mempool is currently active (rotates every block). dYdX's own integration guide states outright that a client cannot prevent seeing a crossed book. Treat a crossed book as a normal, expected condition to correct — not a symptom that, absent other evidence, implies a local pipeline bug (contrast with DATA-02's standard, which still applies to a book that *never* uncrosses at all — see below).
  - **The correct resolution is dYdX's own, from its Indexer's `Roundtable` service (`uncross-orderbook.ts`), not a full resync:** tag every price level, when applied, with the message-id of whichever WS update last touched it (dYdX's own docs: `OrderBookDelta.sequence`/the WS envelope's connection-global `message_id`, applied **per price level**, not per-instrument — a different, valid use of the same field the per-instrument gap-detection removal in commit `944891bbba` correctly ruled out). When crossed, delete only the level with the older message-id (loop until uncrossed), via a synthetic `BookAction.DELETE` — never wipe the whole book for this.
  - **Forced resync (DATA-03) is a fallback only** — for when a level can't be tagged (e.g. immediately after a resubscribe) or a book stays crossed for far longer than active uncrossing should ever take. It is not the first response to an ordinary crossed book.
  - See `_bmad-output/planning-artifacts/research/technical-dydx-v4-orderbook-crossing-resolution-research-2026-09-06.md` for full sourcing (dYdX docs + Indexer source + this repo's own wire captures).

- **DATA-05** — **No data loss, where it can be prevented. Never accept a silent gap as "small" or "just a cache."** This covers derived data too (the SQLite candle store, `ml_signals/candle_store.py`): a missing second understates the bar built from it, so it counts. Any seam that can drop data (restart, shutdown, chunk/range boundary, a failed write) must be closed by design or have a documented, tested way to fill it. A loss that genuinely can't be prevented must be named explicitly, with how to detect and repair it -- never left implicit. **Why / how it is closed:** raw 1s snapshots in Parquet are the ground truth; the store is derived from them and applies each second exactly once (per-instrument watermark), so a restart just means fewer observed seconds in that bucket (`seconds_observed`, and `partial` when under 90% of the span) -- there is no minute-close seam. A failed store write is loud (`collector.candle_store` in the error ledger) and is repaired by `python -m collector_core.build_candles`, which recomputes whole UTC days from raw 1s and is idempotent. Open edges, by design: the store can hold up to ~30 s the archive lost after a crash (a rebuild of that day drops them), and a hole filled into the archive later reaches the store only through `build_candles`. **A live-fold error is filled by the rebuild, never patched at read time** (story 22.13): raw trades are archived (`data/trade_tick/`), and `python -m collector_core.rebuild_seconds --day D --apply` re-derives a closed day's snapshot trade columns from them with the same exact fold (`collector_core/fold.py`), then `build_candles --day D` refolds the store and `compare_klines` proves the day against the venue's klines -- all chained by `make nightly VENUE=...`. Trades that had no sampled second (collector not sampling) are counted as orphans, never dropped silently. Minute rollups no longer exist (retired 2026-09-20; see `docs/DATA_INTEGRITY_AUDIT.md` D-35).

- **DATA-06** — **Never count venue-replayed history as live data, and never store a price the same second's book cannot contain.** dYdX's `v4_trades` subscribed reply carries up to 1000 historical trades; counting them as live created fake ~$850-range, ~21 BTC candles after every (re)subscribe (proven against the raw indexer feed). Any new channel must be checked for a subscribe-time snapshot/replay before its rows are treated as live. Guards: the `stale_trade_seconds` age filter + per-instrument `trade_id` dedup (`seen_trade_ids`), both configured in `collector_core/config.py` and applied in `collector_core/collector.py`'s `_process_data`, and `integrity.ohlc_outside_book` (trade high/low must lie inside that second's own top-20 book range) as both a live ERROR canary and the detector for `repair_catalog`. **Reconnect gaps and duplicate classes** (story 22.14): the dedup map remembers which feed (WS connection) delivered each id first -- a repeat from the *same* feed is a replay (`duplicate`; after the startup grace it is also a reconnect signal), from *another* feed or the REST backfill source `rest` it is `duplicate_feed` (the dual-feed union, `trade_feeds = 2`); both are counted each flush, never folded twice. Trades a reconnect missed are recovered over REST by `collector_core/trade_backfill.py` (one `collector.trade_backfill` ledger entry per reconnect), archived only -- never folded into the live second -- and never older than the 300 s `ARRIVAL_MARGIN_NS` the rebuild depends on; what the venue's depth cannot cover is reported `unrecoverable`, never silent (`docs/DATA_DICTIONARY.md` §1.1 capability table). When wrong rows already exist, repair with `python -m collector_core.repair_catalog` (report first, `--apply` after a backup) rather than hiding them at read time. The full register of known wrong-data dangers, with status, is `platform/docs/DATA_INTEGRITY_AUDIT.md` — add every new one there.
- **DATA-07** — **Never filter, drop, clamp, mute or hide an error that malfunctioning code caused. Find the malfunction and fix it.** A validator that discards a bad candle, a read-time guard that skips bad rows, a log filter that mutes a noisy error, a retry/restart that papers over a crash — each is a symptom treatment that leaves the bug live and the data (or the process) still wrong. Checks are allowed only as **loud canaries** (ERROR log + counter + visible in the UI/audit) that *prove* the fix holds; they never replace it, and they must not silently change what the operator sees. Filtering is legitimate only for input that is not a fault of ours — e.g. classifying a venue's documented subscribe-time replay (DATA-06) — and that classification must itself be evidenced. **Specifically: no OOM kills.** The collector being OOM-killed (audit D-06) is a bug to fix at its cause (unbounded queue/buffer growth, oversubscribed host), never something to live with because restarts are handled by backfill or dedup. A restart-tolerant pipeline does not make a crash-looping one acceptable. **Mechanism:** every site that must continue past a failure calls `observability.error_ledger.record(site, detail, exc)` (ERROR + traceback + per-site count; the generic `observability/` context, standard library only, that every context except `kernel` may import -- Story 23.1 moved it out of `ml_signals`, whose `ml_signals.error_ledger` is now a deprecated re-export); `GET /api/errors` exposes the counts and the frontend's non-dismissible `<ErrorBar>` shows them together with every browser `console.error`/uncaught error, so a failure is visible without reading Dozzle. Outbound notification goes through the one transport `observability.notify(channel, title, body)` (ntfy, Telegram, webhook), whose failed sends are themselves ledgered (`observability.notify.<transport>`), never logged-and-forgotten. **Durable per service (Story 23.3):** besides the in-memory count, `record()` appends one JSON line (`ts_ns`, `service`, `pid`, `site`, `detail`, `exc_type`, `suppressed`) to `<ERROR_LEDGER_DIR>/<ERROR_LEDGER_SERVICE>.jsonl` when `ERROR_LEDGER_DIR` is set (`docker-compose.yml` sets it to the shared `./data/errors:/app/errors_dir` mount for all seven services calling `record()`: `collector`, `bybit_collector`, `hyperliquid_collector`, `ranking_engine`, `data_api`, `live-paper`, `bot_tui`), so a day's failures survive a restart, an image rebuild or Redis loss (Redis here has no volume and `appendonly no`, on purpose). Each process writes a `process_start` line via `observability.error_ledger.start()` at boot, so a reader can tell a zero-error window from a restarted one. `GET /api/errors`'s `services` block reads every service's file back (per-site counts since its last restart and since an optional `?since_ns=`); `python3 -m collector_core.crosscheck_errors` cross-checks a whole window's ledgers against the archived catalog's own gaps (`platform/docs/DEPLOY_CHECKLIST.md` §6). **Known limit:** the write cap (`ERROR_LEDGER_MAX_LINES_PER_SITE_PER_MIN`, default 60/site/minute, with an exact `suppressed` carry) and size rotation (`ERROR_LEDGER_MAX_BYTES` × `ERROR_LEDGER_BACKUP_COUNT`, default 20 MB × 10, mirroring the compose `x-logging` policy) mean a sustained storm can still age a day's lines out of the window before anyone reads them; and the in-memory `counts()` the `<ErrorBar>` polls is still only `data_api`'s own process. Upgrade path: raise the two env vars, or ship the files to object storage alongside the catalog backup (story 22.11's rclone remote); for *live* cross-process visibility, the `errors:ledger` Redis channel (`observability/infrastructure/redis_ledger.py`, DDD spine AD-D16) that `/api/errors` aggregates. A bare `logger.warning(...); continue` at a data-dropping site is not acceptable. **How to apply:** when you find yourself writing `if bad: skip/drop/None`, stop and trace where `bad` is produced; when a symptom is muted, the story is not done until the producer is fixed and the audit register (`docs/DATA_INTEGRITY_AUDIT.md`) says so; when a fix is not possible in this session, register it OPEN — never present a filter as the fix.

- **DATA-08** — **A venue's book "sequence" field means something different at every venue — never gap-check one without that venue's own evidence.** The same-looking `OrderBookDelta.sequence`/update-id is three different things across the three venues collected here: dYdX's is the WebSocket envelope's **connection-global `message_id`**, shared by subscribe-acks and every other market on that connection, so per-instrument gap-detection false-positives on essentially every message once more than a handful of instruments share the socket (removed in commit `944891bbba`; the reasoning is in `platform/dydx_collector/collector.py`'s `_apply_deltas` docstring, and the same field is still legitimately used *per price level* for DATA-04 uncrossing). Bybit's `u` **is** a genuine per-topic sequence, measured contiguous in a healthy stream (31,860 of 31,860 steps exactly +1 over an 800 s BTCUSDT capture), so a gap or a regress is real message loss/reordering — used as a canary in `bybit_collector/collector.py`'s `_sequence_verdict`/`_message_u`, which ledgers `collector.book_sequence`, drops the book and queues a resync. **Carry that evidence's scope with it:** D-41 measured one instrument on one topic (`BTCUSDT` linear `orderbook.50`); Bybit **spot** is collected too and is unmeasured, so a `u` break on a spot topic is an open DATA-02 question, not a proven loss. The canary also has **three** no-verdict cases, two deliberate and one not: it returns `ok` when there is no baseline yet (`last_u is None`) and re-baselines on a snapshot or `u == 1` — so the first messages after a connect or a resync are not gap-checked at all — and it is skipped entirely when `_message_u` returns `None`, which it does for a message carrying zero levels (an explicit wire case: `crates/adapters/bybit/src/websocket/parse.rs`'s `total_levels == 0` branch). That third case is gated at `bybit_collector/collector.py:117`, **outside** which `_last_u` is never updated, so a skipped message leaves the baseline one behind and the *next* message reads as `u - last_u == 2` → `"gap"` → a `collector.book_sequence` ledger entry, a dropped book and a DATA-03 forced resync on a healthy stream. That false positive is an open DATA-02 question, not a measured one `[amended 2026-09-20: Epic 22 story 22.8, review pass]`. Hyperliquid sends a **full authoritative snapshot** every message and keeps no sequence bookkeeping at all, so there is nothing to gap-check and no `resync_orderbook` on its client. **Rule:** before wiring any sequence/update-id check for a new venue, capture that venue's own raw frames and show what the field actually counts — never port another venue's interpretation, and never assume the absence of a check is an oversight. Evidence: stories 22.2 and 22.5; `docs/DATA_INTEGRITY_AUDIT.md` D-41.

## Observability Rules

- **OBS-01** — **Zero book updates across N liquid instruments is a failure mode, not market behavior.** BTC/ETH/SOL perpetuals trade 24/7. If `buy_count == 0` and `sell_count == 0` and bid prices are frozen for all subscribed instruments for more than 30 seconds, the data pipeline has failed — diagnose it, do not accept it as "quiet market." Root cause seen in production: (a) `classify_liquidity` using `openInterest` (token units) instead of `volume24H` (USD), causing BTC=458 tokens to fail a `>= 100_000 USD` threshold; (b) `_bar_builder._books` only updated every 60s at flush time, making `_second_loop` read a 60-snapshot-old book. `_second_loop` now lives in the shared core as `collector_core.collector.Collector._second_loop` (with the gate it calls, `_sample_tick`), inherited unchanged by every venue collector; `_bar_builder` no longer exists at all — minute rollups were retired 2026-09-20 (`docs/DATA_INTEGRITY_AUDIT.md` D-35), so (b)'s mechanism is gone rather than moved `[amended 2026-09-20: Epic 22 story 22.8, review pass — the earlier wording said "both loops now live in the shared core", which implied a deleted symbol had been relocated]`.
- **OBS-02** — **OFI z-score changing while price is frozen does NOT prove the data pipeline is healthy.** The OFI z-score is a rolling 3600-point window mean/std — it evolves as historical values age off even when current OFI input is zero. A changing z-score with a frozen price is consistent with a dead book feed. Check `buy_count`, `sell_count`, and raw bid/ask changes across consecutive snapshots, not derived indicators.
- **OBS-03** — **Liquidity classification must use volume (USD), not open interest (tokens).** `openInterest` from dYdX's indexer is in base-token units. BTC at 458 tokens looks "illiquid" against a $100k threshold. Always classify by `volume24H` (already USD) or by `openInterest × oraclePrice`. The config key `liquidity_min_oi_usd` means "minimum USD liquidity" — enforce it with a USD-denominated field.

## Design Principles

- **DESIGN-01** — **No abstraction without a named invariant.** A class, aggregate, port, interface, factory or config value is admitted only if its docstring names the specific invariant it protects and the commands that could violate it; anything that cannot state one stays a plain function or dataclass. No scaffolding for hypothetical future use. Ports are `typing.Protocol`, wired explicitly at composition roots; no DI container, no event-bus library. **Why:** this is how the DDD spine (`_bmad-output/planning-artifacts/architecture/architecture-ddd-platform-2026-09-21/`, AD-D4) keeps tactical patterns from becoming ceremony — `LiveBook` earns its place by naming "a delta applies at most once, only after a baseline"; a `RankChanged` event nothing consumes does not. Replaced the earlier YAGNI wording on 2026-09-21.
- **DESIGN-02** — Decouple at natural seams: `collector` / `book_features` / strategy / backtest. Components depend on shared data types, not each other's internals. Never import a collector class from a strategy file.
- **DESIGN-03** — Prefer deletion over addition when simplification is possible. Prefer boring over clever. A function you can read in 10 seconds is better than one that needs a comment.

## Adding a venue

A venue is a thin package over `collector_core.collector.Collector` — no new gate, no new loop, no base-class edit.

1. **Investigate the wire behaviour first, before deciding which core hooks to override.** Read that venue's adapter under `crates/adapters/<venue>/` and capture raw frames for: crossed-book semantics (is a cross corruption, or architectural as on dYdX?), sequence semantics (see DATA-08), price/quantity precision (does it need re-stamping, as dYdX's mark/index feed does?), open-interest availability (WS, REST poll, or dropped by the bindings?), subscribe-time replay (DATA-06), and rate/subscribe limits. Stories 19.3 (Bybit), 19.4 (Hyperliquid) and 22.5 are the precedent — each one's Task 1 is exactly this investigation, and each one's answers decided the overrides. `platform/scripts/capture_hl_ws.py` is the capture harness to copy, **not one you can point at a new venue**: its `--venue` is a closed `choices=("hyperliquid", "bybit")` and its subscribe payload is a hard two-way branch, so passing a fourth venue's `--url` sends Hyperliquid's subscribe JSON. Extend it (a third branch plus the `choices` entry) as part of step 1; that extension is the one code change this recipe expects before the package exists.
2. **`<venue>_collector/client.py`** implementing the duck-typed client contract — the contract is the module docstring at `platform/collector_core/collector.py:15-48`, not a base class. The client's **constructor** takes `on_data: Callable[[object], None]` and every decoded message is pushed to it — the collector passes its own `self._on_data` (see step 4). No *market-data message* comes back through the five methods below; miss the callback and the collector connects, writes the instrument definitions (`collector_core/collector.py:830`, the one write that does not go through the client callback) and then nothing else, logs `Started: N subscribed`, and the watchdog fires 30 s later with no clue why. All eight methods are **coroutines** — the core `await`s every one of them (`fetch_instruments` `:828`, `connect` `:832`, `subscribe_global` `:834`, `subscribe` `:844`, `disconnect` `:876`, `resync_orderbook` `:418`, `fetch_book_levels` `:739`), and a plain `def` raises `TypeError: object ... can't be used in 'await' expression` inside `run()`, which `run_forever` then retries forever with backoff — a permanent restart loop whose traceback points at the core, not at the new client. Five required methods: `fetch_instruments()`, `connect(loop, instruments)`, `disconnect()`, `subscribe(iid)`, `unsubscribe(iid)`. Three optional: `subscribe_global()` (venue-wide channels), `fetch_book_levels(iid)` (enables the periodic REST-vs-live book cross-check), `resync_orderbook(iid)` — expose `resync_orderbook` **only** for a venue whose local book can drift; a full-snapshot venue must not have it (Hyperliquid deliberately does not). **The client's own `subscribe()` is also where a per-venue subscribe cap or throttle belongs** — `collector_core/collector.py:843-845` subscribes every configured instrument back-to-back with no spacing and offers no hook in between, so a venue whose pyo3 WS client has no built-in throttle will rate-limit or ban itself at connect, inside `run_forever`'s restart loop. dYdX's answer sits outside the core entirely, as an operating cap in its control plane (`_MAX_COLLECTED_INSTRUMENTS = 30`, `dydx_collector/collector.py:106`, against dYdX's 32-per-channel-per-connection server limit).
3. **`config.toml`** next to the package **and** a `config.py` exposing `load_config(path)` — the loader is always required (step 4's entrypoint calls it); what is optional is the `CoreConfig` **subclass**, needed only for keys the core does not have (Bybit subclasses for `open_interest_poll_seconds`; Hyperliquid's `load_config` returns a plain `CoreConfig` and exists only to raise `stale_book_seconds` to its measured 12 s). Load via `core_config_from_dict`, which rejects an unknown key instead of silently defaulting it — do not copy dYdX's older key-by-key loader. **Pass your venue's own keys through its `extra_keys` argument** (`core_config_from_dict(raw, environments, extra_keys=("...",))`, as `bybit_collector/config.py:33-35` does): the rejection at `collector_core/config.py:64-68` is `set(raw) - (_CORE_KEYS | set(extra_keys))`, so a venue key that is not declared there makes the venue's own valid `config.toml` raise `ValueError: unknown config keys [...]` at startup.
4. **`<venue>_collector/collector.py`**: a ~15-line `XCollector(Collector)` that builds its client in `__init__` as `XClient(on_data=self._on_data, ...)` — handing out a bound method before `super().__init__` runs, which is safe and is what all three do (`hyperliquid_collector/collector.py:42-44` is the shortest) — and calls `super().__init__(config, client)` (add `extra_loops=(...)` for a REST poll), overriding only the hooks step 1 justified; entrypoint is `asyncio.run(run_forever(lambda: XCollector(load_config(CONFIG_PATH))))`, with `CONFIG_PATH = Path(os.environ.get("<VENUE>_COLLECTOR_CONFIG", Path(__file__).parent / "config.toml"))` — without that env var (and its compose counterpart in step 6) the container reads the config baked into the image and every host edit is ignored. dYdX looks like a counterexample and is not: `dydx_collector/collector.py:90` hardcodes `CONFIG_PATH` with no env var, but compose bind-mounts the host file **over** the baked path (the committed `dydx_collector/config.toml` is a 0-byte placeholder). Either shape works; do not mix them — an env var pointing at a path nothing mounts silently falls back to the baked file. Any hook or `extra_loops` body that continues past a failure must call `observability.error_ledger.record(site, detail, exc)` rather than `logger.warning(...); continue` (DATA-07); `bybit_collector/collector.py`'s open-interest loop is the pattern. That import is no longer the AD-4 writer→reader deviation it was while the ledger lived in `ml_signals`: `observability/` is the generic context every context except `kernel` may import (Story 23.1, `platform/tests/test_boundaries.py` enforces it), so a new venue adds no boundary deviation and never a second error path `[amended 2026-09-21: Story 23.1]`. `hyperliquid_collector/collector.py` is the whole-file reference.
5. **One line in `platform/common/venues.py`**: add the venue **as its uppercase Nautilus venue token** (`common/venues.py:8` is keyed `"DYDX"`/`"BYBIT"`/`"HYPERLIQUID"`, and `venue_kind` is a plain `.get()`) to `VENUE_KINDS` (`"cex"`/`"dex"`), and extend `market_kind`'s suffix sets only if the Nautilus id suffix is new. Both helpers return `"unknown"` rather than raising, so skipping or mis-spelling this step fails soft — the venue collects fine and then shows up as `unknown` in rankings, the API and every filter. Check both for a real id before calling the venue done.
6. **Wiring**: a `docker-compose.yml` service (same image, different `command:`, its own `<VENUE>_COLLECTOR_CONFIG` + config mount, the same catalog root **and** the shared candles directory with its own `CANDLES_DB_PATH: /app/candles_dir/candles_<venue>.db`. `<venue>` must be the **lowercase Nautilus venue token**, not the package name — `data_api/settings.py:25` resolves `candles_{venue.lower()}.db` from `venue_of(instrument_id)`. Leaving the variable unset does **not** collide with another venue (separate containers): `collector_core/collector.py:277-279` falls back to `<catalog_path>/../candles/candles.db`, i.e. `/app/candles`, which nothing mounts — so the candle store becomes a container-local SQLite file discarded on every rebuild, and `data_api` finds no `candles_<venue>.db` and serves empty charts, with no error anywhere); a `COPY` line in `platform/collector.dockerfile`; `<venue>_collector/__init__.py` and `<venue>_collector/tests/__init__.py` (three packages already ship a `tests/test_collector.py` — `collector_core`, `bybit_collector`, `hyperliquid_collector` — so without them pytest hits an import-file-mismatch); and the package's `tests/` path in the `Makefile`'s `test` target. The service also needs the four keys all three existing collectors set and this list used to omit (`docker-compose.yml:37,44,59,61` / `:73,77,83,85` / `:97,100,106,108`): `REDIS_URL` (the default `redis://127.0.0.1:6379` misses the `LOCAL_DEV` port shift at `Makefile:20-23`, and `_publish_snapshot_batch` only warns on a publish failure — the venue then writes Parquet normally while being invisible in rankings, `bot_tui` and every live view), `network_mode: host`, `user: "1000:1000"` (all three collectors share **one** catalog root, so a root-writing service leaves partition dirs the uid-1000 collectors cannot write into) and the `logging: *default-logging` anchor (without it a 24/7 writer gets Docker's uncapped `json-file` driver) `[amended 2026-09-20: Epic 22 story 22.8, review pass]`. Check the `Makefile`'s other explicit service lists too — `redeploy-all`, `build-insecure` and `frontend-dev` each name their services one by one, and none of the three lists `bybit_collector` or `hyperliquid_collector` today.

A new venue adds its parser (USD only, OBS-03; ids built exactly as the adapter builds them; an unparseable value `error_ledger.record`ed and skipped, never 0), its fetcher (plus a `<VENUE>_ENVIRONMENT`-style URL map validated in `_volume_sources()`) and its entry there. ## Memory Discipline

- **MEM-01** — Never load full catalog slices into memory. The anti-pattern is `catalog.trade_ticks()` with no time bounds — this will OOM on a large catalog. Always use time-bounded queries or `BacktestDataConfig` streaming instead.
- **MEM-02** — Non-configured coins are in-memory rolling-window only. No unbounded accumulation. If a coin is not in the config, its data must age out.
- **MEM-03** — Use generator/iterator patterns for large data pipelines. Do not materialize full instrument sets into lists when iteration suffices.

## Testing

- **TEST-01** — Tests are **required** for:
  - Any function doing financial calculations: OFI, imbalance, microprice, precision conversion.
  - Integration paths that touch Nautilus types or the catalog.
- **TEST-02** — Tests are **not required** for trivial glue code: config parsing, logging setup, simple data routing. YAGNI applies to tests too. If the function has no branching logic and no arithmetic, skip the test.
- **TEST-03** — Test style:
  - Never mock Nautilus internals — use real `Price`, `Quantity`, `OrderBook`, etc. objects, or skip the test entirely.
  - Use `pytest`; no class-based tests; minimal fixtures (helper functions with `_` prefix).
  - One assertion per logical claim. Return type `-> None` on all test functions.
- **TEST-04** — **Warnings and deprecation notices are not noise — never dismiss them as cosmetic.** A deprecated API gets removed in some future dependency bump (pandas, nautilus_trader, etc.), silently breaking the code at the worst possible time — usually mid-upgrade, far from the original context. A warning is also often the only visible symptom of a real latent bug (a resource never cleaned up, a coroutine never awaited, a type coerced somewhere it shouldn't be). Treat every new warning surfaced by a test run the same as a failing test:
  - Identify its exact source (don't guess "probably from a dependency") and either fix it at that source, or if it's genuinely upstream (a library's own internal deprecated call with no workaround), record it explicitly — file/line, the warning text, and why it can't be fixed here yet — rather than letting it scroll by unacknowledged.
  - Never add a blanket `filterwarnings("ignore")` or similar suppression to make output quieter — that hides the next new warning too, not just the one you're currently looking at.
  - This is what "long-running, easy to maintain" means in practice: the software should still build and run cleanly after routine dependency upgrades, years from now, not accumulate deprecated-API debt that turns every future upgrade into an archaeology project.

## Code Readability

## bot_tui / urwid Patterns

- **TUI-01** — **A `urwid.ListBox` (or any `Filler`) that gets a brand-new `SimpleListWalker`/widget object on every redraw tick silently resets the user's scroll/focus position to the top.** `urwid.ListBox` and its `.focus_position` are properties of the walker *object* — swap in a fresh one and the old scroll state is simply gone, even though the visible rows look the same as before. This has been found and fixed twice independently in this codebase (Collector pane, Story 6.1; Bots pane, this incident) — both reported in production as "the page jumps [back] to the top" / "can't scroll." **The fix, in both cases:** never rebuild the `ListBox` itself on a routine per-tick refresh. Keep it as a persistent instance attribute (`self._foo_body`) plus a `self._foo_shape` sentinel (`None` / `"cold_open"` / `"rows"`); only swap the widget's *type* when the shape genuinely changes (empty ↔ populated); for a same-shape update, mutate the existing walker in place via slice-assignment (`listbox.body[:] = new_widgets`) — this is what actually preserves `.focus_position` across ticks. See `app.py`'s `_refresh_collector_body`/`_refresh_bots_body` for the reference implementation. **Any new scrollable pane in `bot_tui` must follow this pattern from the start** — a "no round-trip needs it yet" YAGNI deferral here specifically has already caused the same bug to ship twice; don't defer it a third time.
- **TUI-02** — **A fixed-width text column must truncate, not just pad.** Python's `f"{text:<N}"` only left-pads a *short* string to width `N` — it does not clip a *longer* one, so any field whose length isn't from a small closed vocabulary (an operator-chosen `bot_id`, an instrument ticker whose length varies, e.g. `RENDER-USD-PERP.DYDX` at 20 chars vs `BTC-USD-PERP.DYDX` at 17) will overflow its intended column width on some rows and push every column after it out of alignment for that row only — other rows still line up, so the table looks randomly, inconsistently broken rather than obviously wrong in one place. Use a real fit-to-width helper that truncates-with-ellipsis when over length (see `bots_pane.fit()`) for any field without a small fixed set of possible values; plain `:<N`/`:>N` remains fine for genuinely bounded fields (short enums like `mode`/`running`/`position_side`).

## Nautilus Usage Patterns

- **NAUT-01** — **Known silent bug:** `Price(decimal, precision)` silently returns a wrong value for some inputs. Example: `Price(Decimal("61090.59855"), 16)` returns `61090.5985500000026624`. **Never use this constructor for re-stamping.** Always re-stamp via:
  ```python
  raw = int(value.scaleb(new_precision))   # Decimal.scaleb() — exact integer arithmetic
  price = Price.from_raw(raw, new_precision)
  qty   = Quantity.from_raw(raw, new_precision)
  ```
  Use `Decimal.scaleb()` + `Price.from_raw()` / `Quantity.from_raw()` whenever setting a value at a different precision. Never round-trip a market-data value through `float` before it is safely inside a `Price`/`Quantity`.

- **NAUT-02** — All data written via `ParquetDataCatalog.write_data()`. No hand-rolled Parquet schemas. The catalog API owns the Arrow schema and partitioning; working around it breaks catalog reads.

- **NAUT-03** — Backtests use `BacktestNode` + `BacktestDataConfig`. No custom simulation engine. Reference strategies via `ImportableStrategyConfig` by string path so parameter sweeps and time-range filtering require no code changes.

## Signal Architecture: 1s-Based, Not Event-Driven

HFT signals are computed from **1-second sampled snapshots** (`DydxSecondSnapshot`), not from raw order book delta events.

**What is stored in Parquet (`DydxSecondSnapshot`):**
- Top-20 bid/ask levels: `bid_prices`, `bid_sizes`, `ask_prices`, `ask_sizes` (lists)
- Per-side trade volume: `buy_volume`, `sell_volume`

**What is NOT stored — computed on read via `ml_signals/indicators.py`:**
- `microprice` = `Microprice().update_raw(bp, bs, ap, as_)` — derivable from level 0
- `spread` = `ask_prices[0] - bid_prices[0]` — derivable from level 0
- `ofi_N` = `MultiLevelOFI(levels=N)` replayed over consecutive snapshots
- `obi_N` = `MultiLevelOBI(levels=N).update_raw(bid_sizes, ask_sizes)`

**- SIGNAL-01** — If a value can be derived exactly from stored level data, do not store it. Store raw inputs; compute signals. Keeps the schema minimal and lets strategies try any N-level variant without re-collecting.

## Metrics Single Source of Truth (Web Dashboard ↔ bot_tui)

Every metric/indicator shown in both the web UI (`frontend/` via `data_api`) and `bot_tui` must trace back to exactly one calculation — never two independent implementations of the same formula, and never two independently-running instances of the same stateful indicator class.

- **SSOT-01** — Stateless, single-snapshot derivations (spread, mid price, CVD, volume_delta, avg_trade_size, microprice) live as plain functions/classes in `ml_signals/indicators.py`. Every UI computes them by calling that shared function on the snapshot it already holds — never a local inline reimplementation of the formula. Safe because the output is a pure function of the current snapshot: two processes calling the same function on the same input can never disagree.
- **SSOT-02** — Stateful/rolling/windowed metrics (OFI/OBI and their z-scores, volatility, pct_1h/pct_24h, EMA trend, `book_features` depth/imbalance/cancellation/cum_delta) must be computed exactly once, by exactly one long-running process, and published (Redis pub/sub or a shared store) for every other reader to consume verbatim. Never let two processes independently subscribe to the same raw feed and run their own copy of a rolling-window indicator, even via the identical shared class — differing startup time, differing window contents, and floating-point accumulation order will silently diverge the two numbers over time. `ranking_engine` is the sole owner of this class of computation (architecture AD-9); `dashboard`/`bot_tui` are pure readers of its published output, never independent computers of it.
- **SSOT-03** — Before adding any new metric to either UI, check whether it already exists in the other first. If so, locate and consolidate its current implementation onto one shared source before displaying it in the new place — never duplicate to move faster.
- **SSOT-04** — The coin ranking page is one feature with two renderers: the web UI (`frontend/` via `data_api`) and `bot_tui` (TUI). Any functionality applied to it — new columns/metrics, sort/filter behavior, ranking logic changes — must land in both, backed by the same shared source (per SSOT-01/02). Treat a request to change "the ranking page" as covering both unless the user scopes it to one explicitly.
- **SSOT-05** — Same rule for the single-coin detail view: the metrics/indicators shown must match between web and `bot_tui`, per-coin. The web dashboard additionally has a per-coin page with visual graphs (charts/plots) — that page is web-only and is not duplicated in the TUI; `bot_tui`'s coin detail should instead surface a link/reference to the web graph page rather than reimplementing charting in the terminal.

## Desktop ↔ VPS Connection

The web UI (`data_api` serving the React SPA, Story 15.10 retired the old `dashboard`
service) and `bot_tui` normally run *on* the VPS (`nifelheim`) alongside `collector`,
inside Docker (`make up`). From the desktop there is exactly **one tunneled web surface,
`data_api`** — it serves the UI and its API from the same port, so no local process is
needed for the browser. Shell functions in `~/.zshrc` (outside this repo):

- **`_troll_tunnel_ensure`** — opens one background SSH tunnel to `$TROLL_VPS_HOST`
  (`nifelheim`) forwarding two ports: `6379` (Redis — live snapshots/rankings pub/sub,
  needed by `bot_tui`) and `9100` (`data_api`: the React UI, REST/WebSocket API, the
  Parquet catalog + `metrics.db` read-only, and the picker's own `chart_indicators.toml`
  config writes, Story 15.6). Idempotent — checks `fuser 6379/tcp` first, so repeated
  calls don't stack tunnels.
- **`troll-web`** — ensures the tunnel, then opens Firefox at `http://localhost:9100`
  (the tunneled `data_api`). There is no local dashboard process any more, so no
  `WEB_PORT` to keep in sync between desktop and VPS `.env` files.
- **`troll-tui`** — same tunnel dependency, plus starts `scripts/open_listener.go`
  locally (`$TROLL_OPEN_LISTENER_PORT`, `8901`) so that pressing "open chart" inside
  `bot_tui` (which itself runs via `make tui`, rebuilding only the thin `bot_tui` Docker
  layer) can pop a chart open in the desktop's browser. `bot_tui` only needs live Redis;
  its chart deep-link targets `DASHBOARD_BASE_URL` (defaults to `data_api`'s port).
- **`troll-logs`** — a separate, independent tunnel (`-L 8080:localhost:8080` to
  `nifelheim`) for Dozzle, the container log viewer; unrelated to the Redis/`data_api`
  tunnel above. Opened with plain `xdg-open`, not Firefox directly.
- **`troll-down`** — tears everything back down: kills the `open_listener` process and any
  `ssh.*nifelheim` tunnel (both the Redis/`data_api` one and the Dozzle one).

**Migration note (Story 15.10):** `_troll_dashboard_ensure`, `$TROLL_WEB_PORT` and
`make dashboard` no longer exist in the repo — `~/.zshrc` must drop the first two and
point `troll-web` at `http://localhost:9100`, or it will poll a port nothing listens on.

**Why this exists:** running the web UI/TUI on the desktop instead of the VPS gets a
real browser and better interactivity without exposing any VPS port publicly — SEC-01
still holds, since nothing new is bound to `0.0.0.0` on `nifelheim`; the connection is
entirely outbound SSH from the desktop.
